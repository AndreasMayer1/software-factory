# Goal: Extend requ-derive-from-flow to emit integration-test requirements

## Objective

REQ-PROC-002 AC-09 names integration tests as required for specific surfaces (data-entry workflow, data-transfer, performance measurements, end-user workflows on critical paths). The user's preference (2026-05-14 F3): integration-test requirements should live as a non-functional epic, with one Feature per user flow, rather than as ACs embedded in functional requirements (which would couple integration tests to specific functional ACs and force re-scoping every time the functional requirements move).

The research summary `2026-05-14_research_automation_and_self_regen.md` §6 identified `requ-derive-from-flow` as the right home for this work: it already reads every flow.md, runs an Opus matrix in Phase 2, and emits non-functional explore goal.md files in Phase 4.2. Adding an integration-test row to the matrix is a small extension that fits the skill's existing shape.

## Requirements Summary

REQ-PROC-002 AC-09 (integration test coverage for critical surfaces). User feedback F3 (2026-05-14).

Current requirements: ../../requirements.md
Research summary used to design this: `../../../code_quality/2026-05-14_research_automation_and_self_regen.md` §6.

## Scope

### In Scope

**Skill file to edit**: `.claude/skills/requ-derive-from-flow/skill.md`.

1. **Phase 2 Opus matrix instruction** (around line 261 per the research): add a side-output instruction:

   > For every flow processed, emit exactly one matrix row of status `integration_test_needed` targeted at `requirements_tasks/non-functional/integration_tests/<flow_id>/` UNLESS such a requirement already exists at that path (in which case status `exists_complete` is emitted instead).

2. **Phase 2 gap taxonomy** (line 267): add the new status value `integration_test_needed` alongside the existing eight (`exists_complete`, `exists_needs_update`, `exists_placeholder`, `new_needed`, `decision_needed`, `decision_needed_exploration`, `foundation_gap`, `out_of_scope`).

3. **Phase 4.2 goal.md template variant** (lines 521–594 area): a small variant for `integration_test_needed` rows with scope text along the lines of:

   > Define what integration-test coverage this flow requires: happy path through every primary scenario step; each exception path; the boundary conditions named in the flow's `exceptions:` and `boundaries:` YAML.

   The generated goal.md is `type: explore` (since the integration-test requirement itself doesn't yet exist — the explore task creates it). The `parent_requirement` field references the new non-functional integration-tests epic if one already exists at `requirements_tasks/non-functional/integration_tests/requirements.md`; if not, the explore task creates the epic too.

4. **Phase 4.2 Suggested Package rule** (line 339): for `integration_test_needed` rows, suggest the same `target_package` as the primary functional gap of the flow. Reason: integration tests should ship together with the features they cover, not in a separate package.

5. **One-time bootstrapping**: as part of this task, manually create the epic-level `requirements_tasks/non-functional/integration_tests/requirements.md` with the standard non-functional-epic frontmatter and a short Overview / Purpose. Allocate the REQ-ID via `python3 scripts/requirements/allocate_req_id.py --parent-id REQ-NFUNC --parent-path requirements_tasks/non-functional/`. Subsequent per-flow Features land under this epic naturally as `requ-derive-from-flow` runs.

### Out of Scope

- Writing the integration tests themselves. The skill produces *requirement* goal.md files; the integration tests are downstream impl work scheduled when each feature's requirement is filled in via `requ-explore`.
- Backfilling integration-test requirements for flows that already exist. The next `requ-derive-from-flow` run on each flow will emit the new row automatically.
- Changing `release-begin-impl-finalize` — per research §6, no change there required; Phase 1 coverage audit already picks up new requirements automatically.
