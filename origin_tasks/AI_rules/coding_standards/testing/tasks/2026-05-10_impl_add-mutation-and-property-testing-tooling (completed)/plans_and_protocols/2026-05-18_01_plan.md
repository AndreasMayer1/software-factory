## Tool choice

### Mutation tooling: `mutation_test` (pub.dev 1.8.0)

Evaluated against `dart_mutant` (dartmutant.dev):

| Dimension | `mutation_test` 1.8.0 | `dart_mutant` |
|---|---|---|
| Distribution | pub.dev dev_dependency — `dart run mutation_test` | Rust binary; no pub.dev package, install path unclear |
| lcov scoping | Confirmed: `--coverage coverage/lcov.info` flag, only mutates lines marked instrumented and hit | Not documented |
| Diff-only mode | Confirmed: invoke with file list from `git diff --name-only` (incremental CI mode) | Not documented |
| Mutation strategy | Regex-based (text replacement with capture groups) | AST-aware (tree-sitter), ~40 operators |
| Reports | HTML / XML / Markdown / JUnit | HTML / JUnit |
| Parallelism | Not specified (single-process) | Parallel (Rust) |
| Maturity | Published; latest 1.8.0 ≈ 3 months ago | Newer; binary distribution flow not yet exercised by this project |

**Choice rationale.** AC-02 explicitly requires lcov-scoped runs and diff-only mode. `mutation_test` documents both; `dart_mutant` documents neither. The pub.dev / `dev_dependencies` install path also fits the project's "no extra OS install" preference for tooling that runs from the test suite (the `claude-install-os-tool` flow exists but adds friction). The regex-vs-AST gap matters less here because mutation operators for the project's domain logic (arithmetic, comparison, boolean, null-safety) are well-served by text-replacement rules. Runtime cost is bounded by the lcov filter and the small critical-path scope (6 files today).

If `mutation_test` later proves too slow or its regex rules produce too many false positives, the configuration in `test/mutation/` is self-contained and a swap to `dart_mutant` can be done without disturbing test code.

### Property-based testing: `glados` (pub.dev 1.1.7)

Already named by REQ-PROC-002 AC-03. Integrates with `package:test`; `Glados<T>().test()` replaces `test()` for property-based cases. No alternative needed.

## Configuration shape

Lists the six AC-04 critical-path files (the two implemented categories: version_migration, data_transfer_serialization). Uses built-in mutation operators (no `<rules>` override). Threshold failure: 80 (matches AC-02). Test command: `flutter test`. Output: HTML + Markdown.

### How operators are scoped to "arithmetic, comparison, boolean, null-safety"

`mutation_test`'s built-in Dart rules cover these categories. No custom rules block is added; if the built-in set produces noise, a project-specific rules XML can be added later (the AC-02 phrasing names the categories, not a specific operator set).

## Baseline run strategy

The full lcov-scoped mutation run on the 6 critical-path files is expected to take 10s–10s+ of minutes (each mutation re-runs the affected test subset). To keep this task tractable in one session and to honour the goal's "or a sample if the full run is too long" clause:

1. **Dry-run pass (mutation count)** on the full critical-path config — produces the mutation total without running tests. Records the structural baseline (how many mutants the operator set generates).
2. **Sample real run** on the smallest file (`transfer_chunk.dart`, value object) — gives a real kill-rate baseline for one critical-path file.
3. **Full real run is deferred** to TASK-PROC-002-XX (surviving-mutant remediation chain) where the actual remediation work consumes the long-running results.

Both numbers are recorded in `2026-05-18_02_protocol.md`.
