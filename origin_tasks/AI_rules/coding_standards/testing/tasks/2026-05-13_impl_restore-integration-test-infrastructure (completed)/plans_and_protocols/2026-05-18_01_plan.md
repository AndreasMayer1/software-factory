### 1.2 Why the existing suite cannot be incrementally fixed

The current `integration_suite_test.dart` rebuilds a parallel router definition (lines 188–348) that has diverged from production routing. Maintaining two router definitions in lockstep is exactly the maintenance burden that "tests broke after every PR" describes in the user's recall. The perf test demonstrates the alternative: per-file `setUp` that mocks at the use-case layer and lets the production router (or a minimal subset of it) handle routing. The plan adopts the perf-test pattern as the canonical scaffolding shape.

### 1.3 Centralised DI helper — `integration_test/helpers/test_di.dart`

This is the single most important new file. It is the artifact that materialises the lesson from goal.md "Notes — Historic fragility: state did not reset between tests".

**Path**: `integration_test/helpers/test_di.dart`

**Public surface** (exact signatures):

```dart
/// Hive box name constants (mirror lib/main.dart lines 43–44).
const String kRoleBoxName = 'role_storage';
const String kAppPreferencesBoxName = 'app_preferences';

/// Build-or-rebuild the full integration-test DI graph.
///
/// Why: The historic fragility (goal.md Notes) was that GetIt registrations
/// leaked between tests — singletons created by one test served the next, with
/// stale state. This helper enforces a hard reset → register-Hive → mock-role
/// → configureDependencies → register-test-router sequence. Every test calls
/// it in setUp; the reset in tearDown (see [tearDownTestDi]) makes the next
/// call start from zero.
Future<void> setUpTestDi({
  required AppRole stubbedRole,           // controls router redirect target
  bool isFirstLaunch = false,             // controls CheckFirstLaunchUseCase
  List<RouteBase> routes = const [],      // empty -> use built-in minimal routes
  void Function(GetIt getIt)? overrides,  // last-mile mock injection
}) async;

/// Tear down the DI graph between tests. MUST be invoked in every tearDown.
///
/// Why: Without this, GetIt singletons from test N are still registered when
/// test N+1's setUp begins — `getIt.reset()` inside setUp is too late if any
/// async work from test N is still holding a reference. Resetting in tearDown
/// while the prior test's stack is still on the call stack is the only safe
/// order.
Future<void> tearDownTestDi() async;

/// Synthetic-user fixture (REQ-PROC-052 AC-07). Produces a recognisably-fake
/// `QuestionnairePlan` for use in data-transfer tests. Latin pseudonyms and
/// placeholder dates per the privacy-and-security rule.
QuestionnairePlan buildSyntheticPlan({String name = 'Test Plan – Lorem'});

/// Hive bootstrap for a single test run (mirrors main.dart but with a
/// per-process temp directory so parallel `flutter test` invocations do not
/// collide on the role_storage box file).
Future<String> initIsolatedHive();         // returns the temp path used

/// Cleanup counterpart to [initIsolatedHive]. Closes Hive and deletes the dir.
Future<void> tearDownIsolatedHive(String hiveTestPath);
```

**Internal structure** (no body, just the order so the implementer follows it verbatim):

```
setUpTestDi:
  1. await SharedPreferences.getInstance().then((p) => p.clear())
  2. final roleBox = Hive.box<String>(kRoleBoxName); await roleBox.clear()
  3. await getIt.reset()                  // <- reset BEFORE re-registration
  4. getIt.allowReassignment = true
  5. getIt.registerSingleton<HiveInterface>(Hive)
  6. // AppDatabase: register an in-memory NativeDatabase (mirrors
  //    testing.md §24); REQ-PROC-046 AC-04 path that depends on AppDatabase
  //    is not exercised by these flows, but configureDependencies()
  //    requires it.
  7. await configureDependencies()
  8. await getIt.allReady()
  9. // Mock role use cases (mirror perf test lines 122–144)
  10. // Register the test GoRouter (helper builds it from `routes` or default)
  11. overrides?.call(getIt)

tearDownTestDi:
  1. await getIt.reset(dispose: true)
```

### 2.2 Data-transfer pipeline — AC-09 (b), single-process simulation

**File**: `integration_test/flows/data_transfer_pipeline_flow_test.dart`

**Test names**:
- `Data Transfer Pipeline round-trips a synthetic plan through chunk encode and decode`
- `Data Transfer Pipeline preserves per-chunk header sequence id and ordering`

**Rationale for not using the UI**: this test exercises `PlanTransferPipeline.serialize()` → `List<TransferChunk>` → `PlanTransferPipeline.deserialize()` directly. The QR-display widget and camera-scan widget are deliberately out of the test path because (a) goal.md scope restricts to single-process and (b) the value of an integration test here is the round-trip correctness of the pipeline under the integration-test binding (which catches platform-channel surprises that unit tests miss).

**Why this lives in `integration_test/` and not `test/unit/`**: per AC-09 (b) the pipeline is listed as a critical surface for integration coverage. Unit tests already cover the pipeline in isolation; the integration test verifies the same code path under the production binding plus DI graph (`PlanImportService`, `PlanSerializationService` resolved via GetIt). If during implementation the engineer concludes a unit test fully covers this and the integration test adds zero value, escalate to user before deleting — do **not** silently drop AC-09 (b) coverage.

**DI graph**: `setUpTestDi(stubbedRole: AppRole.therapist())`. `PlanTransferPipeline` is `new`-instantiated (no DI registration in current code); `PlanImportService` resolved via `getIt<PlanImportService>()`.

**Selectors needed**: none — this is a non-widget integration test (uses `testWidgets` only for the integration binding's `IntegrationTestWidgetsFlutterBinding.ensureInitialized()` lifecycle; no UI interaction).

**Test body skeleton — round-trip**:
```
1. await setUpTestDi(stubbedRole: const AppRole.therapist());
2. final plan = buildSyntheticPlan();      // §1.3 fixture
3. final pipeline = PlanTransferPipeline();
4. final chunks = pipeline.serialize(plan, sequenceIdOverride: 0x1234);
5. expect(chunks, isNotEmpty);
6. final result = pipeline.deserialize(chunks);
7. result.fold(
     (failure) => fail('round-trip failed: $failure'),
     (decoded) {
       expect(decoded.uuid, plan.uuid);
       expect(decoded.name, plan.name);
       expect(decoded.questionnaireUuids, plan.questionnaireUuids);
     },
   );
```

**Test body skeleton — per-chunk correctness**:
```
1. As above, build chunks with sequenceIdOverride: 0x4242.
2. for (var i = 0; i < chunks.length; i++) {
     expect(chunks[i].sequenceId, 0x4242);
     expect(chunks[i].chunkIndex, i);
     expect(chunks[i].totalChunkCount, chunks.length);
   }
3. // Shuffle and re-deserialize — assert reorder-tolerance.
   final shuffled = [...chunks]..shuffle(Random(42));
   final result = pipeline.deserialize(shuffled);
   expect(result.isRight(), isTrue);
```

The shuffle assertion catches the most likely regression mode (a refactor that loses chunk-order tolerance).

## 3. Phase 3 — Runner & Documentation

### 3.1 Runner integration

The runner script (`scripts/integration_test_runner/run_individual_integration_tests.ps1`) currently hard-codes test names that point at the dead suite (lines 36–50). Two changes:

**Change A — `$testSuiteFile`**: change line 12 from
`$testSuiteFile = "integration_test/integration_suite_test.dart"` to discovery-based. Concretely, replace with a loop over `Get-ChildItem integration_test/flows/*_flow_test.dart` and invoke `flutter test --plain-name` per file. The new files do **not** share a parent group, so we lift the `--plain-name` strategy to filename-based discovery; each `*_flow_test.dart` file is invoked directly via its path.

**Change B — `$testNames`** (lines 36–50): delete the manual list entirely. The new model uses one `testWidgets` per file (with optional intra-file groups when a flow has sub-cases, as in §2.2). The runner discovers files, not test names.

Pseudocode for the replacement loop:
```powershell
$flowFiles = Get-ChildItem -Path "integration_test/flows" -Filter "*_flow_test.dart"
foreach ($flowFile in $flowFiles) {
    $relativePath = "integration_test/flows/$($flowFile.Name)"
    flutter test $relativePath -d windows
    # log to outputDir as before
}
```

**Why filename discovery is robust here while it was unstable before** (per `doc/testing/integration_testing.md` Best Practices line 23): the historical instability was running multiple test files within a single dart entry point (`flutter test integration_test/`). Invoking `flutter test <single_file>` per file is the workaround already documented and used today. We're just removing the now-redundant manual `--plain-name` list because each flow file has one (or few) test entries that don't need disambiguation.
