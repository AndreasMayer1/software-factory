# Developer Environment Contract (No Host-Execution Bridge)

## Overview

This requirement defines the supported developer environment for the project, the alternative environments that remain functional, and the explicit decision against operating a host-execution bridge between the devcontainer and the Windows host. The supported configuration places the project source-of-truth on WSL2 ext4, runs a VS Code devcontainer at the parent-folder level of the `flutter_app/` repository (a placement chosen for git-worktree compatibility), and uses a continuous one-way sync daemon to mirror the WSL working tree to a Windows NTFS folder so manual Windows-target operations can use a normal NTFS path. No automated container-to-host execution path exists in any configuration. Daily development — including every back-pressure quality gate and integration tests against the Linux desktop target that enable LLM-autonomous coding — runs entirely inside the container at native ext4 speed. Windows-target operations are initiated by the developer manually against the NTFS mirror.

## Purpose

The app provider (PERSONA-015) is a single solo developer running an LLM-heavy workflow against a mental-health Flutter application. The persona's grounded values include *"longevity over velocity"*, *"the codebase must survive periods where the creator has no time to touch it"*, *"simplicity is a survival strategy for one-person maintenance over years"*. Two pressures converged to force a decision on the developer-environment topology.

The first pressure was speed. With the project on Windows NTFS and the devcontainer reading via DrvFs (WSL → NTFS file IO), the analyzer-driven back-pressure gate `flutter analyze` ran in 10–17 minutes per invocation, and `dart fix --apply` regularly exceeded the 10-minute container timeout. With back-pressure gates running on every change, the slow analyzer turned routine LLM-driven editing into an unworkable feedback loop.

The second pressure was security. A penetration-test exploration (TASK-PROC-054-01, summarized in `decisions/2026-05-19_no-host-bridge.md`) examined the previously-built `scripts/win-command-bridge/` mechanism that routed slow container-side commands to a Windows watcher. The pen-test established with concrete proof-of-concept paths that the bridge's whitelist enumerates *tool names* but not *code that runs*: every whitelisted tool (`flutter test`, `flutter analyze`, `dart fix`, `flutter build windows`, `smoke_test`, `flutter pub get`) interprets container-writable project files on the Windows host. While the watcher was online, the container's stated LLM-sandbox role did not hold — a fully-compromised LLM in the container had, in practice, the same privileges as the Windows user account running the watcher.

A multi-option exploration (TASK-PROC-054-02) evaluated five architectural responses spanning "harden the bridge with a restricted Windows user and a dispatcher facade" through "delete the bridge and accept manual Windows operations". Two empirical findings from that exploration narrowed the option set: (1) routing Windows tooling over the `\\wsl$\` UNC path is broken at multiple independent layers — CMD.EXE rejects UNC `cwd`, MSBuild lower-cases UNC components producing `MSB8064`/`MSB8065` warnings, Flutter strips leading backslashes from UNC paths, and `flutter pub get` inherits the cmd.exe shim failure; (2) the Windows Sandbox alternative is undermined by the analyzer's `.dartServer` cache (~1 GB) living inside the sandbox VM and rebuilding cold on every launch, eliminating the speed advantage that motivated the bridge.

The chosen response — the contract codified by this requirement — deletes the bridge entirely, moves the project source-of-truth to WSL2 ext4 so the speed problem disappears at its root, syncs to NTFS via a continuous sync daemon so manual Windows-target operations remain ergonomic, and adopts the Linux desktop target with a headless framebuffer as the primary LLM-autonomous integration-test path. The decision trades automated Windows-target validation for a strictly smaller attack surface (zero container-to-host execution code), a ~10× speedup on the daily container loop, a simpler operational footprint (one config file plus a sync daemon, no watcher to harden), and a strictly cleaner LLM sandbox (no container-to-host execution path of any kind exists). Manual Windows operations are tolerated as a release-time activity, consistent with the persona's emphasis on simplicity and longevity over per-task velocity.

## Behavior

### Filesystem topology

The supported topology has one source-of-truth root on WSL2 ext4 and two Windows-side derived roots. The WSL root holds the parent folder containing the devcontainer config, the `flutter_app/` git repository, and any sibling git worktrees spawned on demand. The first Windows-side root is the NTFS mirror produced by the continuous sync daemon and used exclusively for manual Windows-side operations; its specific path is a per-developer choice documented in the developer's setup. The second Windows-side root is a cloud-synced backup folder, mounted into the devcontainer at `/home/vscode/backup`, that receives a `git bundle --all` from the existing `.githooks/pre-push` hook on every push.

### Daily development model

The container is the execution environment for every command that is part of the change-and-verify loop. The `verify-quality` skill invokes its underlying tools (`flutter analyze`, `dart fix`, `flutter test`, `flutter pub get`, `flutter build apk`, `flutter build linux`, `flutter build web`) directly as container subprocesses against the WSL ext4 working tree. The back-pressure quality gates defined by REQ-PROC-046, REQ-PROC-002, REQ-PROC-051, and REQ-PROC-052 run in this environment without any host-side routing. Integration tests against the Linux desktop target run in this environment under a headless framebuffer. LLM agents iterating on widget visuals use Flutter's widget-test golden-file mechanism (no display server needed) and consume the produced PNGs by reading them from the filesystem.

No path crosses the WSL ↔ Windows boundary in the daily loop. The container, the WSL ext4 filesystem, and the toolchain installed in the container provide the full execution surface.

### Manual Windows-operations model

Three operations execute on the Windows host directly, initiated by the developer: building the Windows desktop binary, running the Windows desktop smoke test against that binary, and running Windows-target integration tests. The developer opens a Windows session, navigates into the NTFS mirror, and invokes the relevant command. The sync daemon's flush procedure is run before each manual build to guarantee freshness; the procedure is documented in the sync setup guide.

### Sync mechanism

A continuous one-way sync session keeps the Windows NTFS mirror current with the WSL ext4 working tree. The sync's behavior contract: changes in the WSL tree propagate to the NTFS mirror within seconds; deletions in the WSL tree propagate; the mirror's exclusion list omits build artifacts, the `.git` directory, OS swap files, and the local integration-test screenshot output directory so the mirror remains a clean working-tree snapshot suitable for Windows builds. Windows-side accidental writes (typically build outputs) are preserved rather than overwritten. The daemon is started by the Windows host at user logon with restart-on-failure semantics; its health can be inspected through the daemon's own status interface. Configuration details, the daemon's command surface, and the flush procedure are documented in the sync setup guide.

### Integration-test mechanism per target

- **Linux desktop**: the primary daily target. Runs inside the container under a headless framebuffer. LLM-autonomous. Fast (no emulator boot). This target is the platform on which the LLM verifies Flutter changes against the integration suite.
- **Android emulator** (extension architecture, optional implementation): a narrow Windows-side watcher, installed outside the repository, observes a sentinel file in the project tree and starts a configured Android Virtual Device. The watcher reads no project files and takes no parameters from the container; its security profile is materially narrower than the deleted bridge. Whether this extension is implemented does not change any other AC of this requirement.
- **Android physical device**: supported by the developer attaching a device to the Windows host and either forwarding USB into WSL or enabling wireless debugging on the device. The attachment procedure is documented in the Android setup guide.
- **Windows desktop**: manual on Windows host. Not part of the LLM-autonomous loop. Used for pre-release smoke validation per REQ-PROC-053 *verification_strategy*.

### Backup and disaster recovery

The three layers from AC-09 are sufficient that loss of any single layer does not produce loss of work. Additional layers (for example periodic full-distro export) are discretionary developer practice and live outside this requirement's contract.

### Configuration-agnostic correctness

On Mac, native Linux, native Windows without WSL, or a devcontainer without the parent-level layout, the project produces the same set of pass/fail outcomes as on the supported configuration for every quality gate and every integration test that the alternative environment is physically capable of running. The differences from the supported configuration are speed (in-container file IO over the alternative environment's filesystem) and reach (Windows-target operations require a Windows host; non-Windows configurations cannot perform them and the developer using such a configuration relies on a separate Windows host for release-time validation). No command, gate, or test changes behavior, silently skips, or falls back because the alternative environment is detected.

## Developer Guidelines

### Key Decisions

- **No host-execution bridge of any kind exists in the repository.** Any directory named `scripts/win-command-bridge/`, `scripts/host-bridge/`, or analogous, and any Windows-side watcher that polls for and executes whitelisted commands originating from container-writable files, contradicts this requirement. Tooling that historically routed through a bridge invokes its underlying tool directly inside the container.
- **WSL2 ext4 is the source-of-truth on the supported configuration.** The Windows-side NTFS mirror produced by the sync daemon is a derived copy, written one-way from the container side. Editing the NTFS mirror as a primary workflow contradicts this requirement; a developer who occasionally needs to edit Windows-side files (typically only when debugging native Windows runner code) flips the sync mode to bidirectional for that work and resolves the conflict markers that surface.
- **The `.devcontainer/` folder is located at the parent of `flutter_app/`, not inside it.** This placement supports git-worktree workflows where sibling worktrees under the parent open in the same container as the main repo. Placing `.devcontainer/` inside `flutter_app/` forces one container per worktree, which is materially slower and less ergonomic for LLM-driven multi-worktree work.
- **`flutter_app/.vscode/tasks.json` does not auto-launch host processes.** Auto-launch of a host-side script from a repository-tracked `tasks.json` is structurally identical to the V7 vector from the TASK-PROC-054-01 pen-test (LLM modifies file in repo → user opens workspace → trusted task fires).
- **Linux desktop is a first-class Flutter target for this project, enabled in the Flutter SDK configuration and scaffolded in the repository.** It is not a user-facing deployment target; it is the platform on which the LLM-autonomous integration-test path runs. The user-facing deployment targets (Windows desktop, Android, and any future platform) are unaffected.
- **Linux is the authoritative source for committed widget goldens.** Goldens regenerated on Windows or macOS are not byte-identical to Linux-rendered goldens and are not the canonical artifact. A developer working on goldens on an alternative environment regenerates them on the supported configuration before committing.
- **The sync daemon is operational infrastructure, not application infrastructure.** Its presence or absence does not change which commands the project runs or what they produce — only the developer's ergonomics for manual Windows-side operations. A contributor on an alternative environment does not run the sync daemon and is not expected to.
- **The AC-13 sleep watcher is an optional, narrow-action-surface host-side watcher, not a bridge.** It belongs to the same permitted class as the AC-07 emulator watcher: it reacts to container-produced state (`automation/state.json`) with a fixed action set (suspend, register one fixed-name wake task) and executes nothing that originates from container-writable files. Because it runs elevated, the run target is installed outside the repository; the `scripts/windows/` copy is the source of record only. Its presence or absence changes nothing the project builds, tests, or produces — only whether the host sleeps automatically after an unattended automation run.
- **The safety control for host-side execution is deterministic + diff-bounded human review, never an LLM gate (AC-17).** Because the developer will not re-read every Windows-host script on every run, the per-run burden is bounded to the *diff* since the last install (surfaced by the install tool with a SHA-256 manifest), backed by a small deterministic denylist checker that is itself reviewed once and pinned by hash. An LLM may *assist* the diff review (summarize, flag) but is never the gate: an LLM-as-gate is circular (the launcher/checker is itself unreviewed code that runs first), prompt-injectable from the files under review, non-deterministic, and lulls the developer into skipping review. A disposable Windows Sandbox provides containment for first/unreviewed runs and is the dev/test environment for the pure-logic PowerShell (it does not help the suspend/wake or Flutter-Windows-build paths, which stay host/hardware-bound).
- **Windows-host scripts are location-independent by construction (AC-14/AC-15/AC-16).** Because the elevated run target lives outside the repository, a Windows-host script must not assume it runs from the repo tree. The project path it operates on comes from the shared resolution mechanism (explicit arg → co-located config → in-repo auto-derivation), never from a hardcoded path. The install tool is what places the scripts out-of-repo and writes the config that points them at the synced NTFS mirror. This generalizes the AC-13 manual `-ProjectPath` step into a uniform mechanism so the set of host-side scripts can grow without each one re-solving "where is the project?". A new `scripts/windows/` script that derives its project path solely from its own location is a defect — it breaks the moment it is installed out-of-repo.

- **The `write-setup-manual` skill is the mechanism for keeping setup guides current (AC-19).** Whenever `.devcontainer/devcontainer.json`, `.devcontainer/setup.sh`, `scripts/windows/`, quality-gate scripts, toolchain version pins, or any AC of this requirement changes, invoke the skill. It reads those files as sources of truth, proposes changes to the affected guides for developer review, and applies only the approved changes. Letting a guide drift after an environment change contradicts AC-10.

### Common Pitfalls

- **Reintroducing the bridge.** A future contributor encountering a slow container-side command may be tempted to route it through a watcher. The bridge's pen-test and the ADR explain why every variant of this pattern dissolves the container sandbox while the watcher is online. Reintroducing the pattern reintroduces the entire V1–V6 attack surface. The contract response to a new slow command is to make it not-slow inside the container (move project files to ext4 if not already, exclude irrelevant trees from the operation), or to accept it as a release-cadence operation rather than a per-change one.
- **Placing `.devcontainer/` inside `flutter_app/`.** The Microsoft-canonical layout nests `.devcontainer/` inside the repository. That layout is correct for projects that do not use the parent-folder-for-worktrees pattern; it contradicts this requirement for projects that do.
- **Adding host-side auto-launch tasks to any `.vscode/tasks.json`.** A `runOn: folderOpen` entry that shells out to the host (PowerShell, `wsl.exe`, `cmd.exe`) is a candidate for the same V7 vector class as the deleted bridge watcher launcher. Auto-launch entries are restricted to in-container, repository-internal commands; host-side automation is started by the developer, by the Windows host's scheduled-task mechanism, or not at all.
- **Pointing the sync mirror at a cloud-synced folder.** Cloud-sync clients (OneDrive, Dropbox, Google Drive) interact poorly with Flutter build artifacts, git lock files, and the sync daemon's own state. The sync mirror lives on plain local NTFS; backup duty is carried by the pre-push bundle (which already lands in a cloud-synced folder) plus the GitHub remote.
- **Treating WSLg / X11 forwarding as a prerequisite.** Visible Linux app windows are a developer-convenience nice-to-have, not a test requirement. The integration-test path is headless; the widget-visual-iteration path needs no display server at all.
- **Pointing the sleep-watcher shortcut at the Mutagen mirror or `\\wsl$\…`.** The AC-13 sleep watcher runs as Administrator. If the shortcut targets the copy inside the Mutagen mirror (or the WSL source-of-truth over a UNC path), the exact `.ps1` that runs elevated is LLM-writable through a normal commit — the sync propagates a hostile edit to the runnable file, and the next click executes it with Administrator privilege. This is the V7 vector class from the TASK-PROC-054-01 pen-test (LLM modifies a repo-tracked file → user runs it under trust). The watcher must run from a copy installed outside the repository; the repository copy under `scripts/windows/` is the source of record, not the run target. Re-copy on intentional script updates is the deliberate cost of keeping the elevated script out of the container's write reach.
- **Building an LLM-as-gate "is this script safe?" checker for host execution.** It feels like it solves the "I won't review everything every time" problem, but it relocates the trust problem rather than solving it: the checker/launcher is itself unreviewed code that runs first, the reviewing LLM can be prompt-injected by the files it inspects, verdicts are non-deterministic, and a green light erodes the human review that is the actual control. The supported answer is diff-bounded human review (only what changed) + a deterministic denylist checker + optional advisory-only LLM summarization + Sandbox containment.
- **A new `scripts/windows/` script that finds the project by walking up from its own location.** This is the natural pattern for an in-repo script, and it is exactly what breaks once the script is installed out-of-repo (AC-14/AC-15): two levels up from `<install-dir>/...` is not the project tree. Host-side scripts obtain the project path from the shared resolution mechanism (explicit arg → co-located config → in-repo auto-derivation as the last resort), never from own-location derivation alone.
