# ADR: No Host-Execution Bridge for the Flutter Developer Environment

**Date**: 2026-05-19
**Status**: Accepted
**Deciders**: app provider (PERSONA-015)
**Supersedes**: the previous `scripts/win-command-bridge/` implementation (TASK-PROC-054-01, TASK-PROC-054-02)

---

## Context

Two pressures forced this decision, and they pulled in opposite directions until the chosen architecture made them stop competing.

The first pressure was speed. With the project source tree on Windows NTFS and the devcontainer reading it through DrvFs (the WSL kernel's 9P client onto NTFS), the analyzer-driven back-pressure gate `flutter analyze` over the full `lib/ + test/ + integration_test/` tree took 10–17 minutes per invocation. `dart fix --apply` over the same surface routinely exceeded the 10-minute container subprocess timeout and had to be killed. With the closed gate set defined by REQ-PROC-046, REQ-PROC-002, REQ-PROC-051, and REQ-PROC-052 running on every change, the slow analyzer turned routine LLM-driven editing into an unworkable feedback loop. The published WSL performance research (the consolidated `\\wsl$\` / DrvFs source set is referenced in the *Evidence* section below) consistently shows the same root cause: a 9P file-system frontier between a Windows host and a Linux process, with per-file round-trips dominated by a hardcoded small `msize` and a single Hyper-V socket, is between roughly an order of magnitude and ~70× slower than native ext4 for the many-small-files fan-out pattern that `flutter analyze` and `dart fix` produce.

The second pressure was security. The project's previously-built bridge (`scripts/win-command-bridge/`) was a Windows-host PowerShell watcher that read whitelisted command IDs out of a container-writable signal file and executed the corresponding tool — `flutter analyze`, `flutter test`, `dart fix`, `flutter pub get`, `flutter build windows`, `smoke_test_windows.ps1` — on the Windows host with the watcher user's privileges. The stated security model was "the container can only name a command_id; it cannot inject shell." A penetration test (TASK-PROC-054-01) examined that model adversarially. It established with concrete proof-of-concept paths that the whitelist enumerates *tool names* but not *code that runs*. Every whitelisted tool interprets files in the project tree. The project tree is, by design, fully writable from inside the container — the LLM edits it. The bridge therefore reduces to: while the watcher is online, anything the container can write into the project (a `*_test.dart` file, a `CMakeLists.txt` line, an `analysis_options.yaml` plugin entry, the `smoke_test_windows.ps1` body itself) executes on the Windows host with the watcher's privileges. The pen-test enumerated this in vectors V1–V16; V1 (`flutter test` running attacker-planted Dart on the host) and V2 (`smoke_test` running attacker-overwritten PowerShell on the host) were both rated **Critical** — no bypass needed, just the whitelisted behaviour. The container's stated LLM-sandbox role did not hold while the watcher was online.

These two pressures together meant: a bridge solved the speed problem only by dissolving the sandbox. Tightening the watcher couldn't help — the whitelisted tools' interpretation of the project tree was the attack surface, not the watcher script itself.

A multi-option exploration (TASK-PROC-054-02) evaluated five architectural responses spanning "harden the bridge" through "delete the bridge entirely". The decision below selects the last of those.

## Decision

**The project operates no host-execution bridge.**

The supported developer configuration places the project source-of-truth on a WSL2 ext4 filesystem (where the speed problem disappears at its root because the analyzer runs against native ext4 instead of through 9P/DrvFs), runs a VS Code devcontainer at the parent-folder level of the `flutter_app/` repository (a placement that lets sibling git worktrees share one container), keeps a continuous one-way Mutagen sync from the WSL ext4 working tree to a Windows NTFS mirror folder so manual Windows-target operations have a normal NTFS path to operate on, and uses the Flutter Linux desktop target under a headless X virtual framebuffer (`xvfb`) inside the container as the LLM-autonomous integration-test path. Windows-target operations — `flutter build windows`, the Windows desktop smoke test, Windows-target integration tests — are initiated by the developer manually against the NTFS mirror; no automated container-to-host execution path exists.

## Alternatives Considered

### Option A — Phase 2 NTFS+bridge with a restricted Windows user

This option kept the project on Windows NTFS, kept the bridge, and hardened the host side by running the watcher under a dedicated low-privilege Windows local account (no admin, no access to `%USERPROFILE%` SSH keys / browser session data, AppLocker-restricted to the small set of binaries the watcher launches, Job-Object-scoped to prevent process-spawn outside the policy). The model is the Chromium-style "untrusted renderer + brokered policy" pattern: the project tree remains in the host's trust zone, but the host-side runner has its rights pre-stripped so a successful V1/V2 exploit lands inside a small blast radius rather than the full developer account.

This option was rejected because it left the load-bearing assumption from the pen-test in place — *the project tree is in the host's trust zone* — and the empirical narrowing about the surface around it made the trade no longer worth taking. The restricted-account recipe is documented in primitive form by Microsoft Win32 (`CreateRestrictedToken`, `JOBOBJECT_SECURITY_LIMIT_INFORMATION`, `ActiveProcessLimit=1`, mandatory-integrity-level Low/Untrusted) and by the Chromium production reference, but no clear public answer establishes an end-to-end vetted recipe for "least-privilege account for the full Flutter toolchain" — the configuration is ops-side knowledge not published as a recipe (web research [4][5][7][11]). Additionally, the speed problem the bridge was meant to solve still requires `flutter analyze` to read every project file *somewhere* — and reading them through DrvFs / `\\wsl$\` on a restricted-user Windows process re-encounters the same 9P-frontier latencies that drove the original problem. The option also retains the V7 attack vector class (LLM modifies the watcher script in the repo, waits for the user to restart it after reviewing a diff that long-line / encoding / piggyback tricks could obscure).

### Option B — WSL + Mutagen + bridge

This option moved the project source-of-truth to WSL ext4 (solving the speed problem at its root) and kept the bridge for the narrow case of Windows-target operations. The container would do all daily work locally; the bridge would exist only to dispatch `flutter build windows`, the Windows desktop smoke test, and Windows-target integration tests to the Windows host on demand.

This option was rejected because the trimmed bridge still has the V1/V2 attack surface. `flutter build windows` interprets `windows/CMakeLists.txt` (V4) and `pubspec.yaml` (V5 — pub fetches happen on the Windows host); `smoke_test_windows.ps1` is a container-writable file the bridge would execute with `-ExecutionPolicy Bypass` (V2); Windows-target integration tests run `*_test.dart` files the container can author (V1). Reducing the whitelist from six entries to three does not reduce the category. Once the option is "no bridge in the daily loop", the marginal cost of "no bridge for release-time activities either" is small — the developer is at the keyboard for releases regardless — and the win is the complete elimination of a code path that would otherwise need pen-testing on every change to the project's tooling.

### Option C — WSL + on-demand mirror + bridge

This option avoided a continuous sync daemon: instead of Mutagen running at all times, the developer (or a setup script) would invoke a one-shot mirror operation (robocopy `/MIR`, rsync, or equivalent) before any Windows-target operation, then run the operation against the mirror, then either discard or retain the mirror until next time.

This option was rejected for two reasons. First, it still keeps a bridge — and the same V1–V6 vectors apply at the moment the bridge is online. Second, the on-demand-mirror operations have their own friction: robocopy `/MIR` from `\\wsl$\` to NTFS doesn't represent a cross-file consistent snapshot (per-file retries, no quiesce); rsync from inside WSL to `/mnt/c/…` is empirically slow over the 9P boundary (multi-minute runs documented in microsoft/WSL #5299) and loses mode bits; mode bits and Linux symlinks don't survive the trip in either tool (web research [23][24][25][26]). A continuous Mutagen session avoids both classes of pain (its wsl-bridge transport uses `wsl.exe` shell rather than the `\\wsl$\` 9P path, and propagation is incremental and near-realtime per [27][28]) — and Option E removes the bridge entirely, which closes V1–V6 once and for all.

### Option D — WSL + direct `\\wsl$\…` access from Windows tooling

This option placed the project on WSL ext4 and let Windows-side tooling (`flutter build windows`, MSBuild, CMake) operate directly against the `\\wsl$\<distro>\…` UNC path that the WSL host service exposes. No mirror, no sync daemon. Conceptually the cleanest answer: one source-of-truth, two access paths.

This option was rejected because the Windows toolchain is broken at multiple independent layers when its working directory is a `\\wsl$\…` UNC path. Empirically documented failures (web research [9–18]): CMD.EXE rejects UNC working directories ("UNC paths are not supported. Defaulting to the Windows directory.") which affects every tool that shells out via `cmd /c`; MSBuild 17 lower-cases UNC components when processing CMake-generated `.vcxproj` files, producing `MSB8064` / `MSB8065` warnings on every build; Flutter's path canonicalization in Dart strips leading backslashes from UNC paths, producing malformed `UNC\server\share\…` that fails as a build input (flutter/flutter #43594, dart-lang/sdk #52309); `flutter pub get` inherits the same `cmd /c` shim failure that npm and yarn document on UNC roots (npm/cli #6280, yarnpkg/yarn #8715); PowerShell 7 treats FQDN-style UNCs as Internet for execution-policy purposes, requiring `-ExecutionPolicy Bypass` to run scripts off UNC (Microsoft Learn `about_Execution_Policies`); the underlying 9P client itself is throughput-capped to roughly an order of magnitude slower than native ext4 (microsoft/WSL #9125), with metadata-heavy operations measured ~70× slower than alternatives (Allen Kuo benchmark). The toolchain bugs are the proximate blockers; the 9P throughput cap is the structural one. Microsoft does not document `\\wsl$\…` as a supported Visual Studio source location — the supported model is "sources on NTFS, build on NTFS" with `rsync` copying into WSL for Linux-target work, which is the inverse of what this project needs.

### Option E — Delete the bridge entirely (the chosen option)

This option deletes the bridge, places source-of-truth on WSL ext4, runs Mutagen as the continuous mirror for manual Windows operations, and adopts the Flutter Linux desktop target with `xvfb` as the LLM-autonomous integration-test path. The container does every per-change quality gate, every widget golden render, and every Linux-desktop integration test directly against ext4 with no host-side routing. Windows-target operations are manual, against the Mutagen NTFS mirror, on a Windows session the developer opens deliberately.

This option was chosen for four reasons. First, it eliminates the entire V1–V6 vector class by construction — there is no host-execution path of any kind for an LLM to exploit, online or offline. The container's sandbox claim becomes structurally true rather than conditionally true. Second, it removes the speed problem at its root: `flutter analyze` against ext4 inside the container completes in roughly one minute (target codified in REQ-PROC-054 AC-04), which is ~10× the previous DrvFs baseline and well inside the per-change feedback loop. Third, it keeps the operational footprint small — one config file (`mutagen.yml`), one Task Scheduler entry, no watcher to harden — which matches the persona's "simplicity is a survival strategy for one-person maintenance over years" value. Fourth, Windows-target validation is preserved as a release-cadence activity (REQ-PROC-053 *verification_strategy* defines the schedule), not lost: the Windows binary still gets built and smoke-tested before each release, just by the developer's hand rather than the container's. Windows Sandbox was considered as an alternative host-side runner that would have given Option A/B/C a clean isolation layer without the restricted-account complexity, and was rejected because the analyzer's `.dartServer` cache (which reaches ~1 GB on a real project per dart-lang/sdk #29648 [9]) lives inside the sandbox VM and rebuilds cold on every launch, eliminating the speed advantage that motivated the bridge in the first place; Windows Sandbox is also single-instance with no documented IPC primitive for "send another command to the already-running sandbox" (Microsoft Learn [1][2]).

## Consequences

### Positive

**Speed.** The daily-development loop runs at native ext4 speed inside the container. `flutter analyze` over the full source tree completes in under two minutes (AC-04 contract); `dart fix --apply` completes in under one minute. The per-change back-pressure gates defined by REQ-PROC-046, REQ-PROC-002, REQ-PROC-051, and REQ-PROC-052 fit comfortably into the LLM feedback loop instead of dominating it.

**Security.** No container-to-host execution path of any kind exists. A fully-compromised LLM in the container can destroy the container, can rewrite anything in the working tree (and the next commit's diff would surface it), and cannot directly execute code on the Windows host. The LLM-sandbox claim from the project's original threat model holds without conditions.

**Simplicity.** Operational footprint is one config file (`mutagen.yml`), one daemon (the Mutagen Windows daemon, managed by Task Scheduler), and one optional PowerShell function (`Build-Win` for the pre-build flush). No watcher script to harden, no whitelist to maintain, no diff to review before restarting. The persona's *"the codebase must survive periods where the creator has no time to touch it"* value is materially supported.

**Disaster recovery.** Three independent storage layers — GitHub remote, pre-push `git bundle --all` into a cloud-synced backup folder, Mutagen NTFS mirror on a filesystem independent of the WSL `ext4.vhdx` — make loss of any single layer non-fatal (REQ-PROC-054 AC-09).

### Negative / accepted residual

**Parent-folder `.devcontainer/devcontainer.json` and parent `.vscode/tasks.json` remain LLM-writable.** The parent folder lives one directory up from the `flutter_app/` repo — outside the git tree — and is required at that level so that sibling git worktrees can share one container. The container mounts the parent folder, so the LLM can edit those two files. This is the necessary consequence of supporting the git-worktree workflow; the mitigation is VS Code Workspace Trust discipline plus occasional human inspection of those two files, and the documented refusal to add `runOn: folderOpen` host-side auto-launch tasks to any `.vscode/tasks.json` (which would re-introduce the V7 attack class from the pen-test).

**Windows builds and the Windows desktop smoke test are manual.** The LLM cannot autonomously verify that a change builds and runs correctly against the Windows-desktop target. Pre-release manual Windows smoke validation is part of the release procedure (codified by REQ-PROC-053 *verification_strategy*). The accepted trade is "Windows-target validation moves from per-change to per-release" — consistent with the persona's preference for longevity over per-task velocity.

**WSL `ext4.vhdx` is a single virtual-disk file.** Corruption of that file (rare but not impossible — hard reboot during write, host filesystem error, WSL bug) loses everything inside the distro that isn't pushed to remote or mirrored. The three-layer backup strategy (AC-09) makes this not catastrophic; a periodic `wsl --export` of the entire distro is an optional fourth layer available to the developer at their discretion.

**Linux-rendered widget goldens are not byte-identical to Windows-rendered or macOS-rendered goldens.** Font metrics and anti-aliasing differ across platforms. The committed goldens are Linux-platform truth (the only platform on which the LLM-autonomous test loop runs); a developer working on a non-Linux configuration regenerates goldens on the supported configuration before committing. Codified by REQ-PROC-054 AC-08 and the upcoming REQ-PROC-053.

**No automated Windows-target integration tests in the daily loop.** Linux-target integration tests (against the Flutter Linux desktop target) catch fewer platform-specific bugs than Windows-target tests would. The trade is mitigated by the pre-release Windows manual smoke check; the residual gap (Windows-platform-channel-specific bugs that don't surface on Linux) is named explicitly so the verification strategy can plan around it.

**Camera platform-channel code is not automatable on any platform.** The camera integration test requires a human holding a QR code in front of the camera; this is structurally outside the scope of any automated integration test, regardless of the bridge decision. Not a regression from the previous configuration — naming it here for completeness.

## Evidence

- **Pen-test report** — `requirements_tasks/process/AI_rules/dev_infrastructure/dev_environment/tasks/2026-05-19_explore_pentest-host-bridge-safety (completed)/plans_and_protocols/2026-05-19_01_pentest_report.md`. Establishes the V1–V16 vector analysis with concrete proof-of-concept paths and the verdict that the bridge is not a security boundary while the watcher is online. V1 (`flutter test` host-side code execution via container-planted `*_test.dart`) and V2 (`smoke_test` host-side PowerShell execution via container-overwritten `smoke_test_windows.ps1`) are the two Critical findings that alone establish the bridge's dissolution of the container sandbox. V3–V6 are redundant paths via `dart fix` / `flutter analyze` analyzer-plugin execution, CMake `execute_process` at `flutter build windows` configure time, pub dependency execution via `flutter pub get`, and persistence-of-compromise via `dart fix --apply` writing analyzer-plugin "fixes" into `lib/`. V7 (watcher restart deception) defeats the stated "review-before-restart" control. The pen-test's *Assumptions under which the bridge is safe* section enumerates six conditions whose conjunction must hold for the bridge to be a security boundary, and notes that at least condition 4 (Windows account running the watcher has limited privileges, no SSH keys / browser data / etc.) is almost certainly violated on any real developer machine.

The authoritative spec from which REQ-PROC-054 is derived; codifies the five-option evaluation and the chosen architecture.

Mutagen is documented as escaping the 9P frontier via its wsl-bridge transport using `wsl.exe` shell rather than `\\wsl$\` ([27][28]).

- **REQ-PROC-054 — `requirements.md`** — the contract codified from these inputs. AC-03 names this ADR as the authoritative record of the bridge-deletion decision.

## Re-evaluation triggers

This decision is the right one for the project's current shape. The conditions under which reopening it would be warranted are narrow and specific:

- **A future Microsoft release of WSL2 ships a low-latency 9P client that benchmarks within 2× of native NTFS for the many-small-files fan-out pattern produced by `flutter analyze`.** Under this condition, Option D becomes viable: Windows tooling could operate directly against `\\wsl$\…` without a sync mirror, *if* the documented toolchain bugs (CMD.EXE UNC rejection, MSBuild UNC lower-casing, Flutter UNC backslash stripping, pub cmd-shim failure) are also resolved. The bridge-less architecture could then be paired with automated Windows-target tests via `\\wsl$\…`, eliminating the manual-build trade. Both halves of the change must land — 9P speed alone is insufficient if the toolchain still mishandles UNC paths.

- **The Flutter team ships a documented, supported "build Flutter for Windows from a non-Windows toolchain" path.** Today the Windows target requires a Windows host. If a future Flutter release supports cross-compilation to Windows from Linux (analogous to the current Android cross-compilation from Linux), the manual-Windows-build trade dissolves: the LLM-autonomous loop could produce a Windows binary directly inside the container. The bridge stays deleted (this ADR's primary claim is unaffected); the architecture would then add Windows-target integration tests to the in-container test set.

- **A published, audited, end-to-end recipe for "least-privilege Windows account running the full Flutter toolchain" emerges from a reputable source.** Under this condition, Option A's host-side restricted-account model becomes a credible defensive layer if the project ever needs to reintroduce host-side execution (for example to drive an Android emulator from an LLM session). The ADR's primary claim (no bridge in the daily loop) is unaffected; the conditions under which a *narrower* extension architecture — for example the deferred Android-emulator narrow watcher named in REQ-PROC-054 AC-07 — could be implemented would be materially better-understood.

- **The pen-test's V8 (symlink / path-traversal in project tree) is empirically validated as exploitable** — if a future container configuration causes WSL→NTFS-side symlink-following by PowerShell-spawned Flutter tooling to read files outside the project tree. The ADR is unaffected (no bridge means no host-side tool to follow such a symlink), but the *parent-folder LLM-writability* residual risk (REQ-PROC-054 AC-11(a)) would warrant reconsideration: the parent `.devcontainer/` becomes a higher-value target if cross-tree reads become possible.

- **A test framework appears that runs Windows-target Flutter integration tests against a remote Windows runner without exposing a host-execution surface to the container** — for example a CI-style worker pool reachable over a narrowly-typed API rather than a shell. This is the BuildKit / Buildx "remote driver" pattern from the prior-art survey. Under this condition, Windows-target integration tests could rejoin the LLM-autonomous loop without re-introducing the V1–V6 attack class. The ADR's primary claim remains correct; the test-cadence section of REQ-PROC-053 *verification_strategy* would gain a new automated tier.

None of these triggers is currently anticipated. The decision stands.
