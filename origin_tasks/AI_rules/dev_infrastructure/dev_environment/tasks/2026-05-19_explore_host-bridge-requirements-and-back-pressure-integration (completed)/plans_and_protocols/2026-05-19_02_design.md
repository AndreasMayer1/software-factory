## 1. Concept

### 1.1 What this thing is, fundamentally

A **broker that lets a slow / sandboxed environment ask a faster, less-
sandboxed environment to run a small, pre-declared set of expensive
commands on its behalf, and stream the result back.**

The reason it exists is empirical, not architectural. In the current
setup:

- The Flutter project lives on an NTFS folder, accessed from a Debian
  devcontainer via WSL DrvFs.
- Tools that traverse the project tree (`flutter analyze`,
  `dart fix --apply`, cold `flutter pub get`, `flutter build --analyze-size`)
  are I/O-bound on the FS bridge — 10–17 min in the container vs.
  ~1 min directly on the Windows host.
- Tools that produce Windows binaries (`flutter build windows`,
  `smoke_test`) **cannot run** in the container at all — they need the
  Windows toolchain.

So the broker has two distinct reasons to route a command:

- **Speed**: when the WSL→NTFS file IO would dominate; running on the
  host's native filesystem is ~10× faster.
- **Necessity**: when the command physically cannot run in the
  container (Windows toolchain).

Both reasons converge on the same mechanism: *execute on the host that
owns the filesystem*.

### 1.2 What it explicitly does NOT guarantee

The pen-test report (TASK-PROC-054-01) established the following, which
becomes part of the contract:

- **The broker is not a security boundary.** Every whitelisted tool
  interprets container-controlled project files. A compromised LLM
  inside the container has, in practice, the same privileges as the
  Windows user account running the watcher *while the watcher is
  online*.
- **It is a convenience automation layer over the host.** Its presence
  defeats the devcontainer sandbox — that is its intended job.
- **Sandboxing is the operator's responsibility**, not the broker's.
  The broker delegates the trust boundary to one of the architectural
  options in §3.

This honesty about what the broker is *not* is itself a deliverable.
The previous design's stated security model ("the Linux side can only
name a command_id, it cannot inject shell") was technically accurate
but obscured the practical reality. The new requirement codifies the
reality.

### 1.3 What it MUST guarantee (the new contract)

1. **Optionality**: every workflow that uses the broker must also
   produce a correct result without it — possibly slower. Mac, native
   Linux, native Windows, and devcontainer-without-watcher setups
   must all work end-to-end.
2. **Idempotency of routing**: a script that calls a slow tool must
   not need to know whether the broker exists. The dispatch layer
   decides; the script asks for the tool by ID.
3. **Hard failure on policy violation**: if the broker is invoked
   with a command not on the whitelist, the request is rejected
   visibly. Silent fallback is *not* the model (research §4: prior
   art uniformly chooses explicit-declaration + hard-error).
4. **Whitelist as a rule, not an enumeration**: any future addition
   must satisfy a stated policy (§5.2). The whitelist is documented
   alongside the rule that generated it.

## 2. Naming decision

### 2.1 What is wrong with "win-command-bridge"

It centers Windows. Two reasons that's the wrong frame:

- Windows is a *host operating system*, not an architectural role.
  The same broker pattern could route to a macOS host, a native Linux
  host, or a remote VM. The name should describe the role, not the
  current incarnation.
- The two reasons commands route through it are "host owns the
  filesystem" (speed) and "host owns the toolchain" (necessity) —
  both center *the host*, not *Windows*.

### 2.2 Candidates

| Candidate | Pros | Cons |
|---|---|---|
| **host bridge** | Short, neutral, mirrors `devcontainer-bridge` (dbr) prior art. | Slightly vague — what kind of bridge? |
| **host-execution bridge** | Specific. Says exactly what it does. | Wordy. |
| **host command broker** | "Broker" is the Chromium / BuildKit term; signals brokering / policy-gated dispatch. | "Broker" is less recognisable to non-systems folks. |
| **host runner** | Short. Echoes "GitHub Actions runner" mental model. | "Runner" implies it runs jobs autonomously; the broker is reactive. |
| **host worker** | BuildKit-style naming. | Same ambiguity as runner. |
| **host-exec broker** | Hybrid: "host-exec" + "broker". | Hyphen soup. |

### 2.3 Recommendation

**`host-execution bridge`** in long form, **`host bridge`** in short form.

Reasoning:
- "Bridge" is the closest prior-art match (dbr — devcontainer-bridge —
  is the only OSS project doing roughly this pattern).
- "Host-execution" makes the role unambiguous and survives translation
  to a future macOS / native-Linux variant.
- "Broker" would be more semantically accurate (Chromium-style policy-
  gated brokering is exactly what this is) but is less recognisable;
  bridge is fine.

## 3. Trust-boundary architecture

### 3.1 Evaluation framework

For each candidate evaluate against:

- **Threat coverage**: which of V1–V6 from the pen-test does it close
  vs. accept?
- **Setup cost**: one-time admin burden, on each fresh clone, per
  contributor.
- **Runtime cost**: cold-start latency, cache behaviour, ergonomics
  hit during normal development.
- **Interaction with dispatch (§4)**: does this architecture
  presuppose or rule out Approach A or B?
- **Residual risk**: what remains exploitable after this mitigation.

### 3.2 A1 — Dedicated restricted Windows user account

**Approach**: create a local Windows user (e.g. `host-bridge-runner`)
with:

- NTFS read+execute on the project folder, read+write on a dedicated
  cache folder (for `%LOCALAPPDATA%\.dartServer`, `%LOCALAPPDATA%\Pub\Cache`).
- No SeDebugPrivilege, no admin token, mandatory integrity level Low.
- AppLocker policy (scoped per-user) whitelisting only `flutter.bat`,
  `dart.exe`, `powershell.exe` for the smoke test, plus the binaries
  they invoke transitively.
- Windows Firewall outbound block by default; explicit allow only for
  `pub.dev` host and ports (so `flutter pub get` works; arbitrary
  egress doesn't).
- The watcher process runs under this user via `runas` /
  `schtasks /RU` at logon; the developer's normal account never runs
  the watcher.

**Threat coverage (V1–V6)**:
- V1 (flutter_test runs container Dart): partially closed. Code runs
  under the restricted account; no user-profile access, no
  unrestricted network. Reachable damage = anything writable by the
  restricted account, which is the project tree itself + the
  dedicated cache folder. **Blast radius shrinks substantially**,
  but the attacker can still rewrite project source files (V6).
- V2 (smoke_test): same as V1.
- V3 (analyzer plugins): same. Analyzer plugin gets restricted-account
  privileges, not developer-account privileges.
- V4 (CMake execute_process): same — `flutter build windows` runs
  under restricted account.
- V5 (pub fetch network pivot): mostly closed by firewall outbound
  rule restricting to `pub.dev`. Attacker can still abuse pub's own
  protocol (e.g. fetch a malicious package), but cannot dial
  arbitrary URLs.
- V6 (dart fix mutates files persistently): NOT closed — `dart fix
  --apply` legitimately writes to `lib/`. Persistent backdoor in
  `lib/` is still in scope.

**Setup cost**:
- One-time admin: create user, configure AppLocker policy, configure
  outbound firewall, set up scheduled task / logon trigger for
  watcher. ~1–2 hours, requires admin.
- Per-clone: re-apply NTFS ACLs (Git stores no ACLs, per research
  §3); `icacls` post-clone step in an install script.
- Per-contributor: must replicate the local-user setup on each dev
  machine. Document this; provide a setup PowerShell script.

**Runtime cost**:
- Restricted account needs its own `LOCALAPPDATA` — analyzer driver
  cache (~1 GB) + pub cache live there. Warm-cache behaviour is fine
  after first run; **first run after account creation pays the full
  cache build**.
- The watcher's PowerShell session under the restricted account does
  not interfere with the developer's account.
- IDE integration: VS Code's normal Flutter / Dart extension still
  runs under the developer's account against the *same* project
  tree; only the bridge-routed commands cross into the restricted
  account.

**Interaction with dispatch**:
- Compatible with Approach A (facade). The facade dispatches to the
  watcher, which already runs under the restricted account; the
  dispatcher doesn't change.
- Compatible with Approach B (read-only scripts) as defence-in-depth
  but doesn't require it — the restricted account already can't
  modify scripts owned by the developer's account (NTFS ACLs).

**Residual risk after A1**:
- Persistent backdoor in `lib/` via `dart fix --apply` (V6).
- Project-tree pollution that propagates on the next `git push` (any
  whitelisted tool writes to project files: dart fix to lib/,
  flutter test to .dart_tool/, etc.).
- Supply-chain attack via legitimate pub.dev packages (V5 partial).

**No published end-to-end recipe** exists for "least-privilege Windows
account for Flutter tooling" (research §2). We would be the first to
document it. Implication: implementation requires careful empirical
work in Phase 5 — expect rough edges.

### 3.3 A2 — Per-command Windows Sandbox

**Approach**: each whitelisted command spawns a fresh
`WindowsSandbox.exe` instance with the project folder mapped, runs
the command via `LogonCommand`, captures output, closes the sandbox.

**Threat coverage**: V1–V6 closed cleanly at the OS level. Sandbox is
ephemeral, no persistence outside the mapped folder.

**Setup cost**:
- Pro/Education/Enterprise license required (research §1). **Not
  available on Windows Home.** This is a hard blocker for any
  contributor on Home.
- Enable Windows Sandbox feature (admin).
- Author `.wsb` configuration files mapping the project folder and
  the cache folders.

**Runtime cost** — this is where A2 falls apart:
- No multi-instance / no queue / no IPC. Each invocation is a fresh
  VM (research §1).
- "Cold start: a few seconds" per Microsoft, no published
  reproducible benchmark.
- **Analyzer driver cache (`%LOCALAPPDATA%\.dartServer`, ~1 GB on real
  projects) lives inside the sandbox VM and is destroyed on close**
  (research §1, [9]). Mapping it into the project tree would persist
  it but pollutes the repo with binary cache.
- **Pub cache (`%LOCALAPPDATA%\Pub\Cache`) lives inside the sandbox
  VM and is destroyed on close.** Redirect via `PUB_CACHE` env var to
  a mapped folder is possible but requires custom `.wsb` config.
- Net: every `flutter analyze` would re-download pub packages and
  rebuild the analyzer driver cache. **The speedup the bridge exists
  for in the first place would be lost.** The 10–17 min in-container
  runtime would become "1 min execute + 10 min cache rebuild" = same
  order of magnitude as no bridge.

**Interaction with dispatch**: Compatible with Approach A. Approach
B is moot — scripts in the mapped folder are read-write in the
sandbox.

**Residual risk**: minimal in security terms; mostly absorbed by
the ephemeral VM.

**Verdict**: A2 is the strongest sandboxing answer in pure security
terms, but the cold-cache penalty is so severe it negates the bridge's
purpose. The user pays the security tax twice — once at setup, once
on every command. **Rejected on pragmatic grounds**, not security
grounds. Could be reconsidered if cache-redirection via `.wsb` is
empirically proven to work cleanly, but that's its own multi-day
sub-project.

### 3.4 A3 — Persistent lightweight Windows VM

**Approach**: long-lived Hyper-V VM or Windows-on-Hyper-V; watcher
runs inside it; cold-start cost amortized; caches persist.

**Threat coverage**: V1–V6 closed at VM boundary.

**Setup cost**:
- Hyper-V license & enable (admin).
- Provision a Windows VM (multi-GB disk, configure shared folders,
  install Flutter SDK + Dart SDK inside the VM).
- Configure networking, VM lifecycle.
- ~1 day to set up, includes mounting the project tree from host into
  VM (yet another bind-mount layer with its own performance
  characteristics).

**Runtime cost**:
- VM constantly running (memory + CPU baseline).
- File-IO between host and VM has its own slowness penalty (likely
  worse than WSL→NTFS, depending on share protocol).

**Verdict**: Heavier than A1 with marginal additional security gain.
**Rejected**: A1 buys ~90% of A3's security at a fraction of the
setup cost. A3 only makes sense if the developer already has a
hardened VM infrastructure they want to slot into.

### 3.5 A4 — Accept the trade openly (no architectural mitigation)

**Approach**: keep today's design. Document explicitly in the new
`requirements.md`: "use of the broker implies the project tree is in
the host's trust zone". Apply cheap-wins (§6) as defence-in-depth.

**Threat coverage**: V1–V6 NOT closed. They are documented as
accepted residual risk.

**Setup cost**: zero beyond status quo.

**Runtime cost**: zero beyond status quo.

**Honest implication**: while the watcher is online, the
devcontainer's stated security purpose ("worst case the LLM destroys
the container") doesn't hold. The user runs an LLM with effectively
no sandbox.

**Verdict**: Acceptable only as an interim posture. The user's
stated motivation for using a devcontainer (LLM-injection defense)
is fundamentally inconsistent with A4. **Rejected as a final answer.**
Worth keeping as a *fallback option* the user can choose during
transition, with explicit documentation that the LLM sandbox is
nominal-only when the watcher is online.

### 3.6 A5 — Hybrid: A1 for slow tools + drop unnecessary commands

**Approach**:
- Architectural mitigation = A1 (restricted Windows user).
- Whitelist surgery:
  - `flutter_analyze`, `dart_fix`, `flutter_pub_get`: kept; route via
    restricted-account watcher.
  - `flutter_build_windows`: kept (Windows toolchain necessity); route
    via restricted-account watcher.
  - `flutter_test`: **removed from broker whitelist**. Tests run in
    the container (already the default for `verify-quality`'s G3 fast
    path); the bridge variant was unused. Removing it kills V1.
  - `smoke_test`: **removed from broker whitelist**. The user invokes
    it manually when needed (it's an episodic release-cadence
    command). Removing it kills V2.

This is the user's "merge of A1 and surgical whitelist trim". It's
the recommended option.

**Threat coverage**:
- V1 (flutter_test): closed by removal.
- V2 (smoke_test): closed by removal.
- V3, V4, V5, V6: same A1 reduction (blast-radius shrinks; not
  closed; documented).

**Setup cost**: same as A1.

**Runtime cost**:
- Loss of bridge-accelerated tests: in-container test runtime stays
  the slow baseline.
- Loss of bridge-launched smoke_test: user runs the smoke script
  manually on Windows.

**Interaction with dispatch**: works cleanly with Approach A facade
(see §4); the facade only sees the trimmed whitelist.

**Residual risk**:
- V6 persistent-backdoor via `dart fix --apply` to `lib/`: still in
  scope.
- Supply-chain via pub.dev packages: partial.
- Project-tree pollution: in scope.
- All accepted explicitly in requirements.md and visible to the
  user.

**Verdict**: **Recommended.** Best balance of security gain vs.
setup cost vs. retained ergonomics.

### 3.7 Architecture comparison summary

| | V1 | V2 | V3 | V4 | V5 | V6 | Setup | Runtime | Verdict |
|---|---|---|---|---|---|---|---|---|---|
| A1  | partial | partial | partial | partial | partial | open | ~1–2 h, admin once | analyzer cache cold first run only | viable |
| A2  | closed | closed | closed | closed | closed | closed | Pro/Edu license + Sandbox config | **cold cache every run** | rejected |

## 4. Dispatch mechanism

### 4.1 The dispatch problem

Today the only consumer that uses the bridge is `verify-quality`'s
Step 3.2, which calls `win_bridge.sh flutter_analyze` directly. Three
other scripts in `scripts/quality/` and `scripts/release/` invoke
`flutter` directly via `subprocess.run` or `&` and would benefit from
routing through the bridge when present:

- `check_critical_path_coverage.py` (`flutter test --coverage`)
- `check_test_determinism.sh` (`flutter test` ×10)
- `check_bundle_size.py` (`flutter build apk`, `flutter build appbundle`)

If we accept A5's whitelist trim, `flutter test` drops off the
candidate list (no bridge variant). That leaves `check_bundle_size.py`
(builds) and any future `flutter analyze` / `dart fix` / `pub get`
script as the dispatch consumers.

We need a way for these scripts to call a slow tool transparently:
*the script asks for the tool by name; the dispatcher decides whether
to route via the broker, run locally, or refuse.*

### 4.2 Approach A — Container-side facade dispatcher

**Shape**: one `scripts/host-bridge/run_tool.sh <tool_id> [-- args]` (and
a Python wrapper for Python consumers). Scripts call this instead of
the tool directly.

```bash
# Old (in check_critical_path_coverage.py):
subprocess.run(["flutter", "test", "--coverage"])

# New:
subprocess.run([
    "scripts/host-bridge/run_tool.sh",
    "flutter_test_coverage",  # or "flutter_test", "flutter_build_apk", etc.
])
```

The dispatcher reads a config file (§5.4) and decides:

1. Is the broker available right now (`probe` returns online)?
2. Is the tool routable (on the broker whitelist + config allows
   routing in this setup)?
3. If both yes → route via broker, await result.
4. If either no → run locally (the underlying shell command), inherit
   stdout/stderr, exit with the tool's exit code.

If the config says "this setup requires the broker for tool X" and
the broker is offline → **hard error**, do not silently fall back
(prior art §4: explicit declaration, hard error on absence).

**Pros**:
- Single point of policy. New routing rules go in the dispatcher,
  not in every consumer.
- Decouples consumers from the broker. A Mac developer's script
  trace is unchanged: dispatcher detects no broker, runs locally.
- Matches established prior art (dbr, BuildKit worker).
- Read-only-script concerns (Approach B) are moot — the
  dispatcher itself is just code that runs in the container.

**Cons**:
- Requires modifying every consumer that hard-codes `flutter`/`dart`
  to call through the dispatcher. Scope: 3 scripts in `scripts/`
  (above) + `verify-quality` skill + any new consumer. Manageable.
- The dispatcher itself becomes part of the trust surface: a
  compromised container can rewrite the dispatcher to bypass the
  broker. **But this changes nothing**: the broker's whitelist
  already enforces what may run on the host; the dispatcher only
  governs container-side behavior.

**Security analysis**:
- Approach A does NOT close any pen-test vector — it's an
  *ergonomic* layer, not a security layer. Trust-boundary work
  stays in §3.
- The dispatcher is container-writable code. A compromised LLM
  could bypass it by calling `win_bridge.sh` directly. That's fine:
  the broker's whitelist + the §3 architectural mitigation are the
  defenses; the dispatcher is just routing convenience.

### 4.3 Approach B — Read-only scripts on container, executed on host

**Shape**: `scripts/` is mounted read-only in the devcontainer
(`mounts: source=...flutter_app/scripts,target=...,type=bind,readonly`);
scripts run on the Windows host via a broker-mediated invocation;
container can read but not write them; a separate "maintenance mode"
on the host lets the LLM modify the scripts via the broker, gated by
the user.

**Pros (if it works)**:
- Closes the V2 / V7 family of attacks (script-content tampering)
  for everything under `scripts/`.
- Doubles as a partial architectural mitigation (the LLM cannot
  modify the host-side script body between modification and
  execution).

**Cons (research §3)**:
- **Recursive readonly** requires Linux kernel ≥ 5.12 (modern WSL2
  is fine).
- **Devcontainer spec issue 511** is still open: the structured-
  object form is flaky; string form is the established workaround.
  Acceptable.
- **Windows NTFS ACLs do not survive `git clone`**. Git has no
  `core.ntfsACL` equivalent. So enforcing "scripts read-only to the
  watcher account" on the Windows side requires a post-clone
  `icacls` step. This is install-time burden, but it can be folded
  into the bridge installer (which the user already has to run once
  per machine).
- Scripts that are intended to execute on the host would have to be
  PowerShell (or have a PowerShell wrapper). Today most quality-
  gate scripts are Python/Bash, designed to run in the container.
  Rewriting them all is a substantial scope hit.
- The "maintenance mode on host that lets LLM edit scripts via
  broker" is a new attack surface that needs its own design and
  threat model. Recursive complexity.

**Verdict on B (as a standalone dispatch)**: too expensive. The
scripts that benefit most from the broker (the quality-gate scripts)
are *container-native* — they orchestrate analysis, test, coverage,
size measurement using container tools. Moving them to the host
means rewriting them in PowerShell or running them via WSL on the
host (which is the same WSL slowness we're escaping).

**Verdict on B as defense-in-depth**: a slimmed-down version is
worth doing in Phase 5: mount the `scripts/host-bridge/` folder
itself as `readonly` in the devcontainer, so the broker code and
the dispatcher cannot be tampered with from the container. This is
narrow, mechanically simple, and closes the most concerning
script-tampering vector (someone overwriting `host_bridge.sh` itself
to send bogus command IDs that bypass validation isn't a vector
today — the watcher independently re-validates — but defense in
depth is cheap). See §6 cheap-wins.

### 4.4 Recommendation: A + slim B

**Approach A is the dispatch mechanism.** Approach B is reduced to
a defense-in-depth measure: `scripts/host-bridge/` mounted read-only
in the devcontainer (one line in `devcontainer.json`).

The rest of `scripts/` stays writable in the container — it has to,
because quality-gate scripts evolve frequently and the LLM
legitimately edits them as part of normal development. Closing the
attack surface there is the §3 architecture's job (restricted user
account on the watcher side), not the dispatcher's.

### 4.5 Dispatch design — concrete shape

**File**: `scripts/host-bridge/dispatch.sh` (Bash; primary entry).
**File**: `scripts/host-bridge/dispatch.py` (Python; thin
`subprocess.run` wrapper for Python consumers).

**Config**: `scripts/host-bridge/dispatch.config.yaml` (repo-tracked
defaults) + `scripts/host-bridge/dispatch.local.yaml` (gitignored
local override, optional). YAML chosen to match the project's
existing config style (analysis_options.yaml, task_ordering_rules.yaml).

**Logical contract** (`run_tool TOOL_ID [args...]`):

```
1. Look up TOOL_ID in dispatch.config.yaml's tool table.
   If absent → error "unknown tool", exit 2.

2. Determine routing decision:
   a. If config marks tool as "container-only" → run locally.
   b. If config marks tool as "host-required" → broker probe.
      If broker offline → hard error, exit 3.
      If broker online → route via broker.
   c. If config marks tool as "host-preferred":
      - broker probe → online → route via broker
      - broker probe → offline → run locally
      (This is the "fast on devcontainer-Windows, fall back to local
       on other setups" case — the only case where silent fallback
       is allowed, and it is opt-in per tool.)

3. Stream stdout/stderr; exit with tool's exit code.
```

**Tool table example** (proposed `dispatch.config.yaml`):

```yaml
tools:
  flutter_analyze:
    routing: host-required  # in-container too slow to be useful
    host_command_id: flutter_analyze
    local_command: [flutter, analyze]

  dart_fix:
    routing: host-required  # in-container too slow
    host_command_id: dart_fix
    local_command: [dart, fix, --apply]

  flutter_pub_get:
    routing: host-preferred  # speed advantage, works locally too
    host_command_id: flutter_pub_get
    local_command: [flutter, pub, get]

  flutter_build_windows:
    routing: host-required  # toolchain necessity
    host_command_id: flutter_build_windows
    local_command: null  # cannot run locally on non-Windows

  flutter_test_coverage:
    routing: container-only  # always runs locally per A5
    local_command: [flutter, test, --coverage]

  flutter_test:
    routing: container-only  # always runs locally per A5
    local_command: [flutter, test]

  flutter_build_apk:
    routing: container-only  # builds Linux/Android in container
    local_command: [flutter, build, apk, --analyze-size, --target-platform=android-arm64]

  # ... etc.
```

The presence of a tool in this table is the documented routing
contract. Adding a tool = a config edit, not a code edit. Adding a
tool to the broker whitelist = a separate edit to `host_bridge.sh`
+ `host_bridge_watcher.ps1`, gated by user review at watcher
restart.

**Config layering rule**:
- `dispatch.config.yaml` — committed defaults; the same for all
  contributors.
- `dispatch.local.yaml` — optional override; gitignored. Used by a
  developer to flip e.g. `flutter_analyze.routing` from
  `host-required` to `container-only` for testing in a setup where
  the broker is intentionally unavailable.
- Local override wins.

**Auto-detection**: see §5.5.

**Failure modes**:
- Broker probe fails → exit 3, stderr explains.
- Unknown tool → exit 2.
- Tool's `local_command` is null and routing falls back to local
  → exit 4 ("this tool cannot run locally; broker required").
- Tool's exit code passed through otherwise.

## 5. Policy

### 5.1 Optionality contract (the precise rule)

**Statement**: "Every quality-gate command and every quality-gate
script must produce a correct (possibly slower) result on a setup
where the broker is not present. The broker is an optional
accelerator, never a correctness dependency, *except* for two
declared cases:

- Commands that physically cannot run without the host toolchain
  (`flutter_build_windows`, `smoke_test` if it returns to the
  whitelist) — these are explicitly host-required and produce a
  hard error when invoked without a broker.
- Commands that are too slow to be useful without the broker
  (`flutter_analyze`, `dart_fix`) — these are explicitly host-
  required when running inside the devcontainer-on-Windows-host
  setup, and produce a hard error if the broker is offline.

In every other setup (Mac, native Linux, native Windows), every
command runs locally. Quality gates and back-pressure must work end
to end."

The optionality contract is **per-tool**, governed by the dispatch
config's `routing:` field, not a global flag.

### 5.2 Whitelist policy (rule, not enumeration)

A command_id may enter the broker whitelist if **all** of the
following hold:

1. It is a tool the project routinely uses for development or
   release work.
2. Either (a) its in-container runtime exceeds 1 minute and it is
   I/O-bound on the project tree (the "slow" threshold, §5.3); or
   (b) it physically requires the Windows toolchain.
3. It does not read or write credentials, SSH keys, browser
   session data, or other user-profile assets outside the
   project tree under normal operation.
4. It has been threat-modeled against the V1–V6 pen-test pattern.
   Specifically: if it interprets project files, the §3
   architectural mitigation (restricted account) is documented as
   the defense, and the residual risk is recorded in the
   requirements doc.
5. A reviewer (the user, on watcher-restart review) has explicitly
   approved its addition.

Forbidden permanently:

- `git` (any subcommand) — hooks make this an arbitrary code-
  execution surface.
- General-purpose shells (`bash`, `powershell`, `cmd`, `pwsh`) with
  user-supplied script paths or scripts the container can edit
  with no integrity check.
- Network-fetch commands not scoped to a fixed-URL allowlist
  (`curl`, `wget`, `Invoke-WebRequest`, raw `pub get` to a
  configurable host).
- Anything that consumes user input from stdin in a way the
  container can pre-supply.

### 5.3 "Slow" threshold

**Value**: 1 minute of in-container runtime, on a representative
project tree size, AND the cause is I/O fan-out over project
files (not pure CPU work).

**Use**: this is an **advisory rule for whitelist admission**, not a
runtime decision rule. The dispatcher does not measure-and-route at
call time. Tools are categorised once during whitelist design and
routed per their `dispatch.config.yaml` entry.

Rationale: a runtime measure-and-route adds complexity, requires a
test-run baseline per setup, and creates a new attack vector
(container manipulates apparent timings to flip the routing). Static
classification is simpler and more honest.

### 5.4 Configuration location

`dispatch.config.yaml` — repo-tracked. Same for all contributors.

`dispatch.local.yaml` — gitignored. Per-machine override.

`.devcontainer/devcontainer.json` — already repo-tracked; carries
the `scripts/host-bridge/` read-only mount.

Bridge enablement is **explicit**: a contributor opts in to using
the broker by running the installer (which sets up the watcher's
restricted account, applies ACLs, configures the scheduled task)
and by starting the watcher. There is no auto-enable on container
boot.

### 5.5 Auto-detection

**Recommendation: NO auto-detection at the dispatcher level.**

Reasoning:

- The dispatcher already does "broker probe → online/offline" per
  call (§4.5 step 2). That IS auto-detection of the broker's
  presence, no further config needed.
- Auto-detecting "we're in a devcontainer on a Windows host" via
  `/proc/version`, `wslpath`, `/mnt/c` would add complexity without
  changing the dispatcher's behavior — the dispatcher already
  routes based on the probe result.
- Where auto-detection *could* matter is the **installer**: it could
  refuse to install on non-Windows hosts. That's a setup-script
  concern, not a runtime concern.
- The simpler model is the right model here: the broker is opt-in
  via installation; everything else is reactive to whether the
  watcher is running.

So: **auto-detection happens implicitly via the `probe` subcommand**,
and the dispatcher uses that signal. No additional environment
sniffing.

## 6. Cheap-wins re-evaluation

Per the pen-test report's "Cheap-wins" list (7 items), each evaluated
against the chosen architecture (A5 = A1 + whitelist trim) and the
chosen dispatch (A + slim B).

### 6.1 Remove `smoke_test` from whitelist

**Status: still needed; implemented as part of A5.**

Reason: A5 explicitly trims `smoke_test` from the whitelist.

### 6.2 Hash-pin the smoke-test script at watcher startup

**Status: redundant under A5.**

Reason: `smoke_test` is no longer on the whitelist. The script body
on the host can change all it wants; the broker never invokes it.
If the user later wants smoke-test automation, the dispatcher can
add a `host-required` rule for a manually-invoked path (not via the
broker watcher).

### 6.3 Resolve `flutter` / `dart` / `powershell` to absolute paths at watcher startup

**Status: still needed.**

Reason: A5 / A1 reduces blast radius but does not eliminate PATH
hijack. The restricted account's `$env:PATH` should still resolve
toolchain to known canonical absolute paths at watcher startup so
PATH manipulation at request time cannot redirect. Cheap to
implement (one block in `host_bridge_watcher.ps1` at startup).

### 6.4 Bound the request-file read size

**Status: still needed.**

Reason: pure defense-in-depth, decoupled from architecture. One-line
change in the watcher (`Get-Content -TotalCount` or pre-size check).
No downside.

### 6.5 Move the watcher script out of the repo

**Status: still needed, slightly modified.**

Reason: V7 (watcher restart deception) is *not* closed by A5 — the
restricted account doesn't help if a compromised container has
already pre-edited the watcher and waits for the user to restart.
Moving the watcher script to `~/host-bridge-watcher/` (Windows side,
outside the project mount) cuts this attack surface entirely.

The in-repo copy becomes the **reference** copy. The installer
copies it to `~/host-bridge-watcher/` on setup. A side-by-side diff
check on watcher restart compares running copy against repo
reference and refuses to start on mismatch (this folds in cheap-win
§6.6 below).

### 6.6 Side-by-side watcher diff against reference copy at startup

**Status: still needed; folds into 6.5.**

Reason: see §6.5. The installer + watcher's own boot-check enforces
this.

### 6.7 Host-only append-only audit log of accepted requests

**Status: still needed.**

Reason: provides after-the-fact visibility regardless of
architecture. Cheap (a few lines in the watcher to append to
`~/host-bridge-watcher/audit.log` on every accepted request).
Outside the project tree (the container cannot read or tamper with
it).

### 6.8 Summary

| # | Cheap-win | Status under A5 | Implementation effort |
|---|---|---|---|
| 6.1 | Remove smoke_test | needed, folds into A5 | trivial |
| 6.2 | Hash-pin smoke_test script | redundant | n/a |
| 6.3 | Absolute path resolution | needed | ~10 lines PS1 |
| 6.4 | Request-file size bound | needed | ~3 lines PS1 |
| 6.5 | Watcher out of repo + installer | needed | ~50 lines installer PS1 |
| 6.6 | Watcher reference-copy diff at startup | needed; folds into 6.5 | ~20 lines PS1 |
| 6.7 | Host-only audit log | needed | ~5 lines PS1 |

All non-redundant items implemented in Phase 5.

## 7. What this design buys us vs. accepts

### 7.1 Closed vectors (pen-test V-numbers)

- V1 (flutter_test → container Dart on host): closed by whitelist trim.
- V2 (smoke_test → container PowerShell on host): closed by whitelist trim.
- V13–V16 (shell injection, race conditions, etc.): already closed
  before this task; unchanged.

### 7.2 Reduced-blast-radius vectors

- V3 (analyzer plugin): runs under restricted account; no developer-
  profile reach; pub network constrained.
- V4 (CMake execute_process): same.
- V5 (pub network pivot): firewall-constrained.
- V6 (dart fix mutates lib/): still in scope; persistent backdoor
  remains a documented residual risk.

### 7.3 Newly closed by dispatcher + read-only `scripts/host-bridge/`

- Bridge-script tampering (host_bridge.sh, dispatch.sh) — closed by
  read-only mount.

### 7.4 Accepted residual risk

- V6 persistent backdoor via `dart fix --apply` to `lib/`. Mitigation
  is human-process (the user reviews dart-fix output before commit;
  CI catches diffs that look unrelated to the change). Documented in
  requirements.md.
- Supply-chain via legitimate pub.dev packages within the firewall
  allowlist. Mitigation is `pubspec.lock` review and
  `flutter pub get --offline` for non-update runs.
- Project-tree pollution that surfaces on the next git push. The
  developer's commit-review process is the defense.
- The user must trust the installer they run once per Windows
  machine.

## 11. What this design is HONEST about

Borrowed structure from the pen-test report — listing what's
uncertain because the user is going to act on this.

- The restricted-account setup (A1 / A5) has no published end-to-end
  recipe for Flutter. We're writing it. Expect Phase 5 rough edges.
- The dispatcher reduces friction for new consumers but doesn't
  *prevent* misuse — a compromised container can still call
  `host_bridge.sh` directly.
- V6 (dart fix persistent backdoor) is a known residual risk and is
  on the user, not the architecture.
- The optionality contract is "explicit per-tool", not "magic". A
  Mac developer must run `verify-quality` knowing it will use the
  local `flutter analyze` and take however long that takes; the
  dispatcher will not silently swap behavior.

If any of these surprises you, this is the moment to push back —
before we lock the requirements in Phase 4.
