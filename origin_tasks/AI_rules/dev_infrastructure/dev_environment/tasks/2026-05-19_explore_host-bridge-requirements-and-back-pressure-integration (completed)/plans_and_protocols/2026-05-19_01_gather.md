## 1. What the bridge consists of, today

`scripts/win-command-bridge/`:

- `win_bridge.sh` — Linux/devcontainer side. Subcommands `probe`,
  `wait-result`, or a `<command_id>`. Sends a JSON request file, waits
  for an ACK from the watcher, then returns. `wait-result` blocks on
  `win_bridge_result.json` and prints `output` + exits with `exit_code`.
  Client-side whitelist string mirrors the watcher's hashtable.
- `win_bridge_watcher.ps1` — Windows side. PowerShell loop. Polls
  `win_bridge_request.json` once per second. Refreshes
  `win_bridge_heartbeat.flag` every second (Linux uses mtime freshness
  < 10 s to decide online/offline). On request: validates
  `command_id` against `$CommandWhitelist` hashtable, writes ACK,
  deletes request file, runs the script block with cwd = project root,
  writes `win_bridge_result.json` with `exit_code`, `output`,
  `elapsed_s`. Hashtable lookup is exact-key (case-insensitive, no
  string interpolation).
- `win_bridge_heartbeat.flag` — file on disk, updated every second by
  the watcher.
- `tests/test_win_bridge.sh` — Bash test harness covering happy path,
  unknown-command, malformed-JSON, signal-file races, the
  `case-insensitive command_id` edge case, etc.

Whitelist (must match in both files):
`flutter_analyze`, `flutter_build_windows`, `flutter_test`,
`flutter_pub_get`, `dart_fix`, `smoke_test`.

What the bridge does **not** have today:
- No `requirements.md` anywhere under `requirements_tasks/process/AI_rules/dev_infrastructure/host_bridge/`. This task creates it.
- No dispatch layer. Every consumer hard-codes
  `scripts/win-command-bridge/win_bridge.sh <command_id>`.
- No auto-detection of "devcontainer-on-Windows-host". Choice is
  manual: the developer either runs the watcher or doesn't.
- No configuration file for "use bridge here, skip there".
- No restricted-account / sandbox / VM layer between the watcher and
  the Windows host (see §6 for the pen-test consequence).
- No audit log of accepted requests.
- No hash-pin or out-of-repo install of the watcher script.

## 4. Measured / documented runtimes

CLAUDE.md §7 "Windows command bridge" records these measured pain
points:

- `flutter analyze` in devcontainer: **10–17 min** — bridge is
  mandatory.
- `dart fix --apply` in devcontainer: **>10 min**, times out — bridge
  is mandatory.
- `flutter pub get` on cold `.dart_tool`: bridge preferred for speed,
  optional otherwise.
- `flutter test`: only routed when testing Windows-platform-specific
  behaviour; the in-container test runtime is the everyday baseline.
- `flutter build windows`: bridge is the only option (cannot build a
  Windows binary on Linux).

The watcher itself records `elapsed_s` in every result file but we
don't have aggregated bridge-side runtimes archived. For Phase 2 the
relevant input is: **the file-IO-heavy tools (`analyze`, `dart fix`,
heavy `pub get`) are 10× slower in WSL DrvFs than on the Windows
host. The CPU-heavy tools (`flutter test`, `flutter build`) are not
necessarily slower — those are bridge candidates only when they need
the Windows toolchain.**

This validates the user's >1 minute "slow" working threshold, but the
real predictor is **fan-out over the project tree** (analyzer / pub
fetch / size analyzer / dart fix), not raw runtime.

## 5. What the existing whitelist actually grants

The pen-test report (TASK-PROC-054-01) establishes — and we accept as
input for Phase 2 — that every entry on the current whitelist
**interprets container-controlled files on the Windows host**:

- `flutter_test` runs `test/**/*.dart` on Windows under Dart's full
  `dart:io` privileges.
- `smoke_test` runs `scripts/windows/smoke_test_windows.ps1` — a file
  with full container write access — under
  `powershell -ExecutionPolicy Bypass`.
- `flutter_analyze` / `dart_fix` execute analyzer plugins loaded via
  container-controlled `analysis_options.yaml` and
  container-controlled `pubspec.yaml`.
- `flutter_build_windows` runs `windows/CMakeLists.txt` — a file
  with full container write access — via CMake's `execute_process`.
- `flutter_pub_get` performs network egress (pub.dev / git URLs)
  driven by container-controlled `pubspec.yaml`.

The pen-test verdict: **the watcher's whitelist enumerates *tool
names*, not *code that runs*. While the watcher is online, a
fully-compromised container has, in practice, the same privileges as
the Windows user account running the watcher.** All 16 vectors are
listed in `2026-05-19_01_pentest_report.md` (the completed task's
plans_and_protocols folder).

## 6. The trust assumptions baked into the current design

Stated explicitly so Phase 2 can lift or accept them:

1. The project tree is in the host's trust zone. (Today: implicit,
   nowhere documented.)
2. The container's egress is restricted enough that V5's pub-fetch
   network-pivot doesn't matter. (Today: untested assumption.)
3. The user reviews `win_bridge_watcher.ps1` carefully before each
   restart, with tooling that surfaces long-line / encoding /
   whitespace anomalies. (Today: stated by user; tooling unspecified.)
4. The Windows account running the watcher has limited privileges. (Today: assumed-violated on a typical developer machine.)
5. No container-writable directory is on the watcher's `$env:PATH`
   before canonical `flutter` / `dart` / `powershell` locations.
   (Today: setup-dependent; not enforced.)
6. The smoke-test script is treated with the same review rigour as
   the watcher itself. (Today: the user's safety procedure focuses on
   the watcher; the smoke-test script is not separately reviewed.)

## 7. The optionality contract today

There is no contract. The bridge is wired so that:

- `verify-quality` Step 3.2 calls the bridge unconditionally when Dart
  files changed, then runs a container-side fast check
  (`check_quality_gates.sh`) afterwards.
- Developer setups other than devcontainer-on-Windows would fail at
  the first `win_bridge.sh probe` (heartbeat absent → exit 1 →
  `verify-quality` fails).

So **the bridge is currently a hard dependency for Dart per-change
quality gates**. Mac and native-Linux developers cannot run
`verify-quality` Step 3.2 to completion as-shipped. This is a contract
violation against the user's stated requirement (bridge must be
optional). Phase 2 must address it.

The mechanical scope of the rename is small. The naming **decision**
is harder — see Phase 2.

## 9. Open empirical questions, parked

Items that Phase 2 should plan to answer empirically (some during
Phase 5):

- **V8 symlink behaviour**: do WSL→NTFS symlinks placed by the
  container get followed by PowerShell-spawned `flutter analyze`?
  (Listed as a follow-up exploration task in the pen-test report.)
- **Read-only-bind-mount feasibility**: can the devcontainer mount
  `scripts/` read-only while the rest of the project stays writable?
  Devcontainer bind-mount syntax permits `:ro` per-mount, but the
  project is mounted as a unit today.
- **Windows ACL behaviour after `git clone`**: do ACLs survive a
  clone such that "scripts owned by another user, read-only to
  watcher account" works?
- **Windows Sandbox cold-start cost**: practical floor for
  per-command sandbox spawning.
- **PATH-resolution check on the user's machine**: is Flutter
  installed at a project-mounted path (V9 conditional risk)?
