# AC-06 Interpretation: Single Authoritative Location

## The AC

REQ-PROC-044 AC-06: "Active skills + artifact dependencies + ordering rules documented in
single authoritative location."

## The Problem

After Wave 1 contract migration, the factory's authoritative information is distributed:
- Skill capabilities: `.claude/skills/<name>/SKILL.md` (60 files)
- Skill contracts: `.claude/skills/<name>/contract.yaml` (growing)
- Artifact schemas: `.claude/schemas/*.yaml` (~6 files)
- Ordering rules: `.claude/task_ordering_rules.yaml`
- Factory flows overview: `.claude/factory_flows.md`

Per TASK-PROC-044-02 synthesis §D-6 (file 05), this satisfies AC-06 "per dimension" but not
globally. The per-dimension distribution is intentional and correct — co-located ownership is
the design. The literal "single location" interpretation needs an aggregation artifact.

## Decision: The Factory-Map HTML IS the Single Authoritative Location

The rendered file at **`requirements_tasks/STATUS.factory_map.html`** is the AC-06
single authoritative location. It is:

1. **Aggregated**: reads all `contract.yaml` + `schemas/*.yaml` + `factory_flows.md` into
   one interactive graph
2. **Canonical path**: committed to the repo; always at the same absolute path
3. **Regeneratable on demand**: `python3 scripts/factory/render_factory_map.py` regenerates
   it; CI can regenerate per commit
4. **Git-tracked**: the rendered HTML is checked in so any reader (human or AI) can open
   it without running the script
5. **Machine-readable intermediate**: `render_factory_map.py --output /tmp/map.json` emits
   the Cytoscape.js JSON for programmatic consumption by other tools

### Why this interpretation is valid

The PRINCE2 principle behind AC-06 is navigability and consistency — a reader should be able
to find the current state without searching multiple disconnected sources. The factory-map HTML
achieves this: one URL, the full picture. The authoritative sources (contract.yaml sidecars,
schemas) are the writeable truth; the HTML is the readable projection.

This parallels the `requirements.md` pattern: per-requirement files are the authoritative
editable sources; `requirements.md` is the generated readable aggregation. AC-06's "single
authoritative location" maps to the generated artifact, not the source files.

### What the AC does NOT require

- All facts editable in one file (that would conflict with the co-location principle)
- Real-time accuracy (on-demand regeneration is sufficient; CI keeps it fresh)
- A separate "index" beyond what the graph viewer already provides

## Canonical Artifact Path

```
requirements_tasks/STATUS.factory_map.html
```

Generated by: `scripts/factory/render_factory_map.py`

Regeneration command:
```bash
python3 scripts/factory/render_factory_map.py --output requirements_tasks/STATUS.factory_map.html
```

## Heat Overlay Extension

The heat overlay (read-frequency data from `aggregate_read_metrics.py`) is an optional
extension of the same artifact. When present, it colors skill nodes by how frequently they
are read across sessions — exposing candidates for caching or restructuring.

Heat data is generated by:
```bash
python3 scripts/factory/aggregate_read_metrics.py --output /tmp/heat.json
python3 scripts/factory/render_factory_map.py --heat-data /tmp/heat.json
```

## Transition

Until Wave 1 contract migration is complete, the factory-map will show some skill nodes as
`has_contract: false` (grey nodes). The graph is still valid and useful; it degrades
gracefully. As contracts are added, the graph becomes richer.
