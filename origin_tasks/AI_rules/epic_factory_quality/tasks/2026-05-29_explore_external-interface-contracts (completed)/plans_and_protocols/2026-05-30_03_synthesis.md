## 2. Inventory verification (goal step 2)

The parent's E1–E9 stand. Walking the factory tree (`grep` over `.claude/skills/` for
git-remote, signing, ctx7, WebFetch, install channels) surfaced:

- **E4 is two modalities**, not one: the `ctx7` CLI (structured docs via `command_output`)
  and raw `WebFetch`/`curl` (`url_response`). They need different postcondition checks
  (`command_output_nonempty` vs `url_returned_2xx`) — the vocabulary reflects this.
- **E10 — Git-remote interaction** (push to `origin/develop`, tag push, `gh`). Real
  boundary, but **developer-operated today**: no skill issues `git push` unattended
  (`release`/`task-complete` commit locally; tagging/push is manual). Contract + the
  `git_remote_pushed` validator are **deferred (YAGNI)** until an automated push exists.
- **E11 — Windows-host build/test bridge.** The automated `win-command-bridge` was
  **deleted by TASK-PROC-054-02**; Windows builds/tests are now manual on the NTFS mirror.
  An external boundary with no automated channel — documented, no contract authored.
- **E8 (runtime telemetry)** confirmed hypothetical and out of scope — REQ-PROC-052
  forbids telemetry SDKs in the app today.

No signed-package-verification or SSH/SCP channel exists in the current factory.

## 3. Additive-field analysis — what the internal format must absorb

The internal `contract.yaml` format extends to all real boundaries with **one additive
field**: `input_modality:` on `derived_from`/`produces` items, enum
`file | frontmatter | conversation | invocation_arg | command_output | url_response`.

- It is **purely additive**: existing internal contracts (all `file`) remain valid; the
  field can default to `file` when omitted, so Wave 1–3 contracts need no edit.
- It is the *only* new field needed. The parent exploration's other speculation
  (`quality_criteria.kind:`) is unnecessary — the vocabulary-term reference
  (`check: <term>`) already encodes the kind by naming the validator.
- `kind: external-interface` + `interface: E<n>` distinguish boundary contracts from skill
  contracts so the skill lint (`check_skill_contracts.py`) can keep ignoring them (it globs
  `.claude/skills/*/contract.yaml`; boundary contracts live elsewhere — see §4).

## 4. DECISION — where external-interface contracts live

**Recommendation: FOLD under REQ-PROC-044** (broaden it to "all factory contracts"),
**not** a new sibling requirement.

Reasons:
1. **Same mechanism.** The compatibility check (parent §3) + this exploration prove the
   format is *identical* save one additive field. A sibling requirement would describe the
   same mechanism twice and invite drift — exactly the failure REQ-PROC-044 exists to prevent.
2. **AC-02 already requires the boundary.** "The artifact pipeline is traceable
   end-to-end … flow, scenario, persona without gaps" — persona insight *enters* via E2
   (product intake) and code *exits* via E7 (release → user). Splitting internal/external
   would fracture the very end-to-end traceability AC-02 demands.
3. **AC-04 already covers external inputs.** "Malformed or missing input artifacts cause a
   visible warning or graceful stop" — an empty `answer.md` or a failed fetch is exactly
   such an input. The external-state vocabulary is the AC-04 enforcement leg for the boundary.
4. **Single-developer stakeholder.** The "different stakeholder ownership" argument for a
   sibling does not apply — `app_provider` owns both internal and external factory contracts.

**Scope of the fold:** REQ-PROC-044's ACs speak of "skills". One small AC addition makes
the boundary explicit (illustrative):

> **AC-07** — Every external factory-boundary interface (developer I/O, web, OS, release,
> event channels) has a declared contract in the same format, whose `quality_criteria`
> reference the external-state postcondition vocabulary; a failing external-state check
> produces a visible warning or graceful stop (extends AC-01/AC-04 to the boundary).

**Concrete next step — `requ-explore`, NOT `product-intake`.** The goal text suggested
`product-intake`; this exploration's finding refines that. `product-intake` routes
*user-facing app* changes through the Persona→Scenario→Flow→Requirement chain. REQ-PROC-044
is a **process/factory** requirement (`stakeholder: app_provider`) that does not originate
from a persona need, so the correct mechanism to add AC-07 is `requ-explore` on REQ-PROC-044
(the skill that "MUST BE USED TO ADD OR MODIFY REQUIREMENTS"). Routing a REQ-PROC change
through `product-intake` would be a category error. See follow-up FU-8a (§5).

## 6. What this exploration could NOT validate (honest caveats)

1. **Live external state was not exercised.** `url_returned_2xx` and
   `package_installed_at_version` hit the network / OS; the unit tests cover only their
   deterministic predicate functions (`is_2xx`, `version_matches`). A real fetch / real
   install was not run in this session.
2. **The AC-07 wording is a draft.** The exact text lands in FU-8a under `requ-explore`'s
   end-state-language gate; §4's version is illustrative, not final.
3. **`input_modality` default behavior is asserted, not yet enforced.** Claiming Wave 1–3
   contracts "remain valid" assumes the boundary lint treats a missing `input_modality:` as
   `file`. That default must be implemented and tested in FU-8b — until then it is a design
   intent, not a verified property.
4. **Canonical contract location is unconfirmed.** `.claude/contracts/external/` is a
   proposal; FU-8b makes the call. The skill lint's `.claude/skills/*/contract.yaml` glob
   means boundary contracts MUST live outside `.claude/skills/` to avoid polluting it —
   that constraint is verified; the exact folder is not.
5. **E10/E11 are inventoried but unmodeled.** No contract was authored for git-remote or the
   Windows-host bridge because neither has an automated channel today; if one appears, the
   deferred vocabulary terms (`git_remote_pushed`, render/capture checks) activate.
