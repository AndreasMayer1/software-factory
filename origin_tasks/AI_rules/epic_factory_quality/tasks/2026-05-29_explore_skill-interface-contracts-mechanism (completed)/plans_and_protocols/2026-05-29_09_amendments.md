## A-1 — D-3 reframed: revision_target.yaml lives inside auto-created tasks, NOT in `automation/`

Round 3 D-3 was misleading by analogy to Magentic. Our system has no runtime router — sessions only start on tasks (or manual). So the cleanest model:

| Direction | Mechanism | Channel |
|---|---|---|
| skill → skill (async, requires fresh session) | Auto-create a revision task; attach `revision_target.yaml` inside that task's `plans_and_protocols/` | TASKS (the only async backlog) |
| skill → developer (blocking, same session) | `automation/pending_feedback/{TASK_ID}/question.md` | EXISTING channel — unchanged |
| skill → skill (synchronous, same session) | Direct `Skill` invocation | No file artifact needed |

**`revision_target.yaml` schema** moves into the new task's workspace at:
`requirements_tasks/.../tasks/<new_revision_task>/plans_and_protocols/revision_target.yaml`

Field set unchanged from Round 3 D-3. The discriminator `responder_required:` retains its enum but in practice will almost always be `skill` (because if a developer is needed, the channel is `pending_feedback/question.md`, not revision_target).

**Implication for FU-4**: title changes to "Define `revision_target.yaml` schema + auto-task-creation convention for skill→skill async revisions." Documentation lands in `pending_feedback/README.md` (cross-reference to the new pattern) and in `task-create/SKILL.md` (which gains a sub-section on "Creating a revision-attached task").

**Cleanup discipline** (per follow-up user feedback after file 08): active channels must contain only actionable items. Concretely:

| Artifact | Active location | After resolution | Why |
|---|---|---|---|
| `pending_feedback/{TASK_ID}/question.md` + `answer.md` | `automation/pending_feedback/{TASK_ID}/` | Move to `automation/answered_feedback/{TASK_ID}/` (existing convention; observed in current repo with `TASK-PROC-035-17` already archived); periodic archive/delete | Already-answered items pollute orchestrator scans; git preserves history |
| `revision_target.yaml` in new task's `plans_and_protocols/` | Stays in task workspace | NO movement (the task itself moves to `status: completed`; the file becomes audit trail in a non-scanned state) | The revision task's lifecycle gates visibility; no separate cleanup needed |
| Any future scanner looking for revision_target.yaml across all tasks | n/a | FU-4 explicitly forbids cross-task scans for revision_target.yaml — the channel IS the task, status field IS the lifecycle | Avoids creating a parallel active queue |

FU-4 scope expands to include: (1) document the answered_feedback move convention in `pending_feedback/README.md` (not strictly NEW — but currently informal); (2) add a periodic-archive script (`scripts/maintenance/archive_answered_feedback.py`) that moves `answered_feedback/{TASK_ID}/` older than N days to a `.git/`-only archive (or just deletes — git preserves the content); (3) explicitly document the "no cross-task scan for revision_target.yaml" rule.

## A-4 — FU-7 expanded scope: factory-map + token-cost measurement (per file 08 confirmation)

FU-7 absorbs the token-cost measurement work:

| Component | What |
|---|---|
| Factory-map render script | Reads contract.yaml + schemas + `factory_flows.md`; outputs Cytoscape.js JSON (`{nodes:[], edges:[]}`); produces static HTML viewer with filters |
| Script-call edges | Inferred from skill contracts (`may_invoke:` + `side_effects:` naming scripts) — script nodes optional in Wave-3+ |
| Token-cost measurement | `PreToolUse`/`PostToolUse` hook on `Read`; logs file path + active task ID + bytes; aggregator script computes per-file/per-skill frequency |
| Visualization | Heat-map overlay on factory-map nodes (read-frequency = node color/size) |
| Feed to claude-optimize | Read-frequency events also become `.factory/optimize/events/*.json` for claude-optimize consumption |

**Cytoscape.js** chosen as the JS framework (mature, filter-friendly, ~150KB, static HTML output we can ship from `releases/<v>/factory_map.html`).

**"Should we include script calls?"** answer: yes, but as **edges decorating skill nodes** for v1 (inferred from contracts). Promoting scripts to first-class nodes with their own contracts is a Wave-3+ refinement — opens the "scripts need contracts too" larger box. The v1 graph already shows script involvement via edge labels.

## A-7 — Net amendment to D-3 in Round 3
