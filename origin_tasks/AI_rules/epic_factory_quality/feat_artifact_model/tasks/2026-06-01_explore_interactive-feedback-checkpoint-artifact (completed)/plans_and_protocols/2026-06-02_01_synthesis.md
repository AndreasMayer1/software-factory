# Synthesis: Artifact Type for Interactive Skill Feedback Checkpoints

Date: 2026-06-02
Task: TASK-PROC-044-02-05

## 0. TL;DR for a future implementer

- **Recommended token**: `feedback-checkpoint`
- **Category**: `task-workspace` (existing; no new category needed)
- **Path glob**: `requirements_tasks/**/plans_and_protocols/*feedback-checkpoint*.md`
- **One-line definition**: "Interactive-mode developer decision captured at a skill approval/review checkpoint — the interactive analogue of the automated-mode pending-question/pending-answer pair."
- **Schema?**: No mandatory schema. Light YAML *envelope* (skill, phase, mode, decision-kind) + free-form prose body that preserves the developer's words verbatim. Same shape as `pending-question.md` (structured frontmatter, free body).
- **Minimal viable intervention**: capture **after the fact** (the skill writes the record when it logs its protocol / closes the gate), **opt-in**, NOT a mandatory pre-ask emission.
- **One genuine open decision remains for the developer** (see §8): the token *name* and whether capture is opt-in or mandatory.

If the developer prefers zero new tokens, the fallback is §7 Option C (broaden the existing `protocol` glob and rely on a naming convention) — but that loses the semantic distinction this exploration found to be load-bearing.

## 1. The problem, reframed (what we did not know at task creation)

The goal framed this as: "interactive developer feedback during skill execution lives in plans_and_protocols/ prose and disappears after context compression — formalize it as an artifact."

Investigation reframed the problem in three ways the goal did not anticipate:

**Reframe 1 — It is an *asymmetry*, not an *absence*.** The same logical event — *a skill hits an approval/review checkpoint and the developer decides* — is **already a first-class, durable, structured artifact in automated mode**. When `CLAUDE_AUTOMATED_MODE=1`, every such checkpoint is converted by `claude-automated-mode` into a `pending-question.md` + `pending-answer.md` pair under `automation/pending_feedback/<TASK_ID>/`, committed to git. The gap exists **only in interactive mode**, where the developer answers verbally and the decision evaporates on compression. So the artifact type already exists in the registry (`pending-question`/`pending-answer`); what is missing is its **interactive-mode twin**. This makes the cleanest framing "give the interactive checkpoint the artifact the automated path already has," not "invent a brand-new artifact."

**Reframe 2 — The developer's real goal is *visibility for an audience*, not *structure on the input*.** Re-reading the developer's own words (commit e5e716cf answer.md): *"the skills ask for feedback but there is currently no predefined form how the user must provide it and we don't want to force the user in one. therefore there are no defined artifacts. but the feedback is an informal artifact. i think for someone who wants to understand how the user interaction with the factory works (every user and everyone who wants to write a guide and everyone who wants to optimize) is interested in those user inputs."* The motivation is an **overview / discoverability** for three audiences (end users, guide-writers, optimizers). The explicit constraint is: **do not force the developer into a rigid input form**. This rules out a heavyweight mandatory YAML schema on the *answer*. It points to "capture and name the informal artifact" rather than "formalize the interaction."

**Reframe 3 — The pattern already exists organically, unnamed.** There are ~8 ad-hoc `*_decisions.md` / `*ratification*` / `*decision_note*` protocol files across `requirements_tasks/` (e.g. this very feature's `2026-06-01_02_protocol_ratification.md`, which captured the developer's registry feedback in prose). These are the **organically-evolved version of exactly this artifact**. They prove demand and prove value — but their naming is chaotic (no single glob reliably captures them), so they are invisible to any overview tool. This is positive evidence for a token (give the pattern one name + one home).

## 2. Where skills interrupt and ask (Seed 1)

37 skill files contain developer-input checkpoints (74 occurrences). The dominant shape is the **approval gate / review checkpoint**:

> present a draft / analysis / proposal → developer **approves** OR gives **free-form feedback** → skill revises and **re-presents** (iterative loop) → proceed only on approval.

| Skill | Checkpoint | Phase | What the developer decides |
|---|---|---|---|
| `ux-write-persona` | §6.5 User Approval Gate | after draft | approve persona / give revision feedback (gates the cascade scan) |
| `ux-flow-draft` | USER REVIEW CHECKPOINT; release-scope confirm; "satisfied? y/n" | impact analysis, chunking, end | approve analysis; confirm/adjust release chunks; accept flow |
| `ux-write-scenario` | approval gate | after draft | approve / revise scenario |
| `requ-explore` | §2.1a Location Approval Gate; §2.4 package assignment ("if it touches UI, always ask") | before writing; package assignment | approve target folder/path; choose target package per UI item |

| `product-intake` | routing decision | intake | confirm propagation path top-down |

The common denominator: the decisions are **design / structural / scoping** choices — where to put a requirement, whether a persona is right, which package an AC belongs to, whether an architectural plan is sound. They materially shape the produced artifact, and they encode *rationale that the artifact itself does not record* (the artifact shows the "what"; the checkpoint holds the "why we chose this over the alternative the skill proposed").

## 3. What is preserved vs. lost today (Seed 2)

| Mode | Capture mechanism | Durable? | Structured? |
|---|---|---|---|
| **Automated** | `claude-automated-mode` writes `pending-question.md` + `pending-answer.md`, commits them | **Yes** (git history; answer.md verbatim) | Envelope YAML + free body |
| **Interactive — happy path** | Developer answers verbally in native context | **No** — lost on compression | n/a |
| **Interactive — lucky path** | A diligent skill/agent happens to write a `*_decisions.md` protocol | Partially (only ~8 exist repo-wide; naming inconsistent → not discoverable) | Prose only |
| **Both** | `claude-log` appends `protocol.md` Action/Outcome entries; `task-complete` records `skills_used` | Outcome yes, **rationale rarely** | Semi |

What is **silently lost**: in interactive mode, the *rationale* behind a decision — *why* this folder, *why* reject the proposed persona trait, *why* this package over the one the skill suggested. The produced artifact records the chosen state; the discarded alternative and the reason live only in the conversation. After compression they are unrecoverable. The pattern to what matters: **the decisions that lose information are exactly the ones where the developer *overrode or steered* the skill's proposal** — pure "approve as-is" loses nothing of value; "no, do X instead because Y" loses Y.

## 4. Boundary with existing tokens (Seed 3)

| Token | Covers | Cardinality | Why it does NOT fill the gap |
|---|---|---|---|
| `user-input` | verbatim developer seed at explore-task **start** | 1 per task, at start | One-shot seed only; not mid-skill decisions |
| `pending-question` / `pending-answer` | **automated-mode** escalation checkpoint | 1 pair per escalation | Automated mode only; the developer is *absent*. The interactive twin is missing. |
| `protocol` | step-by-step execution log | many per task | Records actions/outcomes, not the developer-decision exchange; too broad to be the *named* home for a checkpoint |
| `cascade-log` | multi-pass cascade tracker | 1 per cascade task | Tracks pass state, not developer decisions |

**The gap, precisely**: the series of interactive approve/steer decisions made *while the developer is present* during a single skill run. It is the **interactive-mode counterpart of `pending-question`/`pending-answer`**, and it has no token and no consistent file home.

## 5. Schema vs. token only (Seed 4)

The registry has two precedents for "feedback" artifacts:
- `scribble-feedback.md` — **unstructured prose**, accumulates reviewer comments.
- `pending-question.md` / `pending-answer.md` — **structured YAML envelope + free body** (task_id, session_id, status, asked_at, skill + free-form question/answer).

The developer's constraint ("don't force the user into a form") and the audience goal ("understand the interaction") pull in opposite directions and resolve cleanly only if we **split the two sides of the exchange**:

- The **ask** (skill-emitted) *is* structurable without burdening the developer: which skill, which phase, mode, and what was proposed. This is metadata the skill already has.
- The **answer** (developer-emitted) must stay **free-form prose** — verbatim, unforced.

So the right shape is **`pending-question.md`'s shape, not `scribble-feedback.md`'s**: a **light YAML envelope + free-form body**. A *full* schema (validated fields on the answer) is contraindicated — it violates the no-forced-form constraint and buys nothing the audience needs. **Recommendation: token + light envelope convention; NO standalone schema file.**

Suggested envelope (all envelope fields are skill-fillable; the body is the developer's words):
```yaml
---
skill: requ-explore          # which skill hit the checkpoint
phase: location-approval     # named gate within the skill
mode: interactive            # interactive | (automated → use pending-question instead)
decision: revised            # approved | revised | rejected
artifact_ref: requirements_tasks/.../requirements.md   # what the decision shaped
captured_at: 2026-06-02T...Z
---
# Proposed
<one-paragraph: what the skill proposed>
# Developer decision
<verbatim developer response — free-form, unforced>
# Rationale captured
<the "why" that the produced artifact does not itself record>
```

## 6. Impact on skill design (Seed 5) — minimal viable intervention

Two candidate intervention points:

- **(A) Pre-ask emission** — skill writes a checkpoint file *before* asking. Rejected as the default: it is heavyweight, slows interactive sessions, and edges toward "forcing a form" (the developer must answer into a scaffold). It also duplicates what the conversation already shows live.
- **(B) Post-decision capture** — skill writes the record *after* the gate closes, when it logs its protocol / at `task-complete`, **only when the developer steered** (decision ≠ plain approve). **Recommended.** It is opt-in, near-zero developer friction (the skill summarizes; the developer already spoke), and it captures exactly the information that is otherwise lost (§3: the override + rationale).

**Minimal viable intervention**: add the `feedback-checkpoint` token + the envelope convention to the registry, and have the highest-value gate skills (`ux-write-persona`, `ux-flow-draft`, `requ-explore` location/package gates, `code-complex` plan review) write one `*feedback-checkpoint*.md` per *steered* decision at protocol-log time. No mandatory pre-ask scaffolding. Other skills adopt opportunistically. This also lets the ~8 existing `*_decisions.md` files be migrated/renamed into the glob over time, populating the overview the developer wants.

## 7. Options laid out for the decision

| Option | Token(s) | Glob | Pros | Cons |
|---|---|---|---|---|
| **A (recommended)** | `feedback-checkpoint` | `plans_and_protocols/*feedback-checkpoint*.md` | clean semantics; mirrors automated pair; honors developer's proposed name | zero existing files → skills must adopt before overview is populated |
| **B** | `decision-record` | `plans_and_protocols/*decision*.md` | immediately captures the ~8 existing organic files; zero retrofit | "decision" is broader than user-feedback (catches AI-only technical decisions too) → noisier overview |
| **C (no new token)** | reuse `protocol` | — | nothing to add | loses the semantic distinction; overview impossible; the gap stays invisible |
| **D** | pair `feedback-checkpoint` + `feedback-response` | two globs | maximal symmetry with `pending-question`/`pending-answer` | two files per interactive checkpoint = heavyweight; nudges toward forcing a form |

A also leaves room to *retro-tag* the existing `*_decisions.md` files by renaming them into the glob during normal maintenance, getting B's population benefit without B's noise.

## 8. Decision framed for the developer (genuine open choices)

The exploration is conclusive on **the shape** (light envelope + free body, post-decision capture, opt-in, task-workspace category, interactive twin of the automated pair). Two choices genuinely need the developer:

1. **Token name**: `feedback-checkpoint` (Option A — clean, matches your own suggested name) vs. `decision-record` (Option B — auto-captures the 8 existing files but is semantically broader). Recommendation: **A**, with optional migration of existing `*_decisions.md` files into the glob.
2. **Capture discipline**: opt-in post-decision capture by high-value gate skills (recommended), vs. mandatory across all 37 gate-bearing skills (higher coverage, but friction + risk of "forcing a form"). Recommendation: **opt-in, high-value skills first**.

Because this is an explore task (`writes_requirements: false`) and the registry is governed by a developer ratification gate (the predecessor TASK-PROC-044-02-01 was ratified, not self-approved), this synthesis is a **proposal**. The registry edit itself (appending the token to `.factory/registry/artifacts.yaml` under `task-workspace`, plus wiring the chosen skills) should be a follow-up impl task created after the developer picks the name + discipline above.

## 9. What remains uncertain (honest)

- **Adoption is the real risk, not definition.** A token without skills emitting into it stays empty. The value depends on skills actually writing the records; this exploration did not implement that wiring, and skill-by-skill adoption effort is unquantified.
- **Migration of the 8 organic files** is desirable for the overview but untouched here; whether they should be renamed in place or left as-is is a judgment the developer may want to make.
- **Overview surfacing**: the developer wants an "overview of user-input informal artifacts." A token makes them *globbable*, but no overview *tool/report* is proposed here (e.g. a generated index akin to `STATUS.md`). If the overview itself is the deliverable the developer cares most about, a small follow-up "render feedback-checkpoint index" script may matter more than the token alone.
- **Boundary nuance with `user-input`**: if a token is added, the one-shot `user-input` seed and the mid-skill `feedback-checkpoint` could be presented together in any overview as "the informal developer-input family" — worth noting for whoever builds the overview.
