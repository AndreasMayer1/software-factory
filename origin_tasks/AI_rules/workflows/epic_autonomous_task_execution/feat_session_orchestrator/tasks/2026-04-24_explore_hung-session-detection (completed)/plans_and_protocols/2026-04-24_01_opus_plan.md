# Opus Plan: Hung Session Detection & Recovery

## Objective

Define what "hung" means for an automated Claude session, evaluate detection approaches,
specify thresholds and recovery strategy, then update `feat_session_orchestrator/requirements.md`
with new ACs and create an impl task goal.

## Analysis Summary

### Architecture facts
- Sessions launched via `subprocess.run(["claude", ...], capture_output=True, text=True, env=env)`
  — **blocking call, no timeout parameter** in current code.
- `OrchestratorDeps` is an injectable dataclass; `run_subprocess: Callable` is the boundary.
  Switching to `Popen` requires adding a new callable to this dataclass.
- JSONL path: `/home/vscode/.ccs/shared/context-groups/default/projects/.../<uuid>.jsonl`
  — does NOT grow while Claude waits for tool results (bash/dart process in flight).
- Child processes under `claude` PID (`ps --ppid <pid>`) indicate tool call in progress.

### Incident (2026-04-23) re-analysis
- Session ran 13+ hours; JSONL stale since 10:08; BUT 4 active dart/bash children.
- Conclusion: **genuinely working** (long test run), NOT hung.
- Key insight: child process presence is the correct liveness signal.

### Approaches evaluated

| Approach | Description | Verdict |
|---|---|---|
| A — `subprocess.run(timeout=N)` | Hard ceiling, raises TimeoutExpired | Only for absolute ceiling; cannot distinguish hung from slow |
| B — `Popen` + watchdog thread | Separate thread polls liveness | Precise, but threading adds complexity and harder to test |
| C — `Popen` + main-thread poll | Poll loop in same thread; check JSONL mtime + child PIDs | Precise, no threads, stop-conditions checkable during wait |
| D — External process (cron kill) | External watchdog outside orchestrator | Requires LLM monitoring → excluded by scope |

### Recommended: Approach C + hard ceiling (A)

**Primary (liveness-based)**: Switch session launch to `Popen`; poll every 60 s:
1. Check `os.path.getmtime(jsonl_path)` — has it grown since last check?
2. If stale: run `ps --ppid <claude_pid>` — any children (dart/bash)?
3. If no children AND JSONL mtime unchanged for ≥ `--hung-timeout` min → hung; kill.

**Secondary (hard ceiling)**: Track wall-clock start time in the poll loop;
if elapsed ≥ `--session-timeout` s → kill regardless of liveness.

### Thresholds
- Poll interval: `--hung-check-interval` = 60 s (default)
- Hung threshold: `--hung-timeout` = 30 min (default) — conservative enough for dart analysis server startup (~30–60 s)
- Hard ceiling: `--session-timeout` = 14400 s = 4 h (default) — catches the observed 13-hour case decisively

### Edge cases handled
- **Long Flutter tests**: `dart` child present → not hung ✓
- **Dart analysis server startup**: 30–60 s with no children; 30-min threshold ignores this ✓
- **Brief tool-result processing**: seconds between tool completion and next tool call; threshold ignores ✓
- **Rate-limit wait inside session**: Claude sleeps internally, no children, JSONL stale; 30-min threshold is still conservative given rate-limit waits are typically 60 min

### Recovery strategy
1. SIGTERM to `claude` child PID
2. Wait 10 s; SIGKILL if still alive
3. Task `goal.md` **left unchanged** (`status: in_progress` + `session_id` intact)
4. Next loop iteration: existing AC-15 in-progress resume logic attempts to resume the JSONL session
5. If resume fails: existing AC-21 exhaustion limit (3 attempts) triggers and includes task in report
