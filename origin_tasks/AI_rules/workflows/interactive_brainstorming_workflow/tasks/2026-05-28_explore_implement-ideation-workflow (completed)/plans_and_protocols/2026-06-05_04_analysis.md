# Analysis (Phase 2) — TASK-PROC-004-02

## Reframed problem

REQ-PROC-004 asks us to add a **divergent creative phase + user voice** to factory exploration, and the 2026-06-05 follow-up adds a **completeness loop** for when one model run cannot emit the whole answer. The gathering phase reveals these are **two orthogonal mechanisms that share one control artifact**:

1. **Divergence mechanism** (quality of ideas): counteract the model's *structural* premature convergence. The lever is NOT temperature (unavailable + weak) but **prompt structure + fan-out**: CoT, mode-separated generator/critic, and ideally context-isolated frame-branches (ADHD).
2. **Completeness mechanism** (coverage of the answer): counteract the *output-budget* ceiling. The lever is a **gap-driven multi-run loop** with a separate gap-detector and a ledger.

Both are governed by the same object: a **ledger of open items** (ideas-to-explore in divergence; gaps-to-close in completeness). This is the central discovery — see synthesis.

## Scope

**In scope** (this exploration must decide):
- Implementation vehicle (skill / agent / protocol-section / combination), per effort.
- Concrete file-watch pause design (reusing or extending `pending_feedback`).
- Draft ideation prompt language (paste-ready).
- Effort-calibration heuristic logic.
- Multi-run iteration loop: gap-ledger schema, gap detection, continuation vehicle, terminal condition, runaway backstop, composition with the user gate and effort.
- Prioritized integration plan.

**Out of scope**: implementing the skill/agent files themselves (that is the follow-on impl task); changing REQ-PROC-004's WHAT; app-domain features.

## Goal (observable properties of a good result)
- A next implementer can build the vehicle without re-deriving the trade-offs.
- The design **reuses existing factory machinery** (pending_feedback, effort field, agent infra, fresh-agent-per-batch tracker) rather than inventing parallel mechanisms — honoring REQ-PROC-059 (a) scripts-over-instructions, (b)/(e)/(h) token economy, (g) sub-agent isolation.
- Divergence design is grounded in evidence (ADHD, CoT), not folklore (temperature).
- The completeness loop is **bounded and terminating** (no infinite churn) and **honest** (emits partial + open-gaps when capped).

## Constraints (cannot change)
- **C1 — No temperature control.** Claude Code CLI cannot set it. Divergence is prompt-only.
- **C2 — Sessions cannot self-schedule** (CLAUDE.md responsibility boundary). The pause/resume across a *human* gate is owned by the orchestrator (automated) or a live turn (interactive). No agent may poll/sleep on a file.
- **C3 — Skill calls do NOT isolate context** (CLAUDE.md §2). Only the Agent (Task) tool isolates. So "make ideation a skill" ≠ context isolation; isolation requires an agent.
- **C4 — File-based memory is law** (no plan tool, plans live in `plans_and_protocols/`). The ledger must be a file in the task folder.
- **C5 — Dependency/admission gates**: no new top-level deps; prefer reusing scripts.

## Tensions the design must navigate
- **T1 — Context continuity vs. isolation.** Inline = context kept, but anchoring (ADHD shows shared context causes premature convergence) and main-window pollution. Agent = anti-anchoring + isolation, but cold-start context-reload cost. The follow-up clarified the completeness constraint is *output budget*, NOT input context — so a *same-session continuation* needs no reload; only a *cold agent restart* pays it. These pull opposite ways and the resolution is effort-dependent.
- **T2 — One gate or two.** The ideation user-gate (divergence→synthesis) and the completeness loop both want approval points. Two competing gates = friction. Must unify.
- **T3 — Self-assessment vs. separate critic.** Evidence says self-judged completeness is biased (amplified). But a separate critic agent costs a spawn + the oscillation risk. Need the cheapest reliable certifier.
- **T4 — Divergence wants high fan-out; token economy wants minimal calls.** ADHD's ~10 calls vs 1 is justified only for high-reversal-cost decisions → ties fan-out to effort.
- **T5 — Mechanism richness vs. over-engineering.** Seed 5 explicitly warns: trace real past explorations; if the gap is small, keep it minimal. Most factory explorations are S/M, where a full 5-branch ADHD + multi-iteration loop is overkill.

## Key unknowns to resolve (not necessarily answer, but clarify enough to decide)
- KU1: Is the vehicle one thing or a layered set (protocol doc + opt-in skill + reusable critic agent)?
- KU2: What exactly carries between iterations, and is the carrier the same for breadth vs depth gaps?
- KU3: What is the operational "no gaps remain" certification, and what bounds it per effort?
- KU4: Can the user gate be the existing `pending_feedback` path verbatim, or does it need extension?
- KU5: What is the *minimal* first integration that delivers value (which skill, what insertion)?
