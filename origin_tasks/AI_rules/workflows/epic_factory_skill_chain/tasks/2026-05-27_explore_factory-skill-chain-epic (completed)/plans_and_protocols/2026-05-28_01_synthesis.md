# Synthesis — TASK-PROC-063-01 (2026-05-28)

## TL;DR

**REQ-PROC-063 was not written.** This exploration discovered that placing it cleanly is blocked by a folder-structure governance issue already partially addressed by REQ-PROC-045 — which itself contains an explicit carve-out that legitimises the problem. The right next step is to **modify REQ-PROC-045**, then restructure `process/AI_rules/`, then return to REQ-PROC-063 with a principled home.

## Investigation path

The goal was to define REQ-PROC-063 — an epic that formalises end-to-end factory skill chain integrity. Four rounds of analysis were conducted:

### Round 1 — Where REQ-PROC-063 sits relative to existing requirements

Search of `requirements_tasks/process/` revealed **REQ-PROC-044 (Software Factory Quality Properties)** with significant overlap: its AC-01 (every skill produces reachable output without silent failure) and AC-02 (artifact pipeline traceable end-to-end) appear to cover chain integrity already.

On closer reading: REQ-PROC-044 covers *static* per-skill quality (each skill is correct). The gap REQ-PROC-063 was meant to close is *inter-skill handoff* (the chain doesn't stop after a skill succeeds). Genuine distinction — but the boundary is fine-grained.

### Round 2 — User feedback: REQ-PROC-044 is the umbrella, REQ-PROC-063 is a child concern

User clarified that REQ-PROC-044 is generic ("could mean anything"); almost every other process requirement sits logically under it. REQ-PROC-063 = "the workflows don't break" = one specific quality dimension under REQ-PROC-044.

Structuring axis question raised: per-flow, per-skill, or per chain segment?

### Round 3 — Per-flow vs per-skill vs per-segment analysis

- **Per-flow**: collapses 14 input types in `factory_flows.md` to ~7 chain shapes. Sub-features inflate handoff ACs across each shape (duplication).
- **Per-skill**: ~25–30 chain-participating skills → ~25 sparse requirements; most would just declare `next: X`. Duplicates `skill.md` recipe content.
- **Per chain segment** (3 features: handoff_contract, chain_topology, chain_break_detection): captures the actual failure modes (handoffs that don't fire, topology that goes stale, breaks that go undetected) without per-flow duplication or per-skill sparseness.

Recommended chain-segment axis. **But user pivoted before this was accepted** — see Round 4.

### Round 4 — Structural problem: `process/AI_rules/` taxonomy itself is unprincipled

User raised the deeper concern: REQ-PROC-063 cannot be placed cleanly because `process/AI_rules/` mixes four axes (meta-principles, what is regulated, tooling, workflows) and has known overlaps:

| Folder A | Folder B | Overlap |
|---|---|---|
| `requirements_management/release_preparation/` | `workflows/release_workflow/` | both release |
| `requirements_management/user_flow_to_requirements/` | `workflows/user_flow_collaboration_workflow/` | both user-flow |
| `coding_standards/testing/` | `workflows/testing_workflow/` | both testing |
| `requirements_management/artifact_soundness/` | `factory_quality/` REQ-PROC-044 AC-04 | both: don't silently corrupt |
| `factory_quality/` REQ-PROC-044 | almost everything else | quality umbrella above every category |

No requirement governs `process/AI_rules/` structure — search returned zero hits for "folder structure", "directory structure", "requirements organization", "requirements taxonomy". The structure is purely conventional.

Established methods (from training):
- **Prevention**: faceted classification · bounded contexts · schema-first · mandatory placement criteria in tooling. Best practice = bounded contexts + tooling enforcement.
- **Refactoring**: Strangler Fig · ID-based aliasing (already enabled by REQ-ID references) · cluster analysis · Tidy First.

### Round 5 — Discovery: REQ-PROC-045 already exists, but exempts process/

Search of `requirements_management/` surfaced **REQ-PROC-045 (Requirements Structure Quality)** — `status: active`, 11 ACs. It already defines:

- WHO–WHAT naming pattern (DDD ubiquitous language + semantic cohesion)
- Three epic boundary tests (independent value, domain entity, parallel development)
- "Depth via grouping, not nested epics" rule
- LLM judgment checklist (10 questions)
- Cross-reference completeness detection (AC-11)
- Validation enforcement at `requ-explore` Phase 1 and `release-begin-impl` Phase 0

**The blocker**: line 136 of REQ-PROC-045's requirements.md explicitly exempts process/ and non-functional/ from the epic-enforcement rule:

> **process/ and non-functional/ usage.** Plain organizational folders dominate these categories because most of their requirements are standalone (one folder = one requirement, no sub-features). The `epic_*/feat_*` convention applies here only when a requirement genuinely decomposes into independently implementable features (example: `workflows/epic_autonomous_task_execution/feat_automated_mode/`).

This carve-out is what allows `process/AI_rules/` to have grown into its current unprincipled shape.

User decision: **modify REQ-PROC-045** to remove the carve-out and extend epic-enforcement to process/ (with stricter epic-content rules than today's), plus evaluate whether non-functional/ should follow the same policy. The modification is the next-step exploration. The folder restructuring of `process/AI_rules/` follows as impl tasks. REQ-PROC-063 placement is the downstream beneficiary.

## Decisions reached

1. **REQ-PROC-063 is not written by this task.** The original goal is deferred until the structural blocker is resolved.
2. **REQ-PROC-063 remains valid as a future requirement.** Its scope (end-to-end chain integrity) is real and distinct from REQ-PROC-044 (per-skill quality). The three-chain-segment axis (handoff_contract, chain_topology, chain_break_detection) is the recommended sub-feature structure when REQ-PROC-063 is eventually written.
3. **REQ-PROC-044 is the umbrella.** REQ-PROC-063 will reference it as logical parent via Related Requirements + an `after:` dependency. No folder nesting.
4. **The blocker is REQ-PROC-045's carve-out for process/ and non-functional/.** A new exploration task modifies REQ-PROC-045 to remove the carve-out.
5. **TASK-PROC-063-02 (requ-explore post-creation continuation) is parked.** It waits on the REQ-PROC-045 modification task, then on REQ-PROC-063 itself.
