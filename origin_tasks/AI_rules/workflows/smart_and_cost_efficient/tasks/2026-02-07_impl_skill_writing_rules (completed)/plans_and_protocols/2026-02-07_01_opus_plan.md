# Opus Plan: Add Rules to Prevent Verbose WHY Comments in Skill Files

## Objective

Establish clear rules that prevent AI agents from adding verbose Dart-style `///` WHY comments to skill and agent files (`.claude/`). Skills are process instructions loaded into context -- every unnecessary token costs money and reduces available context for actual work.

## Analysis Summary

### Scale of the Problem
- **22 occurrences** of `/// Why:` / `/// Source:` across **6 skill files**
- Worst offender: `create-scenario/skill.md` with 10 lines of WHY comments
- Pattern: A recent implementation task (auto ID registry) added WHY comments to every skill it touched, treating skills like code files

### Root Cause
CLAUDE.md Section 5 ("Code Documentation - WHY Comments") says to add WHY comments for non-obvious code, and agents are obeying this rule universally. The section title says "Code" but never explicitly excludes skill/agent files. Agents see "add WHY comments" instructions in Section 4 steps 2-4, which reference the implementation workflow broadly.

### Key Distinction
| Aspect | Code Files (`lib/`, `test/`) | Skill Files (`.claude/`) |
|--------|------------------------------|--------------------------|
| Purpose | Implementation logic | Process instructions |
| Reader | Future AI sessions that might delete code | AI agent executing the skill |
| Risk | Code removal without understanding | Token waste, context bloat |
| WHY comment value | HIGH (prevents deletion) | NEGATIVE (wastes tokens) |
| Format | Dart `///` syntax | Markdown |

### Option Analysis

**Option A: Add exclusion to CLAUDE.md Section 5** -- PARTIAL FIT
- Section 5 is titled "Code Documentation" -- adding a skills exclusion here feels like a footnote
- Agents scanning for "what to do with skills" won't look in a code documentation section
- However, agents applying WHY comments DO read this section, so an exclusion here catches them at point-of-action

**Option B: New section in CLAUDE.md** -- BEST FIT
- CLAUDE.md is the constitution; skills/agents ARE its core subject matter
- A dedicated section about skill writing principles is natural alongside the existing sections about code standards, testing, and documentation
- Adding ~15-20 lines to a 256-line file is acceptable
- Most discoverable location: agents ALWAYS read CLAUDE.md

**Option C: Create `.claude/GUIDELINES.md`** -- GOOD BUT LESS DISCOVERABLE
- Clean separation, but agents are not instructed to read it before editing skills
- Would require adding "read GUIDELINES.md before editing skills" to CLAUDE.md anyway
- Indirection: agent reads CLAUDE.md -> told to read GUIDELINES.md -> finally sees the rule
- Better for comprehensive skill-writing guides (future), not for a single critical rule

**Option D: Add to `doc/general/`** -- REJECTED
- Violates CLAUDE.md's own scope rule: `doc/` is ONLY for `lib/`, `test/`, `integration_test/`
- Self-contradictory to add process rules in a folder explicitly scoped to code guidelines

### Recommendation: Hybrid of A + B

**Primary**: Add a new subsection to CLAUDE.md Section 5 that explicitly scopes WHY comments to code files only and forbids them in skill/agent files. This catches agents at the exact moment they're considering adding WHY comments.

**Secondary**: Add a brief new Section 5b or fold into Section 7 (Coding Standards) a one-liner about skill file token efficiency.

The reasoning: Agents add WHY comments because Section 5 tells them to. The most reliable fix is to add the exclusion WHERE THE INSTRUCTION LIVES. A separate section about "Skill Writing" would be nice but the critical path is Section 5.

## Execution Plan

### Agent 1: Single Implementation Agent

This is a simple, targeted edit to CLAUDE.md. One agent is sufficient.

#### Step 1: Add Scope Clarification to Section 5

**Location**: `CLAUDE.md`, immediately after line 139 (`## 5. Code Documentation (WHY Comments)`)

**Add after "THE SOLUTION" line (line 143)**, before the Format section:

```markdown
**SCOPE**: Code files ONLY (`lib/`, `test/`, `integration_test/`)
**FORBIDDEN in**: `.claude/` skills/agents, `requirements_tasks/`, `doc/`
Skills are token-sensitive context -- every line costs. Use concise markdown instead.
```

#### Step 2: Add Explicit "Where NOT to add" Rule

**Location**: After the existing "When NOT to add" block (after line 172), add:

```markdown
**NEVER in skill/agent files** (`.claude/`):
Skills are loaded into AI context. Dart-style `/// Why:` comments waste tokens.
If a skill step needs explanation, use a single inline note: `(needed because X)`.
```

#### Step 3: Clean Up Existing Violations

Remove or convert all 22 `/// Why:` / `/// Source:` occurrences across the 6 affected files:

| File | Lines | Action |
|------|-------|--------|
| `setup-task/SKILL.md` | 204-207 | Remove entirely (the MANDATORY note below already explains the purpose) |
| `create-persona/skill.md` | 44-47 | Remove (context is self-evident from section heading) |
| `create-user-flow/skill.md` | 95-98 | Remove (same registry pattern) |
| `create-scenario/skill.md` | 119-122, 185-187, 200-203, 257-260, 285-288 | Remove or convert to single-line `(reason)` where non-obvious |
| `create-impl-task/skill.md` | 112-113 | Convert to inline: fold into the step description |
| `modify-user-needs/skill.md` | 191-194, 219-221 | Remove or convert to inline note |

**Conversion rule**: If removing the WHY comment makes the step unclear, add a parenthetical at the end of the instruction line. Example:

Before:
```markdown
/// Why: Category must be assigned before folder creation to suggest canonical name.
/// Source: requirements_tasks/.../2026-02-07_01_high_level_plan.md#phase-1.1

**Step 1.1**: Determine category first
```

After:
```markdown
**Step 1.1**: Determine category first (needed before folder creation for canonical naming)
```

#### Step 4: Verify

- Grep `.claude/` for `/// Why:` -- should return 0 results
- Read modified CLAUDE.md Section 5 for clarity and consistency
- Confirm total CLAUDE.md stays under 280 lines

## Exact Text Changes

### Change 1: CLAUDE.md Section 5 -- Add Scope (after line 143)

Insert between `**THE SOLUTION**: WHY comments explaining non-obvious decisions` and `**Format (Dart)**:`:

```markdown

**SCOPE**: Code files ONLY (`lib/`, `test/`, `integration_test/`)
**FORBIDDEN in**: `.claude/` skills/agents, `requirements_tasks/`, `doc/`

> Skills are token-sensitive context loaded into every agent call.
> Never use `///` WHY comments in skills. If a step needs brief context, use an inline parenthetical: `(needed because X)`.
```

### Change 2: CLAUDE.md Section 5 -- Add to "When NOT to add" (after line 172)

Add after the last "simple changes" bullet:

```markdown

**NEVER in non-code files**:
- `.claude/` skill/agent files: Use inline `(reason)` parentheticals if needed
- `requirements_tasks/` docs: Context belongs in plans_and_protocols/
- `doc/` guidelines: Already explanatory by nature
```

## Risks

1. **Risk**: Agents stop adding WHY comments to code too (overcorrection)
   **Mitigation**: The rule is scoped explicitly -- "SCOPE: Code files ONLY" makes it clear WHERE to add them, not just where not to

2. **Risk**: Some WHY comments in skills contain genuinely useful context that gets lost
   **Mitigation**: Step 3 conversion rule -- if removing makes the step unclear, convert to inline parenthetical rather than deleting

3. **Risk**: Future skill authors don't read the updated Section 5
   **Mitigation**: Section 5 is already mandatory reading for implementation agents (referenced in Sections 4.2, 4.3, 4.4). The implementation-engineer agent explicitly lists WHY comments in its workflow.
