# Opus Review: ux-create-flow Skill System Refactor

**Date**: 2026-03-27
**Reviewer**: Opus (claude-switch-opus)
**Subject**: Four-skill system — ux-create-flow, ux-flow-draft, ux-flow-complete, ux-flow-approve

---

## 1. Overall Assessment

The refactor successfully achieves its primary objectives: the 583-line monolith is cleanly split into four focused skills with clear responsibilities, the state machine is now a single explicit canonical table in the dispatcher, and the natural split boundaries identified in the plan have been respected. The resulting system is more navigable and less error-prone than the original scattered prose. That said, five specific issues warrant attention before the system can be considered production-ready: a status-transition ambiguity in CONTINUE mode for `draft` flows, an asymmetry in the `approved` guard between the dispatcher and sub-skills, an underspecified cluster expansion path when a CONTINUE iteration discovers a new impact on a fourth (non-cluster) flow, a missing explicit commit in the CONTINUE pending-impacts incorporation path for first-time creation, and the absence of any fallback instruction when the user invokes ux-flow-draft directly (bypassing the dispatcher). None of these are showstoppers, but two of them (the `draft`-status CONTINUE reset and the cluster expansion path) are edge cases that an AI executing the skill could handle incorrectly.

## 2. Contradictions / Coherence Issues

### 2.1 CONTINUE mode status reset omits `draft` (ux-flow-draft vs. state machine)

**Evidence — ux-flow-draft, CONTINUE MODE: Load Existing Context:**
> "Status reset: If the flow's current `review_status` is `aligned` or `approved`, set it to `in_review` and add a `review_history` entry"

**Evidence — ux-create-flow state machine:**
> `| draft / in_review | CONTINUE | — | in_review | ux-flow-draft |`

The state machine says a `draft` flow also transitions to `in_review` on CONTINUE. The CONTINUE mode context loading section in ux-flow-draft only resets `aligned` or `approved` — it says nothing about `draft`. The implication is that a flow arriving in CONTINUE mode with `review_status: draft` will remain `draft` after the iteration, never advancing to `in_review`. This contradicts the state machine.

**Verdict**: Bug. The status reset instruction should read: "If the flow's current `review_status` is `draft`, `aligned`, or `approved`, set it to `in_review`." (In-review flows are already at the correct target state and need no reset.)

---

### 2.2 `approved` guard asymmetry between dispatcher and sub-skills

**Evidence — ux-create-flow Guard Rails:**
> "Never set status to `approved` while `## Pending Impacts` exists in flow.md."

**Evidence — ux-flow-complete Illegal transitions:**
> "any status → approved while `## Pending Impacts` section exists in flow.md"

**Evidence — ux-flow-approve Illegal transitions:**
> "any status → approved while `## Pending Impacts` section exists in flow.md"

The guard appears in all three places, which is correct — but the dispatcher guard rail uses a different (weaker) phrasing: it says "Never set status to `approved`..." which is an instruction to the AI. The sub-skills express it as "Illegal transitions (block and report)" which is an enforcement trigger. The dispatcher's version would pass silently if the AI is executing ux-flow-complete or ux-flow-approve and only the sub-skill's version is active in context. This is not a logical contradiction but a framing inconsistency: the dispatcher's guard is rendered moot once the sub-skill is invoked (because the dispatcher is no longer executing). The sub-skills are the actual enforcement point.

**Verdict**: Minor coherence issue. The dispatcher guard rails are redundant with the sub-skill illegal-transition blocks. This is acceptable as a belt-and-suspenders pattern, but it can mislead a reader into thinking the dispatcher enforces these guards at runtime. A clarifying note ("these are enforced by the sub-skills at execution time") would resolve the confusion.

---

### 2.3 CC-E handles `aligned` sibling but state machine has no `aligned → aligned` row

**Evidence — ux-flow-complete, CC-E:**
> "If sibling is `aligned`: No user confirmation needed... Set `review_status: pending_alignment`"

**Evidence — ux-create-flow state machine:**
> `| aligned | sibling CONTINUE identifies impact | — | pending_alignment | ux-flow-complete |`

This is actually consistent — the state machine does have the `aligned → pending_alignment` row. The concern here is a subtle point: CC-E says "No user confirmation needed (`aligned` is not yet final — no joint approval has occurred)" but the state machine row has no explicit guard (`—`). This is correct: `aligned` means content-approved but not yet jointly approved, so rollback without confirmation is correct. No contradiction exists, but the inline justification ("aligned is not yet final") is helpful and its absence from the state machine table could cause a future AI to question whether the guard column should read something other than `—`. The current system handles this correctly.

**Verdict**: No contradiction. Observation only.

---

### 2.4 CC-E: `approved → pending_alignment` guard in state machine vs. skill text

**Evidence — ux-create-flow state machine:**
> `| approved | sibling CONTINUE identifies impact | user confirms rollback | pending_alignment | ux-flow-complete |`

**Evidence — ux-flow-complete, CC-E (approved branch):**
> "Ask user: 'FLOW-[ID] ([name]) is `approved` but is affected by this flow's changes. Roll back to `pending_alignment`? (y/n)'"

**Evidence — ux-flow-complete Illegal transitions:**
> "approved → any status WITHOUT explicit user confirmation"

These are fully consistent. The state machine row's guard ("user confirms rollback") matches the CC-E branch logic and the illegal-transition block. No contradiction.

---

### 2.5 `reviewer` field inconsistency in review_history entries

Across the skills, several `review_history` entries specify `reviewer: Human` and several specify `reviewer: LLM`. The ones that say `reviewer: Human` for automated transitions (e.g., CC-C: "No cross-flow impacts detected" → `reviewer: Human`) appear to be mislabeled: when the AI triggers the transition based on impact analysis with no explicit human review of the flow, the reviewer is the LLM, not a human.

**Evidence — ux-flow-complete, CC-C:**
> `notes: "Approved by user. No cross-flow impacts detected."` with `reviewer: Human`

The notes say "Approved by user" which implies the human explicitly reviewed and approved — this is the correct framing (the user said "content complete"). But the transition in CC-C happens because no sibling impacts were found, not because the user reviewed the flow content again. The user's "content complete" signal at Step 12 of ux-flow-draft is the human review event; CC-C is the automated consequence. Using `reviewer: Human` here conflates the human's earlier "content complete" signal with the AI's automated decision to approve. This could cause confusion in audit trails.

**Verdict**: Minor semantic issue. Not a functional bug but affects traceability.

#### Step E: User signals "content complete FLOW-009"

This step is not explicitly in the walkthrough scenario but is implied — FLOW-009 must reach `aligned` before joint approval can proceed.

**Dispatcher**: "content complete FLOW-009" → ux-flow-complete.

**ux-flow-complete**:

**CC-0**: FLOW-009 has `approval_cluster: [flow_010_name]` already set → "This flow will go to `aligned` (not `approved`) regardless of what the impact analysis finds." ✅ Correct.

**CC-A/CC-B**: Impact analysis runs. If FLOW-009's changes (incorporating FLOW-010's impacts) create no new third-party impacts → proceeds to CC-D.

**CC-D**: Sets FLOW-009 to `aligned`. Sets `approval_cluster: [flow_010_name]` again (already set — no change in effect).

   **MINOR ISSUE**: CC-D always sets `approval_cluster: [source_flow_name_snake_case]` — using the *current* flow's name as the cluster value. Since FLOW-009 already has `approval_cluster: [flow_010_name]`, this would *overwrite* it with `[flow_009_name]`. This breaks cluster coherence: now FLOW-009 points to a different cluster value than FLOW-010.

   **Evidence**: CC-D says "Set `approval_cluster: [source_flow_name_snake_case]` in flow.md YAML frontmatter" where source = the current flow being processed (FLOW-009 in this case). The instruction does not check whether approval_cluster is already set and skip overwriting.

   **Verdict**: Bug. CC-D should have a guard: "If `approval_cluster` is not already set in the YAML, set `approval_cluster: [source_flow_name_snake_case]`. If it is already set, preserve the existing value."

**CC-C**: Not reached (impacts exist — at minimum, FLOW-010 is in the cluster and was already identified).

   Wait — CC-C is only reached if *no* impacts are found. FLOW-010 is a known sibling. But FLOW-010 is in the candidate list. CC-B will analyze FLOW-010. FLOW-010 is `aligned` — it was already processed. Would Sonnet find an impact on FLOW-010? Possibly yes (FLOW-009's changes incorporate FLOW-010's impacts, which means FLOW-009 changed). If Sonnet says `impact: yes` on FLOW-010, CC-E would process FLOW-010 as an impacted sibling — but FLOW-010 is already `aligned`, not `approved`, so it would be rolled back to `pending_alignment` without user confirmation.

   This is an infinite regress risk: FLOW-009 impacts FLOW-010, FLOW-010 rolls back to `pending_alignment`, user must do another CONTINUE on FLOW-010, then another content-complete, then they're both `aligned` again. The system doesn't cap this.

   **CC-0 is the intended guard here**: Because FLOW-010 already has `approval_cluster` set, when FLOW-010's content-complete runs, it will go to `aligned` regardless. But CC-E in ux-flow-complete (which processes FLOW-009's content-complete) does not have a similar guard — it will roll FLOW-010 back to `pending_alignment` even though FLOW-010 is a cluster member.

   **Gap**: The system needs a rule in CC-E: "If the impacted sibling is already a member of the same `approval_cluster` (i.e., its `approval_cluster` value matches the current flow's `approval_cluster`), do NOT roll it back — it is already in the cluster and will be handled by joint approval."

**CC-G**: Commits and outputs.

**State after Step E**:
- FLOW-009: `aligned` (if CC-D bug fixed), `approval_cluster` correct.
- FLOW-010: `aligned` (if no infinite-regress problem).

## 4. Gaps

### 4.1 Cluster merging not defined

If a new FLOW-011 is created and reaches content-complete, and its impact analysis finds both FLOW-009 and FLOW-010 (already a cluster), there is no instruction for what to do. The system would assign FLOW-011 its own `approval_cluster: flow_011_name` and the existing cluster would remain at `approval_cluster: flow_010_name`. Now there are two clusters that overlap in membership. Joint approval would need to include all three flows but the system has no way to detect cluster membership automatically from the FLOW_INDEX or YAML.

**Evidence**: CC-D sets `approval_cluster: [source_flow_name_snake_case]` unconditionally. CC-E sets the same value on impacted siblings. If a sibling already has a different `approval_cluster`, the existing value is overwritten. The skill has no merge or union operation.

**Recommendation**: Add a cluster merging rule to CC-E: "If the impacted sibling already has `approval_cluster` set to a different value, merge the clusters: set both flows' `approval_cluster` to the lexicographically-first value (for determinism) and note the merge in the output."

---

### 4.2 No precondition check in ux-flow-complete for `in_review` status

**Evidence**: ux-flow-complete CC-0 checks for existing `approval_cluster` but does not verify that the flow is currently `in_review`. The state machine says the trigger `content complete` is only valid from `in_review`. If a user accidentally signals "content complete FLOW-010" when FLOW-010 is in `draft` (due to the Step B bug), the skill proceeds without error.

**Recommendation**: Add at the top of CC-0 (before the cluster check): "Verify the flow's current `review_status` is `in_review`. If not, block: 'FLOW-[ID] is [status], not in_review. Run a CONTINUE pass first to advance to in_review.'"

---

### 4.3 No instruction for invoking ux-flow-draft directly (bypassing dispatcher)

**Evidence**: ux-flow-draft opens with "The dispatcher (`ux-create-flow`) has already determined the mode (NEW or CONTINUE) — do not re-run mode detection." But the skill then says "Check whether this is NEW (no existing flow.md) or CONTINUE (flow.md exists)." — it performs mode detection anyway. The opening disclaimer is misleading: it implies mode detection is already done by the dispatcher and handed off, but the sub-skill re-detects mode from file system state.

This is fine functionally (re-detection is correct), but the opening disclaimer could cause an AI to skip the mode check under the mistaken belief it's unnecessary.

**Recommendation**: Replace the opening disclaimer with: "The dispatcher has already determined the mode and invoked this skill. Re-confirm mode from file system state: NEW (no existing flow.md) or CONTINUE (flow.md exists). NEW → run Steps 1–5 then Step 6. CONTINUE → run Context Loading then Step 6."

---

### 4.4 CONTINUE mode does not specify what "feedback files" means when no task folder exists

**Evidence**: ux-flow-draft CONTINUE mode item 2: "Feedback files (from task's `user_feedback/` folder or user-provided path)"

If the user iterates a flow without a formal task folder (e.g., they just say "continue FLOW-010" in a new session), there is no `user_feedback/` folder to read. The skill says "or user-provided path" but does not instruct the AI what to do if neither source exists (no task folder, no user-provided path, no context from current session).

**Recommendation**: Add fallback: "If no feedback files are found and the user has not provided feedback in the current session, ask: 'What changes or feedback would you like to incorporate in this iteration?'"

---

### 4.5 No explicit instruction for the "user answered yes to Step 12 approval question" path in mode detection

**Evidence**: ux-create-flow mode detection table, second row:
> `"content complete FLOW-NNN" / "I'm done with FLOW-NNN" / "approve FLOW-NNN" (single flow) / user answered "yes" to Step 12 approval question | CONTENT COMPLETE | ux-flow-complete`

Step 12 of ux-flow-draft does not include an approval question. The output template for new mode says "Signal content complete when satisfied" and "provide feedback or signal content complete" — it does not include a y/n question for the user to say "yes" to.

This "Step 12 approval question" appears to refer to something that existed in the original monolith but was not carried into the new Step 12 output templates.

**Recommendation**: Either add a closing y/n question to Step 12 output ("Are you satisfied with this flow and ready to proceed to content-complete? (y/n)") or remove the "user answered yes to Step 12 approval question" signal from the mode detection table, as it is currently unimplemented.

---

### 4.6 JA-C does not specify task creation location consistently

**Evidence**: ux-flow-approve JA-C:
> "For each external flow with `impact: yes`: apply the same Case A/B logic from CC-E/CC-F in ux-flow-complete"

CC-F specifies a concrete task location: `requirements_tasks/process/AI_rules/requirements_management/user_needs_content/user_flows/tasks/[today]_impl_align_[sibling_name]_with_[source_name]/`

But in JA-C, the "source" is ambiguous — is it the last flow to reach aligned, or the cluster as a whole? The naming convention `align_[sibling]_with_[source]` breaks down for cluster-level impacts.

**Recommendation**: Specify: "Use `[today]_impl_align_[sibling_name]_with_cluster_[cluster_name]/` as the task folder name when the impact originates from a joint approval (cluster context)."

## 5. Redundancies

### 5.1 Guard rails in dispatcher are runtime-redundant once sub-skills are active

The Guard Rails section of ux-create-flow contains four rules. Three of them are also present as "Illegal transitions" blocks in ux-flow-complete and ux-flow-approve. Once the dispatcher dispatches to a sub-skill, the dispatcher's guard rails are no longer in the active execution context. The sub-skills enforce these rules at the correct enforcement point.

This redundancy is acceptable as documentation for the dispatcher's *intent*, but should be labeled as such. Currently they read as runtime enforcement, which they are not.

**Note**: This is intentional belt-and-suspenders, per plan. The redundancy is acknowledged but minor.

---

### 5.2 "Brevity rule" stated in Step 6 is partially restated in Key Principles

**Evidence**: ux-flow-draft Step 6 (Generate or Improve):
> "Brevity rule (applies to both modes): Write as concisely as possible without omitting content..."

**Evidence**: ux-flow-draft Key Principles:
> "Brevity: Flow files must be as short as possible while remaining complete. No redundancy, no restating what is already clear. Omit no content — but use fewer words."

These say the same thing. Step 6 additionally says "In Continue mode, actively look for redundancy introduced by previous iterations and remove it while incorporating new feedback" — the more useful version. The Key Principles version is a shorter restatement.

**Recommendation**: Remove the Key Principles brevity bullet and keep only the Step 6 version, which is more complete. Or merge: add the "actively remove redundancy in Continue mode" clause to Key Principles.

### 5.3 Review_history entry format repeated across CC-C, CC-D, CC-E, JA-B

Each step that transitions status includes a review_history entry with `seq: [N], from: ..., to: ..., reviewer: ..., notes: "..."`. This is correct and necessary — each entry is unique. However, the `seq: [N]` placeholder is repeated identically across all entries with no instruction on how to compute N.

**Evidence**: Multiple steps say "seq: [N]" or "seq: [existing entries count + 1]" — but only ux-flow-draft's CONTINUE mode status reset says "seq: [existing entries count + 1]". The other skills just say `seq: [N]`.

**Recommendation**: In each skill, standardize the seq instruction to: `seq: [existing review_history entries count + 1]` (i.e., read the current review_history array length before writing the new entry).

## Open Questions

1. **Cluster identity**: Should `approval_cluster` be keyed to a flow *name* (snake_case) or a flow *ID* (FLOW-NNN)? Using ID is more stable (names can change); using name is more readable. The current system uses name. If a flow is renamed, all cluster members need updating.

2. **Multiple rounds of alignment**: Can FLOW-009 and FLOW-010 loop through `aligned → pending_alignment → in_review → aligned` indefinitely? The system has no convergence guarantee. In practice, good impact descriptions in `## Pending Impacts` should prevent re-introducing the same conflict, but there is no documented escape hatch for "we've iterated enough — accept residual divergence."

3. **Who reads ux-flow-draft vs. ux-create-flow in context?**: When the user invokes ux-create-flow, both ux-create-flow and ux-flow-draft will be in the context window (Claude loads the invoked skill). When ux-create-flow dispatches to ux-flow-draft, does ux-flow-draft load as a second skill context? Or does the dispatcher simply instruct the AI to behave according to ux-flow-draft's rules? If the former, the 9 READMEs + full ux-flow-draft content may exhaust context. If the latter, ux-flow-draft's content must fit in a single context load. This is a platform-level question, not a skill design question — but it affects whether the MANDATORY README reading instruction will actually run.

4. **`approved` in CONTINUE mode**: The status reset instruction in CONTINUE mode resets `approved → in_review`. But the state machine does not have an `approved → in_review` row. If an `approved` flow is iterated via CONTINUE, the dispatcher will detect the FLOW-ID and confirm CONTINUE mode — then ux-flow-draft resets status to `in_review`. This seems correct (user wants to revise an approved flow), but it bypasses the "never modify without explicit confirmation" guard rail from the dispatcher. The CONTINUE confirmation at the dispatcher level ("Flow ID provided → confirm with user") is the guard, but it's a weak one for approved flows (one confirmation applies to both routine updates and approved-flow rollbacks).

## Summary

The refactor is well-executed and achieves its stated goals. The state machine extraction and skill split are clean, the natural boundaries were correctly identified, and the resulting skills are significantly more navigable than the 583-line monolith. The main systemic risk is a cluster coherence problem in CC-D/CC-E that can cause incorrect `approval_cluster` overwriting and infinite-regress rollbacks between cluster members. Two additional bugs (draft/pending_alignment not reset at CONTINUE start, missing precondition check in ux-flow-complete) are smaller in impact but should be fixed before the system handles real production flows. All ten improvement suggestions above are actionable with targeted, localized edits — no architectural changes are needed.
