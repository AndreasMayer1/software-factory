# Opus Plan: Refactor ux-create-flow — Explicit State Machine + Skill Split

## Objective

1. Extract the implicit flow state machine into a single explicit reference table (eliminates scattered, error-prone state logic)
2. Split the 583-line monolith into 4 focused skills (dispatcher + 3 mode-specific skills)

---

## Analysis Summary

**Why the current skill causes errors:**
- State transitions are described in prose scattered across 4 sections — an AI working on Step CC-E has to mentally reconstruct the full state graph from memory
- Guards (e.g. "if sibling is `approved` vs `aligned` vs `draft`") are buried in nested bullet lists with no single source of truth
- The "roll back on sibling impact" logic is duplicated between CC-E and JA-C with slight wording differences

**Natural split boundaries:**
| Mode | Lines | Trigger | Shares with others? |
|------|-------|---------|---------------------|
| NEW + CONTINUE | ~230 | User invokes with flow name/ID | Steps 6-12 are shared between the two |
| CONTENT COMPLETE | ~150 | "content complete FLOW-NNN" | Nothing — fully self-contained |
| JOINT APPROVE | ~60 | "jointly approve FLOW-A, FLOW-B" | Nothing — fully self-contained |
| Mode detection (Step 0) | ~30 | Entry point | Calls all others |

**Key constraint**: NEW and CONTINUE both converge at Step 6 (write via Opus) — they must stay in the same skill to avoid duplicating steps 6-12.

## Explicit State Machine

This table goes into `ux-create-flow` (dispatcher) as the canonical reference. All four mode skills read it as ground truth.

```
## Flow Status State Machine

| From status        | Trigger                          | Guard                          | To status          | Skill that executes    |
|--------------------|----------------------------------|--------------------------------|--------------------|------------------------|
| (none)             | NEW mode                         | —                              | draft              | ux-flow-draft          |
| draft / in_review  | CONTINUE                         | —                              | in_review          | ux-flow-draft          |
| pending_alignment  | CONTINUE                         | —                              | in_review          | ux-flow-draft          |
| in_review          | content complete                 | no sibling impacts             | approved           | ux-flow-complete       |
| in_review          | content complete                 | sibling impacts exist          | aligned            | ux-flow-complete       |
| aligned            | sibling CONTINUE identifies impact | —                            | pending_alignment  | ux-flow-complete       |
| draft/in_review/   | sibling CONTINUE identifies impact | —                            | pending_alignment  | ux-flow-complete       |
| pending_alignment  |                                  |                                |                    |                        |
| approved           | sibling CONTINUE identifies impact | user confirms rollback       | pending_alignment  | ux-flow-complete       |
| approved           | sibling CONTINUE identifies impact | user declines rollback       | approved (no change)| ux-flow-complete      |
| aligned            | joint approve                    | all cluster flows aligned,     | approved           | ux-flow-approve        |
|                    |                                  | no Pending Impacts remain      |                    |                        |

**Illegal transitions** (block and report):
- approved → any status WITHOUT explicit user confirmation
- aligned → approved WITHOUT joint approve (never direct-approve an aligned flow)
- any status → approved while ## Pending Impacts section exists in flow.md
```

## Risks

**Risk 1**: Splitting introduces context gaps — sub-skill doesn't have full picture.
- Mitigation: Each sub-skill opens with its own role statement that names its scope. The dispatcher passes no runtime state — the sub-skill re-reads what it needs.

**Risk 2**: "Shared steps 6-12" in ux-flow-draft are currently written for NEW mode only in some places (e.g. Step 7 says "Continue mode: skip if scenarios unchanged"). This conditional logic must be preserved exactly.
- Mitigation: Copy steps 6-12 verbatim first, then only change the outer frame (skill name, opening line). Do not rewrite the step logic.

**Risk 3**: The state machine table has 9 rows with subtle guard conditions. If the table is written incorrectly, it becomes the new source of bugs.
- Mitigation: Derive every row directly from the existing skill text, cross-check against README_12, add "Illegal transitions" section explicitly.
