## Changes to ui-create-scribble

All changes go through `claude-modify-skill`.

### Change 1: Phase 1 — Flow context block (pre-spawn)

**Current**: Passes full flow as `flow_context` (step list + step numbers). No scoping. No implementation_notes.

**New**:
- Extract `steps[]` from `implements_flows[].steps` in requirements.md YAML → screen generation is restricted to these steps only.
- Pass full flow as read-only context (Domain Concepts, exception paths, channel model available to Phase 1 agent).
- Check flow folder for `implementation_notes.md` → pass to Phase 1 agent if present.
- Require `exception_id` in flow_positions entries for exception-path screens.

### Change 2: Phase 1 MUST-DO list — Information constraints step (pre-generation)

**Add as step 0** (before reading requirements): Phase 1 agent reads flow's Domain Concepts section + any requirement section describing channel/system model. Derives explicit "unavailable information" list. Each generated screen state must be consistent with this list.

**Add as step 1b**: If `implementation_notes.md` was passed: read it before designing screens; treat its constraints as authoritative (overrides design choices that seem reasonable from flow alone).

**Update step 3**: Note that `flow_scope` restricts generation — only generate screens for the `flow_scope` steps.

**Add to step 13** (component mapping): When a domain class exists in `lib/features/` for the feature's core logic, reference it by full class name in the component mapping blocks for screens that depend on it.

### Change 3: Phase 2 — Implementation notes read + Extended checklist

**Add to Phase 2 pre-spawn**: Check flow folder for `implementation_notes.md` → pass to Phase 2 agent if present.

**Extend checklist** with items 6–8:
- 6: Information-model consistency — for every non-trivial state panel, is the required data available on this app side?
- 7: Exception paths — every exception path in the parent flow with a distinct UI state → at least one screen or annotated variant? (exception_id in flow_positions required)
- 8: Domain Concepts behavioral constraints — consent prompts, timing rules, opt-in flows → visible as screen states or annotations?

**Add YAGNI gate sub-step** (after states generated, before writing final scribble):
- Gate 1 (inclusion): evidence that (a) state can occur AND (b) system has data to render it?
  - Fail → `<!-- state-deferred: [reason] reopen-when: [trigger] -->`
- Gate 2 (shape): simpler variant satisfies same evidence?
  - Yes → `<!-- state-simplify: [simpler variant] -->`
- User override removes comment; cost is made visible, not vetoed.

### Change 4: Phase 2 — Component auto-promotion

**After Phase 2 completes** (not as part of Phase 1 step 13 tagging, but as a post-review action):
Scan all component-candidate tags across screens. Any candidate appearing in ≥3 screens with identical usage-site pattern → auto-promote to `_scribble_components/` with `status: provisional`. Include promotion list in Phase 3 summary for developer confirmation.
