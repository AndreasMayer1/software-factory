## Gate Definition (re-authored in our voice)

### Gate 1 — Inclusion (evidence test)
Any committed item (AC, scope line, planned feature) must cite ≥ 1 piece of real evidence:
- (a) user-described need
- (b) named direct dependency
- (c) existing code path that breaks without it
- (d) regulation demonstrably in effect today
- (e) documented incident / fired alert / measured metric

Hypotheticals do not qualify: "for future flexibility", "best practice says", "when we scale",
"for completeness", "while we're here".

### Gate 2 — Shape (simpler-version test)
When evidence justifies inclusion, prefer the strictly simpler version that satisfies
the same evidence. A direct function beats an abstraction. A flag beats a config system.

### Deferred (YAGNI) format (standard — used in all three skills)
```markdown
## Deferred (YAGNI)
*(omit section entirely when no items are deferred)*

### {item name}
**Why deferred:** [missing evidence — what would justify inclusion]
**Reopen when:** [named trigger — specific future event providing evidence]
**Source:** [where the hypothetical originated]
```

### User override
Any single deferral can be overridden. Document the override rationale inline (not in a
separate section). The gate makes cost visible; it does not veto the user.
