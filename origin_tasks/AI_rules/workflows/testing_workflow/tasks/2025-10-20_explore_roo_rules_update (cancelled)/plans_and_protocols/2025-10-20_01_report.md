Purpose:
- Incorporate the user's annotations (translated) and replace the previously-proposed simple "one code subtask per test file" strategy with a hierarchical orchestrator pattern that prevents context exhaustion at all orchestration levels while keeping test implementation responsibilities well scoped.

User annotations (translated summary):
- The user requires that a subtask should handle at most a single test file; better: split a test file into multiple parts and have one subtask per part to keep each subtask's context small.
- Creating many subtasks directly from the outer orchestrator will fill the outer orchestrator's context. Instead the outer orchestrator should create a single "testing orchestrator" subtask; this testing orchestrator creates "test file orchestrator" subtasks (one per test file). Each "test file orchestrator" will use architect-mode subtasks to plan splitting a test file and then spawn code-mode subtasks to implement each part.
- Clear naming and role conventions are required.

Decision / proposed approach (high-level):
- Use a three-level orchestration hierarchy for test work:
  1. Outer Orchestrator (existing orchestrator task) — creates and monitors the overall feature implementation and creates a single Testing Orchestrator subtask when tests are required.
  2. Testing Orchestrator (orchestrator-mode subtask) — owns the test program for the feature, lists test files, schedules Test File Orchestrators, aggregates results and runs Phase 3 verification.
  3. Test File Orchestrator (orchestrator-mode subtask per test file) — for each test file: create an Architect subtask to split and design the test, then spawn Code subtasks for each part implementation. Collect commits and produce a per-file protocol.

Why this solves the context issue:
- The outer orchestrator delegates test coordination to the Testing Orchestrator; it only needs to start one subtask and then can continue other work. The Testing Orchestrator's context holds the list of test files and orchestrates their per-file orchestrators. Each Test File Orchestrator only sees the small plan for its single test file and spawns small architect/code subtasks as needed. This keeps contexts small at every level.

Naming conventions (suggested)
- Testing Orchestrator: testing_orchestrator_YYYYMMDD_<feature>
- Test File Orchestrator: testfile_orchestrator_YYYYMMDD_<feature>_<fileId>
- Architect plan for a test file: arch_test_plan_YYYYMMDD_<feature>_<fileId>
- Code subtask implementing part: impl_test_part_YYYYMMDD_<feature>_<fileId>_<partIdx>
- Flakiness probe: impl_flakiness_probe_YYYYMMDD_<feature>_<fileId>

Example workflow (step-by-step)
1. Outer Orchestrator (feature implementer) defines Scope of Work and creates `testing_orchestrator_2025-10-20_plan_templates`.
2. Testing Orchestrator enumerates required test files and creates one `testfile_orchestrator` per file.
3. Test File Orchestrator creates an Architect subtask `arch_test_plan_...` to split the test file into parts and produce:
   - A precise checklist of asserts and test helpers
   - Mocks and DI registration notes
   - Environment commands (e.g., integration test `--plain-name` string and `-d windows`)
   - Acceptance criteria and run commands
4. Test File Orchestrator spawns `impl_test_part_...` code subtasks, one per part (small, focused).
5. Each code subtask creates or updates exactly one test file part (or helper), stages and commits the changes with a descriptive message, and writes a short protocol file in the task's `plans_and_protocols`.
6. After all parts are implemented, Testing Orchestrator runs Phase 3 verification (targeted tests) and aggregates results. If a test fails or cannot be implemented, Testing Orchestrator creates an architect `explore_test_blocker_...` task and stops escalation for that test file.

Flakiness & escalation (refined)
- If intermittent failures are detected during Phase 3 verification, Testing Orchestrator triggers `impl_flakiness_probe_...` code subtasks tasked explicitly to run the failing test multiple times and collect logs. If the probe confirms non-determinism, Testing Orchestrator creates `explore_test_blocker_...` (architect) for root-cause analysis and mitigation recommendations.

Architect <-> Code boundary (important)
- Architect subtasks must produce explicit, low-level instructions (step-by-step) for code subtasks: exact finders to use (byKey/text), expected widget states, sample mock responses, required DI changes, and a short list of acceptance assertions. This is necessary because code mode struggles with writing robust tests without precise instructions.

Verification & acceptance criteria for the roo rules changes
1. New/updated `.roo` rules exist in a branch and include the Testing Orchestrator pattern and lifecycle documentation.
2. A pilot run is executed for one feature where:
   - Outer Orchestrator creates one Testing Orchestrator.
   - Testing Orchestrator creates per-file Test File Orchestrators.
   - Each Test File Orchestrator produces architect plans and code subtasks for at least one test file part, which are committed.
   - Testing Orchestrator runs targeted verification and either marks tests as passing or creates an `explore_test_blocker_...` with a protocol.
3. The pilot's protocol includes metrics: number of subtasks created per level, number of architect directives, and test implementation success rate.
