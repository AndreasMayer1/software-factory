Goal:
- Incorporate the user's annotations and ensure the bottom-level iterative test workflow remains unchanged: Guidelines -> run test -> switch to architect -> plan -> switch to code -> implement -> end (no re-run inside subtask).

Key decisions:
- Use hierarchical orchestrator pattern: Outer Orchestrator → Testing Orchestrator → Test File Orchestrator → Architect plans → Code part subtasks.
- Preserve iterative single-subtask debug cycle at the code-subtask / architect boundaries.

Definitions and naming conventions:
- Outer Orchestrator: existing task owning feature implementation.
- Testing Orchestrator: testing_orchestrator_YYYYMMDD_<feature>
- Test File Orchestrator: testfile_orchestrator_YYYYMMDD_<feature>_<fileId>
- Architect plan for a test file: arch_test_plan_YYYYMMDD_<feature>_<fileId>
- Code subtask implementing a part: impl_test_part_YYYYMMDD_<feature>_<fileId>_<partIdx>
- Flakiness probe: impl_flakiness_probe_YYYYMMDD_<feature>_<fileId>

High-level workflow (per feature):
1. Outer Orchestrator creates a single Testing Orchestrator. (one subtask only)
2. Testing Orchestrator enumerates required test files and creates one Test File Orchestrator per test file.
3. Test File Orchestrator creates an Architect subtask `arch_test_plan_...` to:
   - read guidelines
   - produce a split of the test file into small parts
   - list required mocks, DI changes, helpers, and exact acceptance assertions
   - produce run commands (integration: plain-name + -d windows) and environment notes
   - define acceptance criteria per part
4. After arch_test_plan completes, Test File Orchestrator spawns one `impl_test_part_...` code subtask per part.
5. Each `impl_test_part` follows the preserved iterative single-subtask debugging cycle:
   - Start in `code` mode and read the testing guidelines.
   - Stay in `code` mode and run the relevant failing test(s) to capture full error output and stack traces (or reproduce the issue).
   - Immediately switch to `architect` mode with the captured error output and ask for a precise plan describing the exact code/test changes (finders to use, expected widget states, mock responses, DI notes).
   - Switch back to `code` mode and implement the architect's step-by-step plan. Stage and commit the changes with a descriptive message referencing the task folder.
   - Do NOT re-run the failing test inside the `impl_test_part` after the commit. End the subtask. (Parent Testing Orchestrator will perform verification.)

Why preserve this iterative cycle at the leaf level?
- Code mode is unreliable at deciding test adjustments without explicit guidance. Let it capture precise failure output but require Architect to produce exact, low-level instructions the code executor must implement.
- This keeps changes predictable, reproducible, and prevents code-mode from chasing failures without plan-level oversight.

Flakiness and escalation
- Testing Orchestrator runs Phase 3 verification (targeted tests) after all `impl_test_part` subtasks for a file complete.
- If verification shows intermittent failures, Testing Orchestrator launches `impl_flakiness_probe_...` code subtasks to collect logs by running the failing test multiple times; it then creates an `explore_test_blocker_...` architect task if flakiness is confirmed.
- If a code subtask reports "cannot implement" (e.g., license issue, missing design info), Test File Orchestrator creates `explore_test_blocker_...` (architect) to analyze and propose remediation.

4. Phase 3 verification run by Testing Orchestrator either passes or produces `explore_test_blocker_...` protocols.
