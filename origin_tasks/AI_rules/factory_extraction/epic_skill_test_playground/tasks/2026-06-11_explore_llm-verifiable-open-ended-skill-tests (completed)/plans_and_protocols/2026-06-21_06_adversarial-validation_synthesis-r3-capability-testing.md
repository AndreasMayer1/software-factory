## Major Findings

**M1: The same-turn-baseline discipline is broken by sequential-tier constraint on every tight-window session**

- **Challenged claim:** §4 constraint #6 — "on `pro`/`free`, judge/run leaves spawn sequentially." §7.1 L3 (Iteration 2 resolution) — "execute both versions fresh, now, under the same current model" (citing "skill-creator's own same-turn-baseline discipline").
- **Counter-evidence:** The skill-creator SKILL.md at line: "For each test case, spawn two subagents in the same turn — one with the skill, one without. This is important: don't spawn the with-skill runs first and then come back for baselines later." The synthesis cites this discipline to justify model-matched comparison, then explicitly requires sequential spawning on `pro`/`free`. Sequential spawning introduces a time gap between the old-version and new-version runs, during which model state or temperature sampling can diverge slightly (even if the model version is the same). The entire rationale for same-turn spawning is to minimize this gap. The synthesis adopts the conclusion (model-matched comparison is valid) while violating the precondition (same-turn execution).
- **Unhandled edge case:** On a `pro` tier session (the most common solo-developer tier for this PERSONA-015 factory), the L3 comparison is sequential by mandate. If the old-version run takes 8 minutes and the new-version run follows, any transient model behavior change or API-side temperature drift between runs is attributed to the version difference. The "attributable to version alone" claim in §7.1 is weakened to "probably attributable to version, modulo sequential sampling variance."
- **Flawed assumption:** Same-turn discipline and sequential-tier constraint are presented as simultaneously satisfiable. They are not.
- **Falsification test:** On a `pro` session, spawn old-version run, wait for completion, then spawn new-version run. Record whether the comparator ever assigns a "won" verdict on the basis of a single-run sequential comparison. If it does, the verdict carries unquantified temporal variance. No mitigation is specified in the synthesis for this case.
- **Severity:** MAJOR — The model-drift resolution (the synthesis's answer to blindspot G3) is the central technical novelty of Iteration 2. The sequential-tier constraint undermines it in the exact deployment context (solo developer, pro tier) the factory primarily targets.

The calibration oracle the synthesis proposes wiring L2 judges to is a specified but unimplemented feature.

- **Flawed assumption:** The synthesis treats the Human Judgment Register as a live, queryable calibration source. It is a ratified catalog (types layer exists at `.factory/registry/human_judgment_register.yaml`) over an unreachable corpus with no query interface.
- **Falsification test:** `find scripts/ -name "*.py" | xargs grep -l "human_judgment\|HJR\|judgment_register"` — returns no results. Already in hand.
- **Severity:** MAJOR — The resolution of blindspot B1 (judge has no oracle) is the synthesis's most structurally important addition over r2. **M3: The behavioural-contract tier (CLAUDE.md battery) has no cost/feasibility analysis and conflicts with depth-1 topology**

- **Challenged claim:** §7.8 — "Fixture = a representative task battery on the harness (e.g. 'do this code task', 'do this requ-explore', 'resume after a simulated rate-limit')... The session owns all spawns; every spawned agent is a non-spawning leaf... This is the single highest-value tier for time-saved."
- **Counter-evidence:** CLAUDE.md §2 ("Depth-1 spawning: agents do not spawn agents. The session owns all spawns.") The behavioural-contract test requires the session to run a "task battery" that exercises the orchestrator's behaviour across multiple capability-chain runs. A complete task battery (code task + requ-explore + resume-after-rate-limit) would involve the session: deploying the CLAUDE.md under test, running multiple `claude` child sessions against it (each child session exercises one chain), and collecting transcripts. Each child session is itself a Claude Code session — not a depth-1 agent leaf. Running child Claude Code sessions is what TASK-PROC-066-03 calls `ccs web '<task>' --dangerously-skip-permissions`, which the TASK-PROC-066-03 synthesis explicitly flagged as having open design questions about scoped execution. The depth-1 topology applies only to agents spawned within a session via the Agent tool; a child `claude` CLI process is a different mechanism entirely and is described as "forbidden" for nested agent spawning in CLAUDE.md.
- **Unhandled edge case:** If a CLAUDE.md battery test requires running three capability chains to observe seam behavior, and each chain is a full Claude Code session, the test is not a depth-1 leaf topology — it is a nested CLI invocation. The synthesis asserts this "collapses into one mechanism" with G1+G2 without acknowledging that the mechanism requires nested sessions, which CLAUDE.md prohibits ("shelling out to a nested `claude` CLI session is forbidden").
- **Flawed assumption:** The battery test at the behavioural-contract tier silently assumes the session can orchestrate child Claude Code sessions without violating the depth-1 constraint. This is the exact problem TASK-PROC-066-03 was tasked to solve and did not.
- **Falsification test:** Read CLAUDE.md §2: "shelling out to a nested `claude` CLI session is forbidden — it compounds the work-loss below and needs bespoke instructions." The CLAUDE.md battery test cannot run within the stated topology constraints. The synthesis does not acknowledge this contradiction.
- **Severity:** MAJOR — The "single highest-value tier for time-saved" (§4 #8, §7.8) cannot be implemented within the factory's own stated topology rules without violating CLAUDE.md. The synthesis presents this tier as an elegant collapse of G1+G2 without addressing that it requires the one mechanism CLAUDE.md forbids.

**M4: The discriminating-check rule has no automated enforcement path and is purely advisory**

- **Challenged claim:** §7.1 L1/L2 — "every L1/L2 check must be one a worse baseline would actually fail — non-discriminating checks are pruned... the discriminating-check rule... antidote to vacuous open-ended tests."
- **Counter-evidence:** The skill-creator `analyzer.md` performs pattern analysis *after running the benchmark* across with/without configurations. In the synthesis's model, there is no "without" configuration — the comparison is old-vs-new. To know whether a check is discriminating, you must run it against both old and new versions and see if old fails it. But the discriminating-check rule is supposed to govern which checks are *included in the descriptor* at authoring time. The synthesis conflates two things: (a) the discriminating-check rule as a design principle at descriptor-authoring time, and (b) the analyzer's post-hoc pattern detection after a benchmark run. The descriptor is authored once; the benchmark runs on modify. There is no feedback loop from benchmark results back to descriptor authoring until a human reviews the `eval_feedback` and manually updates the descriptor.
- **Unhandled edge case:** A descriptor is authored for capability X. All its L1 checks happen to pass on both old and new versions of X. The synthesis says non-discriminating checks should be "pruned" — but pruning requires knowing they are non-discriminating, which requires running the old-vs-new comparison, which requires the deploy/run/reset mechanism (see C3). So the discriminating-check rule is practically enforceable only retroactively, not at descriptor-authoring time.
- **Flawed assumption:** "Every check must be discriminating" is presented as a build-time design principle. In practice it is a post-hoc maintenance signal, executable only after the infrastructure from C3 exists.
- **Severity:** MAJOR — The primary quality discipline of the L2 rubric is stated as an upfront authoring constraint but is actually a retroactive maintenance action.

## Residual Risks if Acted Upon As-Is

- The 90 EGP floor-contract violations (including the proposed first-instance capability ideation-start and the meta-skills to be extended) mean the first implementation task will immediately encounter a precondition violation: the "oracle the floor contract promises" cannot be built because no floor contracts declare the relevant archetypes.
- The model-pinned history ledger (Iteration 2's G3 resolution) requires adding `executor_model`/`judge_model` to a schema that the synthesis proposes to selectively-adopt from upstream. Adding non-upstream fields to a selectively-adopted schema breaks the adoption contract and creates a maintenance burden the synthesis does not acknowledge.
- The CLAUDE.md battery test (§7.8, the "highest-value tier") cannot run within the depth-1 topology stated in CLAUDE.md §2 without nested CLI session invocations, which CLAUDE.md explicitly prohibits. Building this tier requires either changing CLAUDE.md's topology rules or accepting that the highest-value tier cannot be automated.
- The Human Judgment Register calibration loop is specified as a live queryable corpus but the query interface (AC-04) is not implemented. Authors of L2 rubric anchors will default to free-authoring, defeating the anchor-provenance resolution (D2 in Iteration 1).
- The test_harness_app does not mirror a real factory project structure (REQ-PROC-068 AC-01 is unchecked). Every descriptor path reference and fixture-library reference in the synthesis points at a directory layout that does not exist.
- Sequential execution on tight tiers makes the L3 old-vs-new comparison a single-sample sequential test, not a same-turn model-matched comparison. Regression verdicts on pro/free are noisier than the synthesis implies.
- D6 (recovery honesty) as a standard L2 dimension will produce vacuous passes in all non-collapse runs, violating the discriminating-check rule the synthesis uses to justify rubric quality.

## Bottom Line

The synthesis's conceptual architecture is coherent and its core insight (assert on process and internal consistency, anchored to the EGP archetype taxonomy as a quality spine) is the right framing for open-ended capability testing. The mechanism design is genuinely novel in its produce-vs-modify axis, the behavioural-contract tier, and the weighted-gate regression model. However, three of its claimed foundations are not real in the current codebase: the EGP floor contracts (90 violations including the primary example capability), the history.json model-tracking field (not in the upstream schema), and the deploy/run/reset execution substrate (design explicitly deferred in TASK-PROC-066-03, harness not yet structured). The requirement shape decision in §11 should be preceded by closing these three gaps, not followed by impl tasks that assume them closed. Treat this synthesis as a sound target architecture requiring three prerequisite corrections before its first impl task can be safely authored.
