# ANALYZE — Problem Structure, Criteria, Decomposition

## Scope & goal
Choose ONE coherent design across four coupled decisions so a legitimately-complete layer-derivation
chain (with a mandatory zero-authoring-pair span) **harvests**, the HIGH-consequence AC-18 abandonment
guarantee stays truthful, an un-harvestable spec fails **loudly at plan time**, and the LLM that authors
these specs is **taught** the model — with the per-task Option-A workaround retired.

## Topic class: composition (K=1)
Not a pick among atomic alternatives — the deliverable composes a decision for each sub-problem into one
design; the sub-problems constrain each other (the disposition SP-1 emits is the label SP-2 names, the
thing SP-3 simulates, and the rule SP-4 teaches).

## Central tension (the crux)
**Truthfulness vs harvestability.** The strict all-DONE oracle exists to stop harvesting an
*unfinished* derivation — a real guarantee we must not weaken. But it currently cannot tell apart:
- **"nothing to author here"** (a mandatory zero-pair span — legitimately, vacuously complete), from
- **"something to author, not done"** (a real ESCALATED blocker / silent under-finish).

Today both collapse to `ESCALATED` and both fail the oracle. The design must **split these two meanings**
apart at the primitive level, so the completion signal is *true* for each. IDEATION-003 already made this
move for reconciliation seams ("document, don't escalate"); this is the zero-pair extreme.

## Constraints / invariants any design must hold
- C1 — Do not weaken the real abandonment guarantee: a span with real authoring pairs that is not DONE
  must still block harvest and (when silent) classify abandoned. (HIGH EGP-F, AC-18.)
- C2 — Do not touch span-1 (real authoring) semantics or the harvest-diff behavior.
- C3 — Mechanism edits route through the governed layer-derivation scripts (`claude-write-script`);
  requirement edits via `requ-explore`; no hand-edited gates.
- C4 — The pre-flight must be reachable on `-start` AND resume (ADV-sg-06: a precondition checked only at
  start is skipped on resume).
- C5 — Authoring guidance lives in the skill/mechanism layer, NOT `doc/`.
- C6 — Truthfulness over convenience: never fake a DONE that hides a real under-finish.

## Rating criteria (authored here; gate-tunable — mid-run gate SKIPPED in automated mode)
Default spine (usefulness .22 / feasibility .18 / viability .12 / novelty .05 / risk .15) +
problem-specific **truthfulness .20** (the crux) + persona-derived **provider_teachability .08**
(PERSONA-015 App-Provider / maintaining role — the LLM spec-author must succeed unaided). No externally-
or empirically-verifiable criteria (all settle by reasoning against the read mechanism) → no evidence/spike
brokering this run.

## Decomposition (4 root sub-problems — coupled, mostly parallel)
- **SP-1 Fix locus**: (a) mechanism vacuous-DONE / distinct disposition; (b) oracle tolerance;
  (c) upstream plan-time no-unit-for-zero-pair-span. Feeds the label/contract the others consume.
- **SP-2 AC-18/19 clarification**: name SP-1's disposition; exclude degenerate no-op from
  abandonment/blame without weakening the real guarantee.
- **SP-3 Harvestability pre-flight**: contract + placement; plan-time loud failure; resume-reachable.
- **SP-4 Spec-authoring surface**: smallest artifact teaching span↔unit + degenerate-span rule;
  skill vs extend `layer-derivation-start` + governed template.

## Early design observations (feed divergence, not conclusions)
- The mechanism already has TWO adjacent primitives to build on: `screen_derivability` (empty
  required-elements, pre-authoring) and the `UnitStatus` enum. A **new disposition** (e.g. `VACUOUS` /
  `NO_OP` / `DEGENERATE`) that is oracle-satisfying-but-not-DONE cleanly splits the crux — vs overloading
  DONE (lies) or ESCALATED (mis-blames).
- "Don't emit a unit for a zero-pair span" (upstream) is attractive but collides with `plan_chain`'s
  `len(span_units)==len(spans)` invariant and the span-indexed chain-state; changing arity has wider blast
  radius than adding a disposition the oracle already iterates over.
- The pre-flight is naturally the **same computation** the oracle+planner already do — resolve spans,
  predict per-span disposition, predict the oracle verdict — run at plan time. Reuse, not new logic.
