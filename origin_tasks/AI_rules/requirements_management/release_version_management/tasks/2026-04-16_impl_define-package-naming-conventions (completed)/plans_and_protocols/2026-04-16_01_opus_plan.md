# Opus Plan: Define Package Naming Conventions

## Objective

Answer the six open questions about package granularity and naming, then update SEC-01 of REQ-PROC-034, the `requ-assign-packages` skill, and the `release-plan` skill with the new conventions. The end result must be concrete enough to unblock TASK-PROC-030-11 (epic_data_transfer package assignments).

## Analysis Summary

### Corpus Analysis — Existing Package Names (31 packages)

Examining all 31 current packages reveals emergent naming patterns:

| Pattern | Examples | Count |
|---------|----------|-------|
| `[Role] [Noun/Noun-Phrase]` | Client Data Entry, Client Roster, Client Plans Screen, Therapist Navigation, Therapist Plan Management | 9 |
| `[Domain-Noun] [Qualifier]` | Transfer Encryption, Storage Security, Data Visualization, Data Backup Restore, Plan Evaluation, Plan Preview, Plan Transfer Full | 10 |
| `[Adjective/Modifier] [Noun]` | Adaptive Scanner Settings, Reverse DataBeam Spike, Accessibility Standards, Accessibility Audit, UX Writing Guidelines, UX Polish | 6 |
| `[Noun] [Noun/Phrase]` | Data Transfer Core, Onboarding Flow, Safety Plan, Privacy Controls, GDPR Compliance, App Branding, Reminder Scheduling, Question Help Text | 8 |
| `[Abstract]` | Production Stabilization, Client Own Plans | 2 |

**Key observation**: The most unambiguous names use a **subject** (who/what) + **capability** (does what) structure. Names like "Client Data Entry" are instantly clear. Names like "Plan Evaluation" are slightly ambiguous (whose plan? evaluated by whom?). The collision example from the goal — "Print" appearing in multiple contexts — is resolved when the subject is explicit: "Client Data Print" vs. a hypothetical "Path Report Print".

### Answers to the Six Open Questions

**Q1: Cross-cutting (user-perspective) or scope-specific (per epic/flow)?**

Answer: **Scope-specific by default, with cross-cutting packages as an explicit exception type.** Evidence from the corpus: most packages are scope-specific (tied to one requirement or flow). Only "Production Stabilization", "UX Polish", and "Accessibility Audit" are genuinely cross-cutting. The naming convention should make this distinction visible through structure, not through separate category fields. A scope-specific package names its subject; a cross-cutting package names the concern.

**Q2: How to prevent packages from becoming too large?**

Answer: The existing size test in `release-plan` Action 4 (3-15 impl tasks) is the right mechanism. Adding a **split trigger** to the naming rules reinforces this: when a package exceeds 15 tasks, the name should be splittable along a capability boundary. Naming convention supports this by requiring that names be specific enough to split (e.g., "Data Transfer Core" can split into "QR Transfer Send" and "QR Transfer Receive"). Names that are too abstract ("Data Transfer") resist clean splitting.

**Q3: When does a set of ACs warrant a new package vs. joining an existing one?**

Answer: Three conditions for a new package (all must hold):
1. The ACs describe a capability that can ship independently of existing packages.
2. The capability has a distinct demo story (the existing "demo test" in release-plan).
3. Adding the ACs to an existing package would blur that package's scope description.

If any condition fails, join the existing package. This is already partially codified in the three tests in `release-plan` Action 4; the naming convention reinforces it by requiring that adding ACs to a package must not require changing the package name to remain accurate.

**Q4: User-perspective vs. technical/enabler packages — different categories?**

Answer: **No explicit category field needed.** The naming pattern itself distinguishes them:
- User-facing packages name a **role + action/screen**: "Client Data Entry", "Therapist Plan Management"
- Technical/enabler packages name a **system concern**: "Transfer Encryption", "Storage Security", "GDPR Compliance"

This is sufficient. Adding a formal `category` field would add metadata without improving clarity. The `source.type` field already captures whether a package came from a flow, requirement, or standalone decision.

**Q5: How to prevent naming collisions for scope-specific packages?**

Answer: Use a **subject-qualifier-capability** structure. The subject disambiguates:
- "Client Data Print" (printing client data from therapist view)
- "Path Report Print" (printing a path report — hypothetical)

Rules:
1. If the same verb/noun appears in multiple contexts, the **subject** (role, entity, or screen) must differ.
2. Uniqueness check at creation time (already exists) catches exact duplicates.
3. A new **similarity check** catches near-duplicates: before creating, the AI must check RELEASE_BACKLOG.md for packages sharing 2+ words with the proposed name and flag them.

**Q6: How to derive a name from a flow's happy path vs. exception bundle?**

Answer: The happy path package gets the "core" or primary name. Exception bundles get a **qualifier** that describes what they add:
- Happy path: "Data Transfer Core"
- Exception bundle 1: "Transfer Error Recovery" (describes the concern)
- Exception bundle 2: "Transfer Notifications" (describes the capability added)

Pattern: `[Flow-Subject] [Core]` for happy path; `[Flow-Subject] [Exception-Theme]` for bundles. The `priority_within_source` field (1 for happy path, 2+ for bundles) is already in the schema.

## The Naming Convention (New Rules for SEC-01)

### Structure: `[Subject] [Capability] [Qualifier?]`

| Slot | Required | Description | Examples |
|------|----------|-------------|----------|
| Subject | YES | Who/what this is about — a role, entity, or system concern | Client, Therapist, Plan, Transfer, QR, Data, Storage |
| Capability | YES | What it does — an action, screen, or outcome | Entry, Print, Encryption, Management, Navigation |
| Qualifier | NO | Disambiguator when subject+capability is not unique | Core, Full, Settings, Audit |

### Rules

1. **2-4 words** (minimum 2 is new — single-word names are too vague)
2. **Start with the subject** — the most important disambiguator comes first
3. **Use nouns and adjectives, not verbs** — "Client Data Print" not "Print Client Data" (subject-first)
4. **No timing or phase words** — "Core", "Full", "Advanced" are OK; "Phase 2", "Sprint 3", "v2" are not
5. **No implementation jargon** — "BLoC", "Repository", "Cubit", "Widget" are forbidden as primary words
6. **Globally unique** — checked against RELEASE_BACKLOG.md at creation time
7. **Similarity check** — before creating, verify no existing package shares 2+ content words (excluding stop words: "and", "the", "for"). If one does, justify why both names should coexist or adjust the new name
8. **Descriptive of delivered capability** — a stakeholder reading just the name should understand what ships
9. **Splittable** — the name must allow future subdivision by appending or changing the qualifier (e.g., "Data Transfer Core" can become "QR Transfer Send" + "QR Transfer Receive")

### Flow-Derived Naming Pattern

| Package Type | Pattern | Example |
|-------------|---------|---------|
| Happy path | `[Flow-Subject] [Core-Capability]` | "Data Transfer Core" |
| Exception bundle | `[Flow-Subject] [Exception-Theme]` | "Transfer Error Recovery" |
| Named variant | `[Flow-Subject] [Variant-Name]` | "Transfer Notifications" |

### Examples and Anti-Examples

| Name | Verdict | Reason |
|------|---------|--------|
| "Client Data Entry" | GOOD | Subject (Client) + Capability (Data Entry) — clear |
| "Data Transfer Core" | GOOD | Subject (QR Transfer) + Qualifier (Core) — indicates happy path |
| "Client Data Print" | GOOD | Subject (Client Data) + Capability (Print) — scope-specific |
| "Storage Security" | GOOD | Subject (Storage) + Capability (Security) — technical enabler |
| "Print" | BAD | Single word, no subject, ambiguous scope |
| "Data" | BAD | Single word, no capability |
| "Phase 2 Print" | BAD | Timing word "Phase 2" |
| "BLoC Refactor" | BAD | Implementation jargon "BLoC" |
| "Transfer" | BAD | Single word, no qualifier — too broad |
| "Plan Transfer Full" | ACCEPTABLE | Existing; "Full" is a valid qualifier meaning complete capability |
| "Production Stabilization" | ACCEPTABLE | Cross-cutting; subject is the system itself |

### Grandfathering Clause

Existing packages in RELEASE_BACKLOG.md are not renamed by this convention. They are considered valid. New packages created after this convention is adopted must follow these rules. If an existing package is referenced in a naming similarity check, the new package must differentiate clearly.

## How to Derive a Good Package Name

This section provides the *generative* counterpart to the validation rules above. Where the rules tell you whether a name is valid, this section tells you how to arrive at a good name in the first place. It is designed for dual use: an LLM executing a skill can follow it mechanically; a human can internalize the mental model and apply it intuitively.

### Foundational Principles (Synthesized from DDD, Technical Writing, API Design, and Information Architecture)

The naming process draws on four established disciplines, distilled into actionable principles:

| Principle | Source Discipline | What It Means for Package Names |
|-----------|------------------|--------------------------------|
| **Ubiquitous Language** | Domain-Driven Design | Names must use terms a domain expert (therapist, product owner) would say aloud. Never invent developer jargon. If a therapist would say "client data entry", the package is "Client Data Entry" — not "FormInput Module". |
| **Bounded-Context Self-Sufficiency** | Domain-Driven Design | RELEASE_BACKLOG.md is a flat list spanning many domains. Each name must carry enough context to be unambiguous *on its own*, without knowing which epic or flow it came from. |
| **Given-New Ordering** | Technical Writing / Linguistics | Place the shared/known element (Subject) first, the new/specific element (Capability) second. Readers anchor on the subject, then learn what it does. "Client Data Print" reads naturally; "Print Client Data" front-loads the action and delays the anchor. |
| **Concreteness over Abstraction** | Plain Language Guidelines | Choose the most specific common word. "Data Entry" beats "Input Management". "Backup Restore" beats "Data Persistence". A concrete name invokes a mental picture; an abstract name requires lookup. |
| **Noun-Phrase Resources** | REST / API Design (Google, Stripe) | Name the deliverable *thing*, not the process. "Transfer Encryption" (a thing that exists) not "Encrypting Transfers" (an activity in progress). This aligns with subject-first noun phrases. |
| **Faceted Classification** | Information Architecture | A good name combines orthogonal facets: *who/what* (Subject), *does what* (Capability), *which variant* (Qualifier). These three facets map directly to the `[Subject] [Capability] [Qualifier?]` structure. |
| **Parallel Structure** | Taxonomy Design | Names at the same level of a flat list should have parallel grammatical form. "Data Transfer Core", "Transfer Encryption", "Storage Security" all feel like peers. "BLoC Refactor" does not — it's a different grammatical register. |
| **Cognitive Load Minimization** | Cognitive Science (Miller's Law) | 2–4 words stays within easy recall. The fewer inferential steps to understand the name, the better. "Client Data Print" → zero inference (who, what, action). "Phase 2 UI" → multiple steps (which phase? which UI?). |

### The Naming Decision Process

Follow these steps in order. Each step narrows the name until it meets all validation rules.

```
STEP 1 — Describe the delivery in one sentence
│
│   Ask: "After this package ships, what can a stakeholder see or do
│         that they couldn't before?"
│   Write a plain-English sentence. Do NOT think about naming yet.
│
│   Example inputs:
│   • Requirement scope text, AC descriptions, flow happy-path summary
│   • For technical enablers: "What previously-impossible user feature
│     does this unblock?"
│
│   Example output:
│   "Therapists can print unprinted client data entries from the
│    Client Data View toolbar."
│
├── STEP 2 — Extract the Subject
│   │
│   │   Ask: "Who is affected, or what domain entity is central?"
│   │
│   │   Heuristics (try in order, stop at the first that fits):
│   │   a. Is there a ROLE? (Client, Therapist) → use the role
│   │   b. Is there a DOMAIN ENTITY? (Plan, Transfer, QR) → use the entity
│   │   c. Is there a SYSTEM CONCERN? (Storage, Privacy, Accessibility)
│   │      → use the concern
│   │   d. Compound subject: if role + entity are both needed for
│   │      disambiguation → combine them: "Client Data", "Therapist Plan"
│   │
│   │   From the example: Subject = "Client Data"
│   │   (Role "Client" + Entity "Data" — needed because "Data Print"
│   │    alone is ambiguous: whose data?)
│   │
│   ├── STEP 3 — Extract the Capability
│   │   │
│   │   │   Ask: "What new ability or artifact does this deliver?"
│   │   │
│   │   │   Rules:
│   │   │   • Use a noun or noun phrase (Print, Entry, Encryption,
│   │   │     Navigation) — not a verb phrase (Printing, Entering)
│   │   │   • Choose the most concrete, commonly-understood word
│   │   │   • If multiple capabilities exist, pick the primary one;
│   │   │     secondary capabilities belong in the description field,
│   │   │     not the name
│   │   │
│   │   │   From the example: Capability = "Print"
│   │   │
│   │   ├── STEP 4 — Test Uniqueness
│   │   │   │
│   │   │   │   Combine: "[Subject] [Capability]" → "Client Data Print"
│   │   │   │
│   │   │   │   Check RELEASE_BACKLOG.md:
│   │   │   │   a. Exact duplicate? → STOP, join the existing package
│   │   │   │      (unless granularity test says split — see Q3 answer)
│   │   │   │   b. Shares 2+ content words with another package?
│   │   │   │      → Evaluate: are these genuinely different capabilities?
│   │   │   │        • YES: justify in the description and proceed
│   │   │   │        • NO: merge into the existing package
│   │   │   │   c. Unique? → Proceed to Step 5
│   │   │   │
│   │   │   │   From the example: "Client Data Print" shares 2 words
│   │   │   │   with "Client Data Entry" — justified because Print and
│   │   │   │   Entry are genuinely different capabilities (output vs. input).
│   │   │   │
│   │   │   ├── STEP 5 — Add Qualifier (if needed)
│   │   │   │   │
│   │   │   │   │   A qualifier is needed ONLY when:
│   │   │   │   │   • Subject + Capability is not unique (Step 4b), OR
│   │   │   │   │   • The package is part of a flow decomposition
│   │   │   │   │     (happy path → "Core"; exception bundle → theme word)
│   │   │   │   │   • The package covers a variant or subset of a broader
│   │   │   │   │     capability ("Full", "Settings", "Audit")
│   │   │   │   │
│   │   │   │   │   From the example: no qualifier needed — "Client Data Print"
│   │   │   │   │   is unique and self-contained.
│   │   │   │   │
│   │   │   │   ├── STEP 6 — Apply Word-Form Rules
│   │   │   │   │   │
│   │   │   │   │   │   Checklist:
│   │   │   │   │   │   □ 2–4 words?
│   │   │   │   │   │   □ Subject is first?
│   │   │   │   │   │   □ All nouns/adjectives (no verb-first phrasing)?
│   │   │   │   │   │   □ No timing words (Phase, Sprint, v2)?
│   │   │   │   │   │   □ No implementation jargon (BLoC, Repository, etc.)?
│   │   │   │   │   │
│   │   │   │   │   │   From the example: "Client Data Print" → 3 words ✓,
│   │   │   │   │   │   subject first ✓, all nouns ✓, no timing ✓, no jargon ✓
│   │   │   │   │   │
│   │   │   │   │   └── STEP 7 — Stakeholder Understandability Test
│   │   │   │   │       │
│   │   │   │   │       │   Run all 5 tests (see next section).
│   │   │   │   │       │   ALL must pass. If any fails, go back to the
│   │   │   │   │       │   failing step and adjust.
│   │   │   │   │       │
│   │   │   │   │       └── DONE — Name is ready
```

### Stakeholder Understandability Tests

These five tests operationalize the vague goal "a stakeholder reading just the name should understand what ships." Each test is a concrete yes/no question. All five must pass.

| # | Test Name | Question to Ask | Pass Criterion | Fail Example → Fix |
|---|-----------|----------------|----------------|-------------------|
| **U1** | **Picture Test** | Can a non-technical stakeholder form a mental picture of what this delivers within 3 seconds of reading the name? | The name evokes a concrete screen, action, or capability — not an abstract concept | "Data Persistence" → fails (abstract). Fix: "Data Backup Restore" (evokes a concrete action) |
| **U2** | **Disambiguation Test** | If you showed this name alongside all other package names in RELEASE_BACKLOG.md, could a reader tell which one is which without reading descriptions? | The name is distinguishable from every other package name in the list by at least the Subject or Capability word | "Transfer Core" alongside "Transfer Encryption" → ambiguous subjects. Fix: "Data Transfer Core" (subject now differentiates) |
| **U3** | **Completion Test** | Can a stakeholder correctly finish this sentence: "When [Package Name] ships, users will be able to ___"? | A domain-literate person (not a developer) can fill the blank correctly on the first try | "Production Stabilization" → hard to complete (what specifically?). Acceptable as a cross-cutting exception; for scope-specific packages this must pass cleanly |
| **U4** | **Recollection Test** | After seeing this name once, could someone refer to it correctly in a meeting 24 hours later? | The name is memorable enough to recall without looking it up. Test: does it use common domain words in a natural phrase? | "Reverse DataBeam Spike" → borderline (unusual terms). Acceptable because "DataBeam" is a product-specific term established in the domain vocabulary |
| **U5** | **Scope Boundary Test** | Can a reader tell what is NOT included in this package? | The name is specific enough that related-but-different capabilities are clearly outside its boundary. Inverse of U2: not just "is it different from others" but "does it exclude what it shouldn't include" | "Data Management" → fails (could mean entry, visualization, backup, print, export...). Fix: "Client Data Entry" (clearly excludes visualization, backup, etc.) |

**Applying the tests (for LLMs)**: After constructing a candidate name in Step 6, evaluate each test by mentally simulating a stakeholder (the app's target user: a German psychotherapist or their client) reading the name in the context of a release notes list. If any test fails, identify which step (2–5) produced the problematic word and revise.

**Applying the tests (for humans)**: Read the name aloud. If you hesitate, stumble, or need to add "you know, the one that..." when explaining it to a colleague, the name fails. Go back and make the Subject or Capability more specific.

### Worked Examples

#### Example 1: "Client Data Print" (REQ-FUNC-007-13, release 0.2.0)

**Step 1 — Describe the delivery:**
"Therapists can print unprinted client data entries from the Client Data View toolbar; printed status persists per entry and print history is accessible on demand."

**Step 2 — Extract Subject:**
- Role involved? Therapist performs the action, but the *data* belongs to the client. The subject is about *whose data* is being printed.
- Compound subject: "Client Data" (the entity being acted upon — more descriptive than "Therapist Print" which obscures what is printed).

**Step 3 — Extract Capability:**
- What new ability? Printing. Noun form: "Print".
- Alternative considered: "Print Export" — but the feature is specifically printing, not generic export. "Print" is more concrete.

**Step 4 — Test Uniqueness:**
- Candidate: "Client Data Print"
- Similarity check: shares "Client Data" with "Client Data Entry". Justified? Yes — Print (output) and Entry (input) are opposite operations on the same entity. Both names are needed.

**Step 5 — Qualifier:**
- Not needed — "Client Data Print" is unique and scoped.

**Step 6 — Word-Form Rules:**
- 3 words ✓ | Subject first ✓ | Nouns ✓ | No timing ✓ | No jargon ✓

**Step 7 — Understandability Tests:**
- U1 Picture: "Client Data Print" → picture of a print button on a data screen ✓
- U2 Disambiguation: distinct from "Client Data Entry" by capability word ✓
- U3 Completion: "When Client Data Print ships, users will be able to *print client data entries*" ✓
- U4 Recollection: natural phrase, easy to recall ✓
- U5 Scope Boundary: clearly excludes data entry, data visualization, data export-to-file ✓

**Result: "Client Data Print"** — all tests pass.

### Common Pitfalls in the Naming Process

| Pitfall | Why It Happens | How to Avoid |
|---------|---------------|--------------|
| **Starting with the verb** | English imperative habit ("Print the data") | Always ask "who/what is this about?" first (Step 2), not "what does it do?" |
| **Too abstract a subject** | Trying to cover too much scope in one package | If the subject could be mistaken for 3+ different packages, it's too broad. Add a modifier or split. |
| **Capability word duplicates subject** | e.g., "Transfer Transfer Core" | If capability = subject, the capability slot becomes the qualifier. Use "Core", "Full", or a theme word instead. |
| **Naming after implementation** | Developer habit of thinking in code | Apply the U1 Picture Test immediately — if the name evokes code instead of a screen or user action, reword. |
| **Skipping the uniqueness check** | Confidence that the name is "obviously different" | Always scan RELEASE_BACKLOG.md. A 2-word overlap that seems fine today causes confusion when the backlog grows. |
| **Over-qualifying** | Adding words "just in case" (e.g., "Client Therapist Data Entry Full") | If the name passes U2 and U5 without the qualifier, drop it. Shorter is better. |

```markdown
#### User-Facing vs. Technical Packages

No explicit category field is needed. The naming pattern itself distinguishes:

- **User-facing**: Subject is a role or screen — `"Client Data Entry"`, `"Therapist Navigation"`
- **Technical/enabler**: Subject is a system concern — `"Transfer Encryption"`, `"Storage Security"`, `"GDPR Compliance"`

Both follow the same `[Subject] [Capability] [Qualifier?]` structure. The `source.type` field in RELEASE_BACKLOG.md already captures origin (flow, requirement, standalone).

#### Grandfathering

Existing packages in RELEASE_BACKLOG.md at the time of this convention's adoption are not renamed. New packages created after adoption must follow these rules. When an existing package triggers a similarity check against a proposed new name, the new name must differentiate clearly.

#### Package Granularity Guidelines

**When to create a new package** (all three must hold):
1. The ACs describe a capability that can ship independently of existing packages
2. The capability has a distinct demo story (a stakeholder can see what changed)
3. Adding the ACs to an existing package would blur that package's description

**When to join an existing package**:
- The new ACs are a natural extension of an existing package's scope
- Adding them does not require changing the package name to stay accurate
- The combined package stays within the 3–15 impl task size range

**Preventing oversized packages**: When a package exceeds 15 impl tasks, split along a capability boundary. The naming convention supports this: specific names can be subdivided by changing the qualifier (e.g., "Data Transfer Core" → "QR Transfer Send" + "QR Transfer Receive").

**Initial sizing philosophy — err on the broader side**: When creating a package for the first time, it is better to cut it slightly broader than too narrow. The reason: merging two packages later is painful (backlog entries, references, and release assignments must be reconciled), while splitting is well-supported by Rule 9 (splittable names) and the 15-task size trigger. In practice: size the initial package so it satisfies the 3–15 task range given what is *known today*. Future requirements that fit the name and keep the package within range join it organically; requirements that would push it over 15 tasks or blur the name trigger a split. Over-engineering the initial cut — splitting preemptively before any requirements exist — creates unnecessary overhead and fragments the backlog.
```

```markdown
#### How to Derive a Good Package Name

This subsection provides the generative counterpart to the rules above. Follow these steps to arrive at a name — whether you are an LLM executing a skill or a human naming a package manually.

##### Step-by-Step Process

1. **Describe the delivery** — Write one sentence: "After this ships, a stakeholder can ___." Do not think about naming yet.
2. **Extract the Subject** — Who is affected or what entity is central? Try in order: (a) Role (Client, Therapist), (b) Domain entity (Plan, Transfer, QR), (c) System concern (Storage, Privacy, Accessibility). Use a compound subject (e.g., "Client Data") if a single word is ambiguous.
3. **Extract the Capability** — What new ability does this deliver? Use a noun or noun phrase (Print, Entry, Encryption), not a verb phrase.
4. **Test uniqueness** — Combine Subject + Capability. Check RELEASE_BACKLOG.md for exact duplicates and 2+ word overlaps. If overlap exists, justify coexistence or merge.
5. **Add a Qualifier only if needed** — When Subject + Capability alone is not unique, or the package is part of a flow decomposition (happy path → "Core"; exception → theme word), or it covers a variant/subset ("Full", "Settings", "Audit").
6. **Apply word-form rules** — 2–4 words, subject-first, nouns/adjectives, no timing words, no implementation jargon.
7. **Run the Stakeholder Understandability Tests** — All 5 must pass.

##### Stakeholder Understandability Tests

| # | Test | Question | Pass Criterion |
|---|------|----------|----------------|
| U1 | Picture Test | Can a non-technical stakeholder picture what this delivers within 3 seconds? | The name evokes a concrete screen, action, or capability |
| U2 | Disambiguation Test | Is this name distinguishable from every other name in RELEASE_BACKLOG.md? | Differs from every other package by at least Subject or Capability |
| U3 | Completion Test | Can a stakeholder finish: "When [Name] ships, users will be able to ___"? | A non-developer can fill the blank correctly on the first try |
| U4 | Recollection Test | Could someone recall this name correctly 24 hours after seeing it once? | Uses common domain words in a natural phrase |
| U5 | Scope Boundary Test | Can a reader tell what is NOT included? | Specific enough that related-but-different capabilities are clearly outside |

If any test fails, return to the corresponding step (2–5) and revise.
```
