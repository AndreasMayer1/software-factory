# Opus Plan: Release Version Management — Requirement Specification

## Objective

Create a comprehensive, implementable requirement specification for REQ-PROC-034 that covers all 7 exploration areas from the goal. The specification must be concrete enough to derive implementation tasks directly.

## Analysis Summary

### Investigation Findings

1. **Existing YAML Patterns**: The project uses a mature two-layer YAML system (requirements.md + goal.md) with well-defined fields. Adding `target_release` follows established conventions.

2. **Script Infrastructure**: `generate_status_overview.py` (2000+ lines) already has dependency analysis, graph building, and multi-mode reporting. Adding release grouping is an incremental extension.

3. **Dependency Validation**: `reconcile_dependencies.py` and `validate_meta.py` already handle bidirectional dependency consistency and field validation. Release-dependency cross-validation can build on these.

4. **Skills Architecture**: 5 skills modify requirements/tasks YAML. `task-create` does the heaviest YAML work (inheriting priority, populating covers). Release version inheritance fits naturally into its existing propagation logic.

5. **Parent Requirement**: REQ-PROC-009 (Requirements and Tasks Structure) is the dependency — release versioning extends its metadata standards.

### Key Design Decisions Made

| # | Decision | Choice | Rationale |
|---|----------|--------|-----------|
| 1 | Release definition location | `requirements_tasks/RELEASES.md` | Near the artifacts it governs; conventional path |
| 2 | Release definition format | YAML frontmatter + Markdown body | Consistent with all project files |
| 3 | YAML field name | `target_release` | Indicates intent (planned), not current state |
| 4 | Unassigned representation | Field absent = not yet considered | Minimal noise; explicit null not needed |
| 5 | Per-trackable-item releases | `target_release` on each AC/section | Fine-grained planning across releases |
| 6 | Version comparison | Semantic versioning (semver) | Industry standard, Python `packaging.version` |
| 7 | Script extension approach | Additional `--release` filter + release section in reports | Augments, doesn't replace existing views |
| 8 | Dependency validation location | In `generate_status_overview.py` + `validate_meta.py` | Leverages existing infrastructure |
| 9 | Migration strategy | Incremental, user-driven with batch helper | Respects existing ~68 reqs + ~170 tasks |
| 10 | Release status tracking | `planned → active → released` | Enables STATUS.md to show release progress |

## Risks

- **Risk**: Over-engineering the per-trackable-item release assignment
  - **Mitigation**: Start with top-level `target_release` only; per-item is optional Phase 2
- **Risk**: Migration disrupts existing workflows
  - **Mitigation**: Incremental approach; `target_release` is optional, not required
- **Risk**: Semver comparison complexity (pre-release, build metadata)
  - **Mitigation**: Use simple MAJOR.MINOR.PATCH only; no pre-release tags needed
