# Opus Plan: Fix Next-Task Prioritization — Explore vs. Impl

## Objective

Stop `scripts/next_tasks.py` (called by the autorun via "Do Next Task") from letting **unrelated, low-priority explore tasks block implementation of the next release**, while **preserving** the original safety guarantee that explore tasks writing/updating requirements for the current release run *before* their corresponding impl tasks.

## Analysis Summary

### The actual bug

`next_tasks.py` has two ranking functions (`rank_tasks`, `rank_tasks_by_package`) that share the same sort key:

```python
(type_rank, is_next, req_not_active, -priority_score)
```

- `type_rank = 0` for explore, `1` for impl
- `is_next = 0` if task is in next release/package, `1` otherwise

Because `type_rank` is the **primary** sort criterion, **every** explore task (any release, any priority) beats **every** impl task (any priority). That's why low-priority explores like `TASK-PROC-027-34` (Explore Therapy End Flow, U2) are picked before e.g. `TASK-FUNC-007-04-08` (Impl Spike-Cleanup, U2, assigned to current release 0.0.1).

### The original intent

The rule "explore before impl" was introduced to protect the `requ-derive-from-flow` workflow: when a user flow creates a batch of explore tasks (which write/update requirements), those must finish before any impl that would consume those requirements.

But the rule was only meant to apply **within the scope of current work**, not globally. Globally applied, it breaks release planning.

### Two real problems, one root cause

1. **Unrelated explores block current release** (the symptom the user noticed).
2. **The sort order is semantically wrong** (the root cause).

## Options Considered

### Option A — User's proposal: `after: [release-0.0.1]` deferral

Manually tag every explore task that should wait with a release dependency in the `after` field. Teach `next_tasks.py` to recognize `release-X.Y.Z` entries and treat them as blockers until the release is shipped.

**Changes required:**
- `scripts/next_tasks.py`: extend `_is_blocked()` to recognize the pattern, look up release status in `RELEASES.md`
- `scripts/validate_meta.py`: accept the pattern in `after` field
- Tag ~7 existing tasks (one-line edits)

**Pros**
- Explicit and auditable per task
- Matches user's mental model (blocked waiting for a release)
- Robust in the sense of "no surprises"

**Cons**
- Manual tagging overhead — forever. Every new "not-yet-relevant" explore must be tagged.
- Easy to forget → problem reappears silently
- Doesn't fix the underlying sort-order bug, only works around it
- Tag invalidates if release plan is reshuffled (needs re-tagging)

**Token cost:** zero at script runtime; small human-interaction cost per new task.

---

### Option B — Fix the sort key (RECOMMENDED)

Swap the first two elements of the sort key in both `rank_tasks` and `rank_tasks_by_package`:

```python
# Before:
(type_rank, is_next, req_not_active, -priority_score)
# After:
(is_next, type_rank, req_not_active, -priority_score)
```

**Semantic effect:**
- Next-release/package tasks beat non-next-release tasks (as intended by rank rule #1 in the docstring)
- Within the next release: explore before impl (preserves `requ-derive-from-flow` safety)
- Non-next-release explores sink to their correct position — they no longer hijack the queue

**Changes required:**
- 2 lines in `scripts/next_tasks.py` (plus update the docstring to match)
- Update the existing regression-style test if one exists (`scripts/` tests)
- Zero task tagging

**Pros**
- Fixes the root cause
- Zero maintenance going forward
- No human error surface — applies automatically to every new task
- Preserves the original safety guarantee
- Matches the ranking rules *already documented* in the docstring (lines 5–11): rule 1 says "next release first", rule 2 says "explore before impl". The current code violates its own documented order.

**Cons**
- If a user deliberately wants to force-run a future explore (e.g. urgent research to de-risk a future feature), they can't — but that's what the `--type explore` flag and manual task selection already cover.

**Token cost:** zero, forever.

---

### Option C — Hybrid (B + A)

Fix the sort key **and** also support release-deferral via `after: [release-X.Y.Z]` as an escape hatch for edge cases.

**Pros**
- Maximum flexibility
- Belt-and-suspenders

**Cons**
- Two mechanisms to document and maintain
- Invites "when do I use which?" confusion
- Over-engineering for a problem B solves cleanly

---

### Options rejected without deep analysis

- **Remove the explore-first rule entirely** — explicitly ruled out by user; breaks `requ-derive-from-flow`.
- **New `defer_until_release` frontmatter field** — same effect as Option A but worse (new field vs. reusing `after`).
- **New `deferred` status** — yet another status to maintain, no advantage over A.

---

## Recommendation

**Adopt Option B** (fix the sort key).

Reasons, weighed against user's robustness + token-efficiency priorities:

| Criterion | A (tag tasks) | B (fix sort) | C (hybrid) |
|-----------|---------------|--------------|------------|
| Robustness | Medium (manual; forget-risk) | **High (automatic)** | High |
| Token cost | Zero runtime; small human | **Zero, forever** | Zero |
| Maintenance | Ongoing | **None** | Ongoing |
| Matches documented intent | No (workaround) | **Yes** | Partial |
| Implementation effort | ~1h + tagging | **~20 min** | ~1.5h |

Option B is a surgical fix that restores the script to what its own docstring already claims it does. The seven tasks the user was going to tag become automatically deprioritized — no tagging needed.

## Risks

- **Risk:** Someone relies on the old "explore globally first" behavior for a legitimate workflow we haven't identified.
  - **Mitigation:** Grep for other callers of `rank_tasks` / `next_tasks.py` output consumers. The only known consumer is the autorun via "Do Next Task". If another consumer exists with different expectations, it would have been written against the documented rules, which B aligns with.

- **Risk:** `requ-derive-from-flow` creates explore tasks without `target_release`/`target_package`, so they wouldn't be in `is_next=0` and could get deprioritized even when they genuinely matter.
  - **Mitigation:** Check what `requ-derive-from-flow` sets. If it doesn't set a target_package, update the skill to inherit the parent requirement's target_package. This keeps the safety guarantee intact.
  - **Verification step needed** before rolling out B: inspect an explore task created by `requ-derive-from-flow` and confirm it has a `target_package`. If not, add that to the B plan as a prerequisite fix.

- **Risk:** Unintended ranking for the `rank_tasks` release fallback path (when no package data).
  - **Mitigation:** Same fix in both functions; behavior is consistent.

## Execution — How Many Agents

**One implementation agent** (small, low-risk change) — plus the prerequisite verification step noted under Risks. If verification reveals that `requ-derive-from-flow` explores don't inherit `target_package`, the agent also updates that skill. Still one agent, two files at most.
