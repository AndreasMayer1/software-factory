# Opus Plan v2: Fix Next-Task Prioritization via Explicit Critical-Path Flag

## Objective

Make `scripts/next_tasks.py` pick the right next task in all scenarios, **without** requiring a `target_package` on every explore task — because `requ-derive-from-flow` intentionally creates explores without one (package assignment needs the full cross-flow picture, which comes later).

## Why v1 (Option B) was insufficient

The previous plan (`2026-04-22_01_opus_plan.md`) recommended swapping the sort key from `(type_rank, is_next, …)` to `(is_next, type_rank, …)` and argued that `requ-derive-from-flow` explores would "inherit a target_package" as a prerequisite.

That assumption is wrong. Per `requ-derive-from-flow/skill.md` lines 658 and 756–758, the skill **deliberately** leaves `target_package` unset:

> "Never use `target_package` for this step — `target_package` is assigned by `release-plan` only after all requirements exist."
> "Package assignment … requires the full cross-flow picture — that belongs to `release-plan`, not here. Never assign `target_package` in this skill."

Consequence: with Option B alone, a legitimately critical requirements-writing explore (no package, no release) would score `is_next=1` and get ranked **below** every current-release impl task. That breaks the original safety guarantee — the whole reason "explore before impl" exists. Option B is off the table.

## Analysis Summary

### The two distinct categories of explore tasks

| Category | Example | Must block impl? | Has `target_package`? |
|----------|---------|------------------|-----------------------|
| **Critical path** — writes/updates requirements that pending impl tasks consume | Tasks from `requ-derive-from-flow`, `requ-apply-market`, some manual requirement exploration | **Yes** | No (by design) |
| **Forward-looking research** — investigates future features, flows, backup strategies, etc. | TASK-PROC-027-34 (Therapy End Flow), TASK-FUNC-006-03 (Security open questions) | No | Usually no, sometimes yes |

The current script treats both categories the same via `type == 'explore'`. That's the bug.

### The user's proposal, refined

Introduce an explicit frontmatter flag that marks a task as *critical-path* — i.e. **writes requirements that impl depends on**. The flag is set automatically by the relevant skills (primarily `requ-derive-from-flow`) and read by `next_tasks.py` to give those tasks absolute priority.

Proposed flag name: **`writes_requirements: true`**

Why this name over alternatives:
- `writes_requirements` — **describes what the task does** (clear semantics, self-documenting, extensible to other skills that also write requirements)
- `blocks_impl: true` — describes effect but sounds negative and invites misuse
- `derive_from_flow: true` — ties the flag to one skill; prevents reuse by future skills that also write requirements
- `priority_lane: fast` — over-engineered; boolean is sufficient
- `critical_path: true` — too generic; would attract unrelated uses

### The new sort key

```python
(not writes_requirements, is_next, type_rank, req_not_active, -priority_score)
```

Ranking rules in order:

1. **Critical-path explores first** (those writing requirements, `writes_requirements == True`)
2. **Within the remainder:** next release/package first (`is_next`)
3. **Within next release:** explore before impl (`type_rank`) — legacy rule, still correct for tasks inside current scope
4. **Within same type:** requirements with in-progress work first (`req_not_active`)
5. **Tiebreaker:** urgency × 10 + impact (`priority_score`)

### Trace against current open tasks

Assuming fix is applied and no current task has `writes_requirements: true`:

- **TASK-FUNC-007-04-08** (Impl Spike-Cleanup, package → 0.0.1): `(1, 0, 1, …)` → rises to top
- **TASK-PROC-027-34** (Explore Therapy End, no package): `(1, 1, 0, …)` → sinks below current-release impl
- **TASK-FUNC-006-03** (Explore Security, REQ for 0.0.2): `(1, 1, 0, …)` → same; correctly deferred until 0.0.1 done

And for a hypothetical future `requ-derive-from-flow` explore (no package but flagged):

- `writes_requirements: true`, `type: explore`, no package: `(0, 1, 0, …)` → beats everything including 0.0.1 impl

Safety guarantee preserved: if a flow triggers a batch of requirements-writing tasks, they run first no matter what.

## Options Reconsidered

### Option 1 — Flag on task (recommended, user's idea refined)

Add `writes_requirements: true` to explore tasks that write requirements. Skills set it automatically; script honors it.

**Pros**
- Auto-set by the skills that need it → zero manual tagging day-to-day
- Decoupled from package/release metadata → works even for tasks `requ-derive-from-flow` creates
- Preserves safety guarantee (critical-path always wins)
- Extensible — other requirement-writing skills can set it
- 2–3 line change in script, 1 line in skill template

**Cons**
- New field to document
- Requires coordinated update: skill template + script + validator

**Token cost:** zero at runtime.

### Option 2 — Migration to implicit via task folder path

Infer `writes_requirements` from task folder location (e.g. "any explore under a flow-derived path"). Rejected on analysis — paths are inconsistent (`user_flows/tasks/` holds a mix of requirements-writers and unrelated flow work like TASK-PROC-027-38). Would require restructuring folders, much higher cost.

### Option 3 — Use task type enum instead of boolean flag

Add a new `type: derive` (or `type: writes_requirements`) alongside `impl`/`explore`. Rejected — more invasive (every `type`-reading script needs updating, CLAUDE.md task-type docs need updating, validator enum expansion) for no semantic advantage over a boolean.

### Option 4 — Release-deferral on every non-critical explore (original user proposal, Option A)

`after: [release-0.0.1]` manual tagging. Rejected — it's the inverse of Option 1 (tag the *non*-critical ones instead of the *critical* ones). Scales badly because forward-looking explores far outnumber critical-path ones, and each new one needs manual tagging forever.

### Option 5 — Combine 1 + sort-key fix from v1

**This is what Option 1 actually does.** The new sort key adds the `writes_requirements` lane *and* fixes the `is_next` vs `type_rank` order for everything else. It's one coherent change, not two separate options.

---

## Recommendation

**Option 1**: introduce `writes_requirements: true` frontmatter flag; update script sort key to recognize it; update `requ-derive-from-flow` to set it.

Scoring against user's priorities:

| Criterion | Option 1 | Option 4 (tag non-critical) |
|-----------|----------|-----------------------------|
| Robustness | **High** — auto-set by skill | Medium — manual, forget-risk |
| Token cost | **Zero runtime, zero human** | Zero runtime, small human |
| Maintenance | **Near-zero** — flag grows with requirements-writing skills (infrequent) | Ongoing — every new forward-looking explore needs a tag |
| Preserves safety | **Yes** | Yes |
| Implementation effort | ~30 min | ~1 h + indefinite tagging |

### Single implementation agent

**Step 1: Update `scripts/next_tasks.py`**

1. In `load_tasks()` (around line 222), read the new flag:
   ```python

   ```
2. In `rank_tasks()` (line 342–346) and `rank_tasks_by_package()` (line 362–366), change the sort key to:
   ```python
   def sort_key(t):
       writes_req_rank = 0 if t.get("writes_requirements") else 1
       is_next = 0 if (next_release and t["target_release"] == next_release) else 1
       type_rank = 0 if t["type"] == "explore" else 1
       req_not_active = 0 if t["parent_requirement"] in reqs_active else 1
       return (writes_req_rank, is_next, type_rank, req_not_active, -_priority_score(t))
   ```
3. Update the docstring (lines 5–11) to reflect the new four-tier ranking:
   1. Critical-path explores (`writes_requirements: true`)

## Risks

- **Risk:** Another currently-open explore task actually writes requirements and isn't flagged, so after the fix it gets deprioritized.
  - **Mitigation:** Audit all 8 currently-open explores against the "writes requirements" criterion. From what the gathering agent surfaced: none qualify (scenario generation, therapy-end flow exploration, backup flows, security tech questions, market research, backup compression — all forward-looking or content-generation, not impl-blocking requirements writing). Confirm during execution.

- **Risk:** A user writes a skill later that creates requirement-writing tasks and forgets to set the flag. Those tasks would be deprioritized.
  - **Mitigation:** Document in `task-create` skill and in `requ-derive-from-flow` guidelines. Low risk because new skills creating tasks are rare.

- **Risk:** The flag gets abused ("I want my task to run first, I'll just set writes_requirements").
  - **Mitigation:** Low realistic risk in a solo-developer context. If it happens, add a validator rule: `writes_requirements: true` requires `type: explore` and a documented source (flow ID or similar).

- **Risk:** Script change breaks the automated mode pipeline mid-run.
  - **Mitigation:** Test interactively first (Step 5) before any autorun invocation. The change is isolated to sort order, so worst case is suboptimal task pick, not a crash.
