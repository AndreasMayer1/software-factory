# Goal: Explore Consistency Checks in requ-derive-from-flow and requ-explore Skills

## Objective

Investigate whether the current `requ-derive-from-flow` and `requ-explore` skills adequately prevent contradictions with existing requirements and existing source code when requirements are created or modified. Identify gaps and propose concrete improvements.

## Background

A recent incident showed that a task generated by `requ-derive-from-flow` introduced requirement content that contradicted an existing implementation in the source code. The skill was not aware of the implementation because it only scans existing requirements (`requirements_tasks/`), not source code. This raises two related questions:

1. **Does the requirements scan work well enough?** The skill is supposed to detect overlaps (AC-03), but it may rely on folder-tree traversal and explicit ID references rather than semantic keyword matching — meaning it can miss overlaps when the naming differs.
2. **Does `requ-explore` catch what `requ-derive-from-flow` missed?** The skill has a "1.5 Analyze Implementation" step, but it's unclear how thoroughly it is executed and whether it reliably catches implementations that have no backing requirement.

## Questions to Answer

1. Does `requ-derive-from-flow` currently scan existing requirements well enough?
   - Is the scan deep/broad enough to catch semantic overlaps, or does it only match on explicit file names/IDs?
   - What search strategy does it actually use (read all? keyword grep? folder walk?)?

2. Does `requ-explore` read enough sibling requirements before writing to avoid duplicate or contradictory content?
   - Section 1.4 says "Read parent and sibling requirements" — but how broadly are siblings scanned?

3. Is section "1.5 Analyze Implementation" in `requ-explore` sufficient to detect implementations without a corresponding requirement?
   - Under what conditions is codegraph used vs. skipped?
   - How deep is the Glob/Grep search in practice?

4. Is it realistic and efficient to add a code analysis step to `requ-derive-from-flow`, or should that responsibility stay in `requ-explore`?

5. What is the right keyword-search strategy for requirements consistency checks?
   - A targeted Grep across `requirements_tasks/` for relevant terms per gap (not reading all files) seems promising.
   - What keywords would reliably surface overlaps without false positives?

6. Should the "implemented but no requirement exists" legacy gap be addressed proactively — e.g., a one-time code-to-requirements backfill task — rather than requiring every skill run to re-check the whole codebase?

## Ideas to Evaluate

- **Add a targeted Grep step in `requ-derive-from-flow`**: Before categorizing a gap as `new_needed`, Grep `requirements_tasks/` for keywords derived from the gap description. This would surface semantic overlaps without reading all requirement files.
- **Strengthen sibling scanning in `requ-explore`**: Replace (or augment) the folder-walk approach in section 1.4 with a keyword-Grep that searches broadly — not just up the folder tree.
- **Code-to-requirements backfill task**: A separate, one-time analysis of `lib/` to identify implemented features without a corresponding requirement, then create placeholder `requirements.md` files. This closes the legacy gap cleanly and eliminates the need for each skill to defensively check the whole codebase.
- **Non-recommendation**: Do NOT add a full source-code scan to `requ-derive-from-flow` — this would be overkill for a flow-analysis skill. Implementation awareness belongs in `requ-explore`.

## Scope

### In Scope
- Analyzing the current gap-detection logic in `requ-derive-from-flow` (`.claude/skills/requ-derive-from-flow/skill.md`)
- Analyzing sections 1.4 and 1.5 of `requ-explore` (`.claude/skills/requ-explore/skill.md`)
- Proposing concrete, low-token-cost search strategies for cross-requirement consistency checks
- Recommending whether a backfill task is the right solution for the legacy gap
- If improvements are proposed: writing concrete skill-change descriptions or draft goal.md stubs for follow-up impl tasks

### Out of Scope
- Implementing the skill changes (that is a follow-up impl task)
- Running the backfill analysis itself (that is a separate task if recommended)
- Changing `requ-derive-from-flow` to scan source code directly

- [ ] Sibling-requirement scanning in `requ-explore` is assessed: is it sufficient, and what specific improvement (if any) is needed?

## Notes

This task was triggered by the observation that `requ-derive-from-flow` produced tasks with requirement content contradicting an existing source-code implementation. The root cause was that the skill does not analyze source code. However, `requ-explore` already has a code-analysis step (1.5) — so the real question is whether that step is deep enough, and whether earlier stages (the derive skill + sibling scanning in explore) can catch issues before `requ-explore` runs.

The goal is not to make every skill run exhaustively safe — that would be too expensive. The goal is to find the right, low-cost safeguard at the right stage of the pipeline.
