# Plan Review: requ-assign-packages Task

## Summary

The goal.md is well-structured and covers the full pipeline. However, several implementation details need clarification before execution can begin safely: (1) the gap scanner needs a new parser function since the existing `parse_item_package_map` returns only assigned items, (2) Signal 1 (`release_chunk`) has zero current matches in the codebase and is pure future-proofing, (3) the fuzzy matching strategy is underspecified for a Python script but appropriate for the AI skill, and (4) the AC item structure varies significantly across requirements (some have `text:` fields, some do not). The deliverables are otherwise clear, the edit locations are precise, and the execution order has a clean dependency chain.

## Findings

### Deliverable Clarity

**Deliverable 1 — `sync_requirement_packages.py`**: Mostly clear. Two issues:

1. **Parser gap**: The goal says "Reuse `split_frontmatter()`, `parse_release_backlog()`" but the script's core need is to find items WITHOUT `target_package`. The existing `parse_item_package_map` returns items WITH packages. A new function `parse_unassigned_items(req_path)` is needed that returns `list[(item_id, text_or_empty)]` for items lacking `target_package`. This is straightforward but not mentioned.

2. **AC description output**: The example output shows AC descriptions (`"Notification is shown when transfer initiates"`), but many requirements have ACs with only `- id: AC-01` and no `text:` field (e.g., REQ-FUNC-007-06 has 11 ACs with no text in frontmatter). The script must either: (a) show just the ID when no text exists, or (b) parse the markdown body for AC descriptions. Option (a) is simpler and sufficient for a gap scanner.

**Deliverable 2 — `requ-assign-packages` skill**: Clear and well-specified. The 4-signal heuristic is logical. Minor ambiguities noted below in Heuristic Logic Analysis.

**Deliverable 3 — `release-plan` Action 4 quality guidance**: Precise edit location, exact text provided. Unambiguous.

**Deliverable 4 — `release-plan` Action 6**: Clear. Two edits needed: menu item in Step 2 and action block in Step 3. The menu renumbers: current "5. Done" stays as-is and "6. Assign packages..." is appended. The Step 3 insertion point is explicitly stated: after Action 5, before "After each action (except Done)...". However, the "After each action (except Done)" line must be updated to include "(except Done and Action 6)" or similar, since Action 6 invokes another skill and should not loop back to the menu — the invoked skill handles its own flow. **This update is not mentioned in goal.md.**

**Deliverable 5 — `requ-derive-from-flow` Phase 2 edits**: Both edit locations are precisely identified. Edit 1 inserts Suggested Package column rules after line 288 and before line 291 of the current file. Edit 2 renames "Suggested Release Chunk" to "Suggested Package" on line 289. Execution order matters: Edit 2 must be done first (or simultaneously) since Edit 1 inserts text near Edit 2's target line. In practice, both are in the Notes block and non-overlapping — safe to do in either order.

### Heuristic Logic Analysis

**Signal 1 — `release_chunk` field**: Currently produces zero matches (no requirements.md has this field yet). This is forward-looking: `requ-explore` is documented as writing this field when `suggested_release_chunk` is present in the goal.md. The signal is correctly placed as highest priority since it's the most direct evidence.

**Risk**: If `release_chunk` values diverge from RELEASE_BACKLOG.md package IDs over time (organic naming drift), the fuzzy match could produce false positives. Mitigation: the skill shows proposals with reasoning and the user confirms per-requirement.

**Signal 2 — `requirements_matrix.md` lookup**: Currently applies to the 16 requirements with `implements_flows`. The lookup chain is: requirement → `implements_flows[].id` → find flow directory → check for `cluster_matrix:` frontmatter → read that matrix OR the flow's own `requirements_matrix.md` → scan "Suggested Package" column for matching rows.

**Edge cases identified**:
- **Multiple flows, multiple matrices**: A requirement could implement FLOW-002 and FLOW-004. FLOW-002 has its own old matrix AND a cluster matrix. The skill must prefer the cluster matrix (it supersedes single-flow matrices). Goal.md handles this by checking `cluster_matrix:` first.
- **No matrix exists for a flow**: If a flow has no matrix yet (e.g., a new flow just approved), Signal 2 silently falls through to Signal 3. Correct behavior.
- **Matrix row matching**: "Search matrix rows for a 'Suggested Package' value whose description aligns with the AC" — this requires the AI to semantically match an AC description against matrix gap descriptions. Appropriate for an AI skill, but the word "aligns" is vague. Recommendation: make this "whose Gap Description covers the same functional area as the AC".
- **"Suggested Package" column values are chunk labels, not package IDs**: The actual matrix data uses labels like "Core Protocol Delivery", "Scope & Privacy Controls", "Notification System". These must be fuzzy-matched to RELEASE_BACKLOG.md IDs ("Data Transfer Core", "Transfer Encryption", etc.). This two-hop matching (matrix chunk label → backlog package ID) is non-trivial but appropriate for LLM judgment.

**Signal 3 — semantic analysis**: Fallback for requirements without flow origins. Compares AC text against package `description` and `source.scope`. This is where most REQ-PROC-* requirements will land — and correctly be flagged as "no match / skip".

**Risk**: The skill reads "the full requirement body" for semantic analysis. For large requirements this could consume significant context. Mitigation: the skill processes one requirement at a time and shows proposals incrementally.

**Signal 4 — sibling ACs**: Good fallback. The "unless clearly belongs to a different capability area" clause is inherently subjective. This is fine for an AI skill (LLM judgment) but means the reasoning shown to the user must be transparent.

**Edge case not covered**: What if a requirement has some ACs assigned (from a previous partial run) and some not? The goal.md handles this implicitly through Signal 4, but the gap scanner (Deliverable 1) should explicitly show only the unassigned ACs, not all ACs. The goal.md output example shows this correctly.

**Ordering assessment**: The signal priority order is correct. Signal 1 is highest-confidence (explicit annotation), Signal 2 is flow-traceable (matrix lookup), Signal 3 is inference (semantic), Signal 4 is inheritance (sibling). A lower-numbered signal should always be preferred when it produces a result.

### Risk Assessment

1. **"41 unassigned requirements" count may be stale**: The urgency_reason states "41/95 requirements have no target_package". Based on current grep data, ~54 requirements files have at least one `target_package:` line, and ~93 have `trackable_items:`. The gap count is approximately (93 - 54) = 39 files with zero assignments, plus some partial assignments in the 54. The actual number should be verified by the gap scanner itself — the AC in goal.md says "Manual test: run gap scanner -> shows 41 unassigned requirements" which may need adjusting.

2. **Process requirements (REQ-PROC-*) dominate the unassigned set**: Many of the ~39 fully-unassigned requirements are REQ-PROC-*. The skill correctly allows skipping these. However, the gap scanner output will be noisy with process requirements. Consider adding a `--category functional` filter or grouping output by category.

3. **The `release_chunk` field does not exist yet**: Signal 1 will never fire until `requ-explore` starts writing this field. The skill must not error on its absence.

4. **AC text field may be absent**: Not all requirements have `text:` on their AC entries. The gap scanner must handle `- id: AC-01` without a text field gracefully (show ID only).

5. **Deliverable 4 loop behavior**: Action 6 invokes another skill (`requ-assign-packages`). After that skill completes, the release-plan skill's "return to Step 2" loop behavior needs consideration. Goal.md does not address whether control returns to release-plan after the invoked skill finishes.

6. **Large requirement count**: Processing 41+ requirements interactively (one-by-one confirmation) could be tedious. The skill should support batch confirmation ("accept all proposals for this category") in addition to per-requirement review.

### Recommendations

1. **Deliverable 1**: Document that a new `parse_unassigned_items()` function is needed. Handle missing `text:` field by showing ID only. Add `--category` filter or group output by functional/non-functional/process.

2. **Deliverable 2**: 
   - Specify that fuzzy matching is LLM semantic judgment (not algorithmic — this is an AI skill, not a Python script).
   - Add batch confirmation mode: "Accept all proposals? [y/n/review-individually]"
   - Clarify Signal 2 matrix preference: cluster matrix supersedes single-flow matrix.
   - Handle the case where AC has no `text:` field: read the markdown body section for AC descriptions.

3. **Deliverable 4**: Add a note that after Action 6 completes, control returns to the release-plan Step 2 menu (consistent with "After each action, return to Step 2").

4. **AC gap**: The "41 unassigned" count in AC-08 should be softened to "shows unassigned requirements (expected: approximately 41)" since the exact number depends on timing.

5. **Missing AC**: Add an acceptance criterion for: "Process requirements (REQ-PROC-*) are handled gracefully — user can skip them without error."
