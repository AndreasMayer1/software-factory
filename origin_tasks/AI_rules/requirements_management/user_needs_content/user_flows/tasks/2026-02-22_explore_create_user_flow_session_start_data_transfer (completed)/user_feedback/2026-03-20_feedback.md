# Corrections and feedback

## happy path

### phase 1

- "Share with therapist" prompt or indicator on the home screen: That's UX/UI design detail, not part of the user flow. There will be a transfer entry in the apps main navigation. (label tbd).
- App with client role always starts in the data entry screen.
- One UX note: My assumption is that we can use progressive disclosure for the limit the data step 3. I think 90% of the users just want to send everything since last transfer. Another note: Maybe it is already included later in the document, but a user might want to "create a bundle", that means define what he wants to share already before the session. He could also include information that is not part of the questionaire plan that the therapist assigned to him. 
- step 4: We don't need a waiting for therapist device notice. We use animated qr codes to transfer as primary transfer channel. That means that the animated qr code is displayed. But the user must also have the option to:
    - a) change to the file transfer approach manually. This file transfer will probably work via encrypted file that gets attached to an email, but details are tbd.
    - b) select that this is a remote session and he is in a video call.
- Addition to step 4: The app shows how long the transfer will take with the current settings. The app will ask the user if he wants to use file transfer instead if the duration is longer than 2 minutes. But as noted above, the app allows the user to select the file transfer regardless of this, because maybe he wants to send data without haveing a visual channel to the therapist.
- step 5: changes accordingly. Therapist uses a laptop or desktop computer with webcam. Therefore we probably need another step: The client holds his phone with the animated qr code in the view of the therapists camera. We assume a distance from camera to smartphone of 20 cm, which is comfortable to do. But since we don't know the room setup, the app provides a mechanism on the sender side to "increase the working distance", which reduces the qr level.
- step 8: therapist can discard the transfered data, UX detail: but that must cause a verifiation prompt because the data transfer can take a while and both will be really annoyed if they have to do it again if the button is pressed by mistake. The data must stay available even if the phone is locked. That means that the data is technically saved permanently, but for the user it looks like if he can confirm or reject the received data at this point. 
- Step 8: Correction: I thought about it and I do NOT want to show this confirmation screen I described before. Unless you see why our personas would need it. I think the user flow is much smoother if the app just directly opens step 9 without a data received summary screen. And the data visualization is actually the best data received summary we can imagine, because it displays the received data and the users directly see if it's correct. That's more than a summary screen could do. or, please investigate.
- Step 9: with the correction from abocve: no tab on open needed.
- Yes the view is configuerd based by protocol type, but please add that the details are not part of this flow, because it may be influenced by other factors as well or the layout is embedded in the protocol directly, that would also be an option. Keep it open.
