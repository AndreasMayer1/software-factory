### missing: therapist step (before step 5)

The flow currently has no step describing how the therapist opens the receive screen. This is missing and needs to be added before Step 5:

- The therapist opens the receive screen via a dedicated entry in the navigation bar/rail — same pattern as the client side. This entry is intentionally prominent: receiving client data is one of the most important workflows in the app, arguably even more important for the therapist than the transfer step is for the client.
- Alternative entry point: the therapist may also navigate to a specific client's profile and start the data receive from there. This must be supported because many therapists will look for this option in the client profile. However, it is just a shortcut link — it leads to the same receive screen from the navigation bar/rail. No separate flow needed.
- Client identification on the receive screen: the therapist does NOT need to manually select the client. The receiving app identifies the client automatically via a small, separately encrypted header block transmitted at the start of the QR sequence (before the main fountain-coded data, but it's repeated in invervalls, so that not all qr codes has to be transfered if the first code was missed). The app tries all known pairing keys against this header; the key that decrypts it successfully identifies the client. This happens after the first few QR frames — very early in the transfer. The therapist's receive screen therefore does not need a client selector in the normal case; it just shows "receiving..." and then displays the client name once identified. The same mechanism works for file import — the file contains the same encrypted header block, and the app identifies the client automatically by trying all pairing keys. Manual client selection is only needed when no pairing exists yet (new client), and that applies equally to QR and file transfer.

## exceptions

### new exception: app not installed on one device

One of the two parties always has the app already installed (otherwise this flow could never have been reached). But the other side may not. Both cases need to be considered separately, because the UX and recovery differ.

#### Case A: Client has app, therapist does not

The client arrives with data to transfer, but the therapist has not installed the app yet.

- The client's side of the flow works fine (data entry, data scope) — but there is no receiving device.
- The therapist cannot participate in the QR transfer or file import.
- Recovery: Therapist installs the app. For the therapist-side app (desktop/laptop), this may involve downloading directly (not from an app store). Installation and pairing then happen during or after the session, and the transfer is deferred to the next session.
- Note: If the therapist has no app, pairing has also not happened yet — this exception likely overlaps with Exception 2.1A (first-time pairing). Consider whether to merge or cross-reference.

#### Case B: Therapist has app, client does not

This is the more common case (therapist introduces the app to the client). It is already handled in FLOW-002 Exception 1.2.

- For FLOW-003: if the client arrives without the app, there is nothing to transfer. The session proceeds without data.
- Recovery: Same as FLOW-002 Exception 1.2 — therapist shows an app store reference, client installs after the session, transfer happens at the next session.
- Reference FLOW-002 Exception 1.2 rather than duplicating the logic.
