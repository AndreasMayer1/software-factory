### step 8: transfer completion detection (replaces current explicit confirmation button)

The current explicit success/failure confirmation button at Step 8 is replaced by a time-based detection model combined with a single "Discard" override button. The design is as follows:

**Time-based detection:**

The app calculates the expected minimum transfer duration based on data volume and QR density. Three zones are defined:

- **Under calculated duration** (screen closed before transfer could possibly be complete): Transfer is not marked as successful. A non-blocking, non-shaming warning is shown to the client: the exact copy is TBD, but it must not blame or pressure. Nothing is marked as sent. Data remains available for the next transfer.

- **Over calculated duration** (screen open at least as long as transfer requires): Transfer is marked as successful optimistically — no user action required. Entries are marked as "shared." This applies regardless of how the client exits the screen: explicit close, device lock, app minimized, home button — any exit counts.

- **Grey zone (calculated duration to calculated duration + ~5 seconds)**: Same optimistic marking as above, but a subtle notice is stored and shown at the top of the Data Scope Screen in the next session: e.g. "The last transfer may have been incomplete — please verify the date range below." Exact copy TBD. The ~5-second buffer accounts for the time the client needs to walk to the webcam and position the phone before the QR scan can actually begin.

**"Discard transfer" button:**

A "Discard transfer" (or equivalent label — exact copy TBD) button is always visible on the QR Transfer Screen. Tapping it at any point — regardless of how much time has elapsed — immediately cancels the transfer: nothing is marked as sent, no data leaves the device. This is the explicit user override for "this did not work."

A secondary positive action button ("Complete transfer" or similar — exact copy TBD) may be shown alongside the Discard button. It is not required for the optimistic-success model to function — it exists for users who want to explicitly confirm. Tapping it marks entries as sent immediately, without waiting for the time threshold.

**Implications for the "shared marker" domain concept:** The shared marker is now set either (a) automatically when the screen is closed after the time threshold, or (b) immediately when the client taps the positive action button. It is never set if the client taps Discard, regardless of elapsed time.

**Implications for file transfer:** File transfer retains optimistic marking on export — entries are marked as sent the moment the file is shared via the system share sheet. The Discard button is not applicable to file transfer (the file already exists and the therapist can import it later from email/messaging). No time-based detection needed for file transfer.

**Note on session count display:** The Data Scope Screen must NOT attempt to display how many therapy sessions have passed since the last transfer. Session frequency is not known to the app, and sessions can be skipped or rescheduled. Show only the date range (e.g. "4 weeks — since 3 March") to give the client enough context to notice if a previous transfer may have been missed, without implying incorrect session-count information.

### Gap: Paper fallback / parallel delivery

FLOW-002 Exception 1.8 documents paper + digital parallel delivery (common for first-time protocol users). FLOW-003 has no equivalent. Add an exception covering the case where a client still uses paper alongside the app (e.g. in an early transition phase). Think through what this means for the transfer flow: what does the therapist receive, and how does the session proceed when only partial data is digital?
