# Opus Plan: Persona-Driven Design System Bridge

## Objective

Create a requirements document (REQ-PROC-026) that defines **how** this project bridges user needs (personas, scenarios, flows) to concrete UI/UX design system rules — making every design decision defensible through a traceable chain: *Persona trait → Design constraint → Design rule → Implementation guideline*.

The exploration also identifies what project artifacts must change (skills, `doc/` guidelines, requirement annotations) and produces a follow-up implementation task.

### The core gap

The project has two strong pillars that never touch:

1. **User Needs pillar**: personas with exquisite detail about human constraints (tremors, brain fog, 3-second capture windows, dark-bedroom usage, shoulder-surfer paranoia).
2. **Design System pillar**: rules about touch targets, contrast ratios, loading indicators, UX writing tone.

**Nobody connects them.** When an AI implements a new screen, it reads `doc/presentation.md` and follows rules mechanically — but it doesn't *know* that the 48dp minimum exists because Sophie has ADHD-related motor imprecision, or that dark mode must be truly black because Hanna uses the app in bed at 3 AM.

### Persona trait extraction (design-relevant)

From reading all 13 personas, I extracted these design-relevant trait categories:

| Category | Personas affected | Design implications |
|----------|-------------------|---------------------|
| **Motor impairment** | Jana (tremors during crisis), Sophie (ADHD motor imprecision), Nina (fatigue-reduced coordination) | Large touch targets, generous spacing, error-forgiving interactions |
| **Cognitive load sensitivity** | Max (depression brain fog), David (ADHD <3s window), Nina (Long-COVID brain fog), Sophie (executive dysfunction), Jana (crisis tunnel vision) | Minimal steps, pre-filled defaults, no blank fields, progressive disclosure |
| **Time-pressure constraints** | David (<3 taps), Dr. Turan (3-min appointments), Hanna (3 AM, wants to sleep), Jana (crisis = seconds) | Instant capture, zero-friction flows, auto-save |
| **Light/environment sensitivity** | Hanna (absolute darkness required), Lisa (late night, roommates), Elias (discrete in public) | True dark mode (OLED black), reduced brightness, discrete visual identity |
| **Privacy/discreteness** | Elias (therapy stigma), Michael (career fear), Lisa (Verbeamtung fear), Hanna (partner shouldn't see) | Non-identifiable app appearance, discrete notifications, hide content |
| **Emotional sensitivity** | Max (shame from failed tracking), Sophie (streak-breaking shame), Jana (crisis vulnerability), Lisa (abandonment by system) | No guilt-inducing language, forgiving UX, no streak counters, positive framing |
| **Sensory adaptation** | Hanna (dark room), Prof. Weber (no technology in therapy), Dr. Sarah (desktop in office) | Adaptive themes, print-friendly views, non-clinical appearance options |

### Concrete mapping examples (Persona → Design Rule)

**Example 1: Jana's tremors → Touch target inflation**
- PERSONA-014 (Jana): "hands shake" during crisis, "cannot read small print"
- Design rule: Interactive elements in crisis-mode flows must be ≥64dp (not just 48dp minimum)
- Additional: Increase spacing between destructive actions to prevent mis-taps

**Example 2: Hanna's dark bedroom → True dark theme**
- PERSONA-007 (Hanna): "Light barrier is ABSOLUTE", "White/bright apps are unusable"
- Design rule: Dark mode must use OLED-true black (#000000) background, not Material Dark grey (#121212)
- Additional: Initial app open defaults to system theme; night detection could auto-switch

**Example 3: David's 3-second window → Interaction budget**
- PERSONA-008 (David): "If it takes more than three taps, I've already forgotten why I opened the app"
- Design rule: Core capture flows must complete in ≤3 interactions (tap → input → done)
- Additional: Auto-save on every keystroke, no explicit "save" button

**Example 4: Max's blank-field paralysis → Pre-filled scaffolding**
- PERSONA-002 (Max): "Empty fields feel cognitively overwhelming"
- Design rule: Never show empty text fields without structured prompts or pre-filled defaults
- Additional: Use slider/selection inputs instead of free text where possible

**Example 5: Elias's discrete need → Non-clinical app identity**
- PERSONA-009 (Elias): "cannot bring himself to pull out therapy homework notebook in public"
- Design rule: App icon, name, and default screen must not signal "mental health" or "therapy"
- Additional: No pastel/wellness color palettes; neutral, professional appearance

## Risks

- **Risk**: Requirements document too abstract, not actionable → **Mitigation**: Include concrete examples with persona IDs and file paths
- **Risk**: Methodology adds too much process overhead → **Mitigation**: Design for "lightweight by default, deep when needed" — a simple lookup table for common cases, detailed analysis only for novel patterns
