# Opus Design: Intelligent Task Ordering Rule Set

**Task**: TASK-PROC-042-01
**Parent**: REQ-PROC-042 — Intelligent Task Ordering
**Date**: 2026-04-22
**Status**: Phase 2 complete — design finalized; ready for impl-task derivation
**Author model**: Opus (design), Sonnet (Phase 1 investigation)

---

## Executive Summary

This document designs a **portable, dynamic, token-efficient** system that replaces `scripts/next_tasks.py`'s hardcoded sort key with a declarative rule set. The design has four components:

1. **A rule file** (`.claude/task_ordering_rules.yaml`) — describes THIS project's layers, ordering signals, and dependency heuristics
2. **An evaluation engine** (refactor of `next_tasks.py` + new `scripts/task_ordering/` module) — project-agnostic logic that reads the rule file and applies it
3. **A path-based dependency heuristic** (`scripts/propose_after.py`) — suggests `after:` entries at task creation time without requiring an LLM
4. **A maintenance skill** (`claude-modify-ordering-rules`) — allows the factory to evolve its own ordering rules

The design is **additive, not destructive**: the existing script becomes the fallback when the rule file is absent, and the existing frontmatter fields (`writes_requirements`, `verification_task`, `target_package`, etc.) remain the source of truth for per-task overrides. The rule file describes the defaults — how the engine interprets the broader landscape.

## Part 1: Final Layer Taxonomy

This is the authoritative layer taxonomy for this project. Each layer has a numeric `order` using **sparse integers (10s)** so new layers can be inserted between existing ones without renumbering.

| # | Layer | Order | Path patterns | Produces | Skills |
|---|---|---|---|---|---|
| 1 | `factory_process` | 0 | `requirements_tasks/process/**/tasks/**` | skills, scripts, CLAUDE.md, doc/ updates | requ-explore, task-resolve, code-* (on process files) |
| 2 | `persona` | 10 | `requirements_user_needs/personas/*/tasks/**` | `persona.md` | ux-write-persona |
| 3 | `scenario` | 20 | `requirements_user_needs/personas/*/scenarios/*/tasks/**` | `scenario.md` | ux-write-scenario |
| 4 | `user_flow` | 30 | `requirements_user_needs/user_flows/*/tasks/**` | `flow.md`, `notes.md` | ux-create-flow (→ ux-flow-draft/complete/approve) |
| 5 | `requirement_derivation` | 40 | any, matched by **`source_gap:`** frontmatter | `requirements.md` (gap-targeted) | requ-derive-from-flow → requ-explore |
| 6 | `flow_verification` | 45 | any, matched by **`verification_task: true`** frontmatter | coverage assessment, requirement patches | requ-verify-flow-coverage |
| 7 | `requirement_exploration` | 50 | `requirements_tasks/**/tasks/**` with `type: explore` and no special flag | `requirements.md`, design docs | requ-explore, task-resolve |
| 8 | `ui_design` | 55 | `requirements_tasks/**/tasks/**` with `scope_description` containing "scribble" OR `scribble_task: true` *(new flag, see §1.1)* | `scribbles/v{n}/` | ui-create-scribble, ui-verify-flutter |
| 9 | `implementation` | 60 | `requirements_tasks/**/tasks/**` with `type: impl` or `type: bugfix` | `lib/**/*.dart`, skills, docs | code-simple, code-complex, code-bugfix |
| 10 | `testing` | 70 | `requirements_tasks/**/tasks/**` with `type: impl` AND scope references `test/` or `integration_test/` | `test/**/*.dart` | code-test, code-run-integration |

**Orchestration tasks** (created by `task-create-impl-orchestrator`) are NOT a separate layer. They live at `factory_process` (order=0) but act as generators for `implementation` tasks. Their ordering is controlled by the standard `factory_process` rules.

**Release tasks** are NOT a task-folder layer. The `/release` skill is invoked directly. The engine treats them as out-of-scope.

### 1.1 Layer Classification Priority

A task may match multiple layer paths. The classifier applies rules **in declaration order**; first match wins. This means the rule file order matters and the more-specific rules are declared first:

```
1. factory_process           (path-based, broad)
2. persona                   (path-based)
3. scenario                  (path-based)
4. user_flow                 (path-based)
5. requirement_derivation    (flag: source_gap)              ← must precede layer 7
6. flow_verification         (flag: verification_task: true) ← must precede layer 7
7. requirement_exploration   (type: explore, no special flag)
8. ui_design                 (flag: scribble_task: true)     ← NEW FLAG, see below
9. implementation            (type: impl, type: bugfix)
10. testing                  (impl referencing test/ folder)
```

**NEW FLAG PROPOSAL**: Introduce `scribble_task: true` frontmatter flag for standalone UI scribble tasks. Rationale: scribble work is currently spawned *inside* code-complex/code-simple sessions, but the requirement REQ-PROC-032 implies scribbles can also exist as standalone goal.md tasks. Without a classification flag, they would be misclassified as `implementation` or `requirement_exploration`. The flag is optional; scribble-as-subroutine is unaffected.

## Part 2: Draft Rule File (actual content)

**Location**: `.claude/task_ordering_rules.yaml`
**Rationale for location**: Factory behavior configuration lives in `.claude/` (alongside skills, `factory_flows.md`). The file describes how the factory *interprets* the project, not product content.

```yaml
# Task Ordering Rule Set — Private Mood Tracker Flutter App
# ---------------------------------------------------------------------------
# This file declares the project's task-ordering conventions.
# The evaluation engine (scripts/task_ordering/) reads it to rank open tasks.
#
# HOW TO EDIT:
#   - Use the `claude-modify-ordering-rules` skill when adding/changing rules.
#   - Run `python3 scripts/task_ordering/validate_rules.py` after any manual edit.
#   - Run `python3 scripts/task_ordering/simulate.py` to preview the impact
#     on the current backlog before committing.
#
# SCHEMA VERSION: 1.0
# Older engines will refuse to load newer schemas; bump `schema_version` on
# breaking changes (new top-level keys, removed keys).
# ---------------------------------------------------------------------------

schema_version: "1.0"
project_id: "mood-tracker-flutter"
updated: 2026-04-22

# ---------------------------------------------------------------------------
# LAYERS
# Ordered from most upstream (low order) to most downstream (high order).
# Sparse integers (10s) allow insertion of new layers without renumbering.
# Order determines ranking priority: lower order = higher priority when all
# other signals are equal.
# ---------------------------------------------------------------------------

layers:

  - name: factory_process
    order: 0
    description: >
      Tasks that evolve the factory itself — new skills, scripts, CLAUDE.md
      updates, doc/ guidelines. Cross-cutting; often prerequisites for all
      product work.
    match:
      - path_glob: "requirements_tasks/process/**/tasks/**"
    scope_key: "parent_requirement"   # REQ-PROC-*
    notes: >
      Task ordering within this layer relies on target_package if set,
      otherwise on urgency × impact. Explore tasks precede impl within a
      single requirement.

  - name: persona
    order: 10
    description: >
      Writing or updating persona.md files. Upstream of scenario, flow,
      and requirement work that depends on the persona.
    match:
      - path_glob: "requirements_user_needs/personas/*/tasks/**"
    scope_key: "path_segment[1]"      # persona folder name
    produces: "persona.md"

  - name: scenario
    order: 20
    description: >
      Writing or updating scenario.md files under a specific persona.
    match:
      - path_glob: "requirements_user_needs/personas/*/scenarios/*/tasks/**"
    scope_key: "path_segment[1]"      # persona folder name (inherited scope)
    produces: "scenario.md"
    consumes: [persona]               # same scope_key

  - name: user_flow
    order: 30
    description: >
      Writing or updating flow.md files. Flows can serve multiple personas
      and scenarios, so there is no single scope_key — matching is done via
      the flow's serves_scenarios field.
    match:
      - path_glob: "requirements_user_needs/user_flows/*/tasks/**"
    scope_key: "path_segment[1]"      # flow folder name
    produces: "flow.md"
    consumes: [scenario]              # by serves_scenarios link, not scope_key

  - name: requirement_derivation
    order: 40
    description: >
      Explore tasks that write requirements derived from specific flow gaps.
      Critical path — these block downstream impl work.
    match:
      - frontmatter: { source_gap: "*" }                # any non-empty value
      - frontmatter: { writes_requirements: true }      # equivalent signal
    scope_key: "parent_requirement"
    produces: "requirements.md"
    consumes: [user_flow]             # by source_gap's flow reference

  - name: flow_verification
    order: 45
    description: >
      Verification tasks that check whether requirements derived from flows
      actually cover the flow's behavior. Runs after a bundle of
      requirement_derivation tasks completes; explicit `after:` list gates it.
    match:
      - frontmatter: { verification_task: true }
    scope_key: "verification_bundle"  # cluster identifier
    produces: "coverage_assessment"
    consumes: [requirement_derivation]

  - name: requirement_exploration
    order: 50
    description: >
      Standard requirement exploration tasks (not tied to a specific flow gap).
    match:
      - path_glob: "requirements_tasks/**/tasks/**"
        frontmatter: { type: "explore" }
    scope_key: "parent_requirement"
    produces: "requirements.md"

  - name: ui_design
    order: 55
    description: >
      Standalone UI scribble tasks (as opposed to scribble work embedded in
      a code-simple/code-complex session). Gates implementation for features
      with presentation scope.
    match:
      - frontmatter: { scribble_task: true }
    scope_key: "parent_requirement"
    produces: "scribbles/v{n}/"
    consumes: [requirement_exploration, requirement_derivation]

  - name: implementation
    order: 60
    description: >
      Code implementation tasks. Consume approved requirements + approved
      scribbles (if the requirement has a presentation scope).
    match:
      - path_glob: "requirements_tasks/**/tasks/**"
        frontmatter: { type: "impl" }
      - path_glob: "requirements_tasks/**/tasks/**"
        frontmatter: { type: "bugfix" }
    scope_key: "parent_requirement"
    produces: "lib/**/*.dart"
    consumes: [requirement_exploration, requirement_derivation, ui_design]

  - name: testing
    order: 70
    description: >
      Test tasks — may be TDD-before-impl (ordered with impl) or
      verification-after-impl (ordered after). Classified via scope
      description; no automatic upstream/downstream relationship.
    match:
      - path_glob: "requirements_tasks/**/tasks/**"
        frontmatter: { type: "impl" }
        scope_description_contains: ["test/", "integration_test/"]
    scope_key: "parent_requirement"
    produces: "test/**/*.dart"
    consumes: []   # intentionally empty — test tasks are timing-policy-driven


# ---------------------------------------------------------------------------
# SPECIAL FLAGS
# Frontmatter flags that short-circuit or modify normal ordering.
# The engine treats these as first-class signals.
# ---------------------------------------------------------------------------

special_flags:

  - flag: writes_requirements
    value: true
    effect: priority_boost
    weight: -10000          # large negative = ranks above everything else
    rationale: >
      Requirement-writing explores are critical-path: impl tasks downstream
      cannot start until these complete. They must rank above even
      current-release impl tasks to keep the dependency graph respected.
      This is equivalent to treating them as "layer -1".

  - flag: verification_task
    value: true
    effect: respect_explicit_after
    rationale: >
      Verification tasks always have an explicit `after:` list covering the
      full bundle. No sort-key override is needed — the standard `after:`
      blocking mechanism suffices. This entry documents the expectation.

  - flag: opus_recommended
    value: true
    effect: none
    rationale: >
      Signals Opus should be used when executing; does not affect ordering.
      Listed here to prevent future confusion.

  - flag: cascade_type
    value: "user_needs"
    effect: none_yet
    rationale: >
      Multi-pass cascade tasks have their own internal ordering handled by
      cascade_log.md. Ordering between cascade tasks is driven by their
      pass status, not the ranking engine. Open question: should we add a
      cascade-aware signal later?


# ---------------------------------------------------------------------------
# RANKING SIGNALS
# Ordered list of sort-key components. Each component is a named function
# the engine implements. Earlier components dominate later ones.
#
# IMPORTANT: changing this order changes ordering semantics across ALL tasks.
# Use `simulate.py` to preview the impact before editing.
# ---------------------------------------------------------------------------

ranking_signals:

  - signal: special_flags_weight
    description: "Sum of `weight` from matching special_flags. Lower = higher priority."

  - signal: current_package_scope
    description: "0 if task's target_package matches the active package; 1 otherwise."

  - signal: layer_order
    description: "The layer's numeric order. Lower = higher priority."
    notes: >
      This is the new signal compared to the current script. It gives a
      concrete layer-based dependency signal even when explicit after/awaiting
      are missing.

  - signal: layer_intra_type_rank
    description: "Within a layer, 0 if explore, 1 if impl/bugfix. Only applies if layer has both task types."
    applies_to_layers: [factory_process, requirement_exploration]

  - signal: requirement_in_progress
    description: "0 if any task for this parent_requirement is completed in the current package; 1 otherwise."
    notes: "Prefer finishing a requirement over starting a new one."

  - signal: priority_score
    description: "Negative (urgency × 10 + impact). Lower = higher priority."


# ---------------------------------------------------------------------------
# DEPENDENCY HEURISTICS
# Rules applied at task-creation time to PROPOSE `after:` entries.
# These are suggestions for human review — not auto-applied.
# The heuristic runs via `scripts/propose_after.py`.
# ---------------------------------------------------------------------------

dependency_heuristics:

  - name: same_scope_upstream_layer
    when:
      new_task_layer: any
    propose:
      - select: "open tasks at any layer with order < new_task.layer.order"
        and: "scope_key matches new_task.scope_key"
      - reason: "Upstream layer dependency, same scope"

  - name: requirement_then_implementation
    when:
      new_task_layer: implementation
    propose:
      - select: "open tasks with same parent_requirement at layers [requirement_exploration, requirement_derivation]"
      - reason: "Implementation consumes requirement artifact"

  - name: scribble_then_implementation
    when:
      new_task_layer: implementation
      new_task_parent_requirement_has_presentation_scope: true
    propose:
      - select: "open tasks with same parent_requirement at ui_design layer"
      - reason: "Scribble must be approved before Flutter implementation"

  - name: flow_approval_then_derivation
    when:
      new_task_layer: requirement_derivation
    propose:
      - select: "open tasks at user_flow layer whose flow is not yet approved AND is referenced by new_task.source_gap"
      - reason: "Flow must be approved before requirements can be derived from it"

  - name: bundle_explores_then_verification
    when:
      new_task_layer: flow_verification
    propose:
      - select: "all open requirement_derivation tasks with same verification_bundle"
      - reason: "Verification runs after all bundle explores complete"


# ---------------------------------------------------------------------------
# FALLBACK BEHAVIOR
# What the engine does when a task doesn't match any layer or when the rule
# file is absent/malformed.
# ---------------------------------------------------------------------------

fallback:
  unclassified_layer_order: 999     # ranks last
  unclassified_task_behavior: warn_and_rank_last
  malformed_rules_behavior: use_hardcoded_defaults_and_warn
```

### 2.1 Format choice rationale

**YAML was chosen** because:
- PyYAML is already a dependency (see `next_tasks.py` imports)
- Native support for comments — critical for rationale (each rule has a `notes:` or `rationale:` field that future LLMs will read and respect)
- Anchors/references (though this file avoids them for simplicity)
- Existing frontmatter schema throughout the project is YAML; contributors are already fluent

**TOML was rejected** because nested lists and documents are less ergonomic for the hierarchical rule structure.
**JSON was rejected** because it lacks comments.
**Custom DSL was rejected** as adding implementation and documentation cost without benefits over YAML.

### 2.2 Token efficiency

The file is ~180 lines, ~2,500 tokens. When the update skill (§5) runs, only the relevant layer/signal section is loaded, not the full file. An agent editing the rule set operates with full context without consuming a meaningful share of its window.

## Part 3: Evaluation Engine Design

### 3.1 Minimal-change refactor (recommended)

Keep `scripts/next_tasks.py` as the CLI entry point. Factor the ranking logic into a new module `scripts/task_ordering/`:

```
scripts/
├── next_tasks.py                    (CLI wrapper — unchanged interface)
└── task_ordering/
    ├── __init__.py
    ├── rules.py                     (loads + validates YAML rule file)
    ├── classifier.py                (classify_layer(task, rules))
    ├── ranker.py                    (sort_key(task, rules, ctx))
    ├── dependencies.py              (is_blocked logic, unchanged behavior)
    ├── simulate.py                  (CLI: preview rule changes against backlog)
    ├── validate_rules.py            (CLI: YAML schema check)
    └── defaults.py                  (hardcoded fallback = today's behavior)
```

The existing `next_tasks.py` keeps its CLI surface (`--release`, `--package`, `--count`, `--type`) but delegates to the new module. Output format unchanged → existing skills and automation (e.g. `claude-route` Mode C) keep working.

**Migration path (incremental)**:

1. **Phase A**: Add `task_ordering/` package with the module structure and `defaults.py` encoding current behavior. `next_tasks.py` delegates; all existing tests pass unchanged. No behavior change.
2. **Phase B**: Add `rules.py` to load `.claude/task_ordering_rules.yaml`; if absent, use `defaults.py`. Committing a rules file with the current behavior encoded in it produces identical output.
3. **Phase C**: Extend rules with `layer_order` signal and path-based classification. Run `simulate.py` against backlog; accept the change only if the shift is understood.
4. **Phase D**: Add dependency heuristics (§4) as a separate CLI tool.
5. **Phase E**: Add maintenance skill (§5).

### 3.2 Engine skeleton (pseudocode)

```python
# scripts/task_ordering/ranker.py

from typing import Callable, Dict, List, Any
from .rules import Rules
from .classifier import classify_layer

def sort_key_factory(rules: Rules, context: Dict[str, Any]) -> Callable:
    """Return a sort_key function tailored to the current ranking context.

    context includes:
      - active_package: str | None
      - requirements_in_progress: set of REQ-IDs
      - completed_ids: set of TASK-IDs
      - known_ids: set of TASK-IDs
    """
    signal_funcs = [_build_signal(name, rules, context) for name in rules.ranking_signals]

    def sort_key(task: Dict[str, Any]) -> tuple:
        task['_layer'] = classify_layer(task, rules)  # memoized on task dict
        return tuple(f(task) for f in signal_funcs)

    return sort_key


def _build_signal(signal_name: str, rules: Rules, ctx: dict) -> Callable:
    if signal_name == "special_flags_weight":
        return lambda t: _sum_flag_weights(t, rules)
    if signal_name == "current_package_scope":
        return lambda t: 0 if t.get("target_package") == ctx["active_package"] else 1
    if signal_name == "layer_order":
        return lambda t: t["_layer"]["order"]
    if signal_name == "layer_intra_type_rank":
        return lambda t: _intra_type_rank(t, rules)
    if signal_name == "requirement_in_progress":
        return lambda t: 0 if t.get("parent_requirement") in ctx["requirements_in_progress"] else 1
    if signal_name == "priority_score":
        return lambda t: -((t.get("urgency", 0) * 10) + t.get("impact", 0))
    raise ValueError(f"Unknown ranking signal: {signal_name}")
```

```python
# scripts/task_ordering/classifier.py

import fnmatch
from typing import Dict, Any

def classify_layer(task: Dict[str, Any], rules: "Rules") -> Dict[str, Any]:
    """Return the first matching layer for a task.

    Match precedence:
      1. Layers with `frontmatter:` criteria (more specific) — in declaration order
      2. Layers with `path_glob:` + frontmatter type filters
      3. Layers with `path_glob:` only
      4. `fallback.unclassified_layer_order` sentinel layer
    """
    for layer in rules.layers:
        for match_rule in layer.match:
            if _matches(task, match_rule):
                return layer
    return rules.fallback_layer()


def _matches(task: dict, rule: dict) -> bool:
    if "path_glob" in rule:
        path = task.get("path", "")
        if not fnmatch.fnmatch(path, rule["path_glob"]):
            return False
    if "frontmatter" in rule:
        for k, v in rule["frontmatter"].items():
            task_value = task.get(k)
            if v == "*":
                if not task_value:
                    return False
            elif task_value != v:
                return False
    if "scope_description_contains" in rule:
        desc = (task.get("scope_description") or "").lower()
        if not any(s.lower() in desc for s in rule["scope_description_contains"]):
            return False
    return True
```

### 3.3 Rule file loading and validation

```python
# scripts/task_ordering/rules.py

import yaml
from dataclasses import dataclass
from pathlib import Path

@dataclass
class Rules:
    schema_version: str
    layers: list
    special_flags: list
    ranking_signals: list
    dependency_heuristics: list
    fallback: dict

def load_rules(path: Path = Path(".claude/task_ordering_rules.yaml")) -> "Rules":
    if not path.exists():
        from .defaults import hardcoded_rules
        return hardcoded_rules()
    try:
        with path.open() as f:
            data = yaml.safe_load(f)
        _validate_schema(data)
        return Rules(**_normalize(data))
    except Exception as e:
        import sys
        print(f"WARNING: Could not load {path}: {e}. Falling back to hardcoded defaults.",
              file=sys.stderr)
        from .defaults import hardcoded_rules
        return hardcoded_rules()
```

## Part 4: Heuristic Dependency Detection

### 4.1 Algorithm

```python
# scripts/propose_after.py

def propose_after(new_task_path: str, new_task_metadata: dict, rules: Rules) -> list:
    """Return a ranked list of (task_id, reason) tuples to propose as `after:`.

    Does NOT write to any file — emits to stdout for skill consumption.

    Runtime: O(N) where N = number of open tasks; no LLM needed.
    """
    new_layer = classify_layer({"path": new_task_path, **new_task_metadata}, rules)
    new_scope = extract_scope_key(new_task_path, new_task_metadata, new_layer)
    open_tasks = load_open_tasks()   # reuses next_tasks.load_tasks()

    proposals = []
    seen_ids = set()

    for rule in rules.dependency_heuristics:
        if not rule.applies_to(new_layer, new_task_metadata):
            continue
        for task in open_tasks:
            if task["task_id"] in seen_ids:
                continue
            if task["status"] in TERMINAL_STATUSES:
                continue
            if rule.matches(task, new_task_metadata, new_scope, rules):
                proposals.append((task["task_id"], rule.reason))
                seen_ids.add(task["task_id"])

    return proposals


def extract_scope_key(path: str, metadata: dict, layer: Layer) -> str:
    """Extract scope key based on layer definition.

    Examples:
      path_segment[1]       → second folder in the path
      parent_requirement    → frontmatter field
      verification_bundle   → frontmatter field
    """
    spec = layer.scope_key
    if spec.startswith("path_segment["):
        idx = int(spec[len("path_segment["):-1])
        return path.split("/")[idx] if idx < len(path.split("/")) else ""
    if spec in metadata:
        return str(metadata[spec])
    return ""
```

### 4.2 Edge cases and how the algorithm handles them

| Edge case | Behavior |
|---|---|
| Upstream task is **completed** | Excluded (terminal status filter) |
| Upstream task is **blocked** | Included (a blocked task can still produce artifacts later; `after:` should reflect that) |
| Many upstream tasks match | All proposed; user picks; skill can limit to top N by priority_score |
| No upstream tasks match | Empty proposal — `after: []` |
| Scope key cannot be extracted | Log warning; skip rule, try next |
| Task path matches no layer | Emit warning; propose nothing; user fills in manually |
| Circular proposal (rare) | Detected via known-ids set; drops later duplicates |
| Flow referenced by `source_gap:` doesn't exist | Log warning; skip that heuristic; user sees no proposal for that rule |

### 4.3 Integration with task-create skills

The existing task-creation skills (`task-create`, `task-create-impl`, `requ-derive-from-flow`) gain a new step:

1. After computing the target folder path and filling frontmatter
2. Before writing `goal.md`
3. Run: `python3 scripts/propose_after.py --path <target-folder> --metadata <json>`
4. Present proposals to the user (or auto-accept "same package continuation" in automated mode, as task-create-impl already does)
5. Write confirmed proposals to `after:`

**Output format** (for machine parsing):
```
TASK-FUNC-007-03   same package continuation
TASK-FUNC-007-05   upstream layer dependency, same scope
```

### 4.4 What the heuristic does NOT do

- It does **not** propose `awaiting:` entries. External blockers (flows awaiting approval, design decisions) require human judgment and cannot be inferred from folder structure alone. The heuristic is conservative: it proposes only direct artifact-consumption relationships.
- It does **not** retroactively update `after:` entries on existing tasks when a new upstream task is created. That would require a separate reconciliation pass (already handled by `scripts/reconcile_dependencies.py`).
- It does **not** call `next_tasks.py`. It is a **creation-time** tool; `next_tasks.py` is a **ranking-time** tool. They share the rules file but have independent lifecycles.

## Part 5: The "Update Ordering Rules" Skill

### 5.1 Skill outline

**Name**: `claude-modify-ordering-rules`
**Location**: `.claude/skills/claude-modify-ordering-rules/skill.md`
**Analogous to**: `claude-modify-skill`

### 5.2 When triggered

Three trigger modes:

1. **On demand**: User invokes `"Use claude-modify-ordering-rules skill for <change description>"` — most common.
2. **Engine hint**: The evaluation engine emits a warning (to stderr) when it classifies more than X% of open tasks as `unclassified`. The next time a user sees that warning, they invoke the skill to fix it.
3. **Skill-creation trigger**: `claude-create-skill` ends by asking: *"Does this new skill produce a new task type? If yes, use `claude-modify-ordering-rules` to register it."*

### 5.3 Skill workflow

```
Step 1 — Read state
  - Read .claude/task_ordering_rules.yaml
  - Read the change description from the user
  - Read current open tasks to understand what exists

Step 2 — Classify the change
  - New layer?              → add to `layers:` + update dependency_heuristics
  - New special flag?       → add to `special_flags:`
  - New ranking signal?     → add to `ranking_signals:` (with caution)
  - New dependency rule?    → add to `dependency_heuristics:`
  - Edit to existing rule?  → edit in place, flag for simulation

Step 3 — Propose diff
  - Show the user the YAML diff
  - Explain what ordering effect the change will have
  - Highlight any cross-references that need co-update (e.g. a new layer
    may need a new `consumes:` entry in layers that depend on it)

Step 4 — Simulate
  Run: python3 scripts/task_ordering/simulate.py --proposed-rules <tmpfile>
  Output:
    - Old vs new top-20 tasks
    - Any task whose position shifts by >= 5
    - Any task that becomes unclassifiable
  Present to user.

Step 5 — Approve
  If user approves → write rule file, commit.
  If user rejects  → discard diff, start over.

Step 6 — Propagate
  If a new layer was added, remind the user:
    - Does any existing skill need to know about this layer?
    - Update factory_flows.md if the information pipeline changed
    - Update requirements_tasks/STATUS.md generator if needed
```

### 5.4 Validation rules (enforced by the skill)

Before accepting a change:

- **Schema version check**: any change that adds/removes top-level keys → bump `schema_version`
- **Layer order uniqueness**: no two layers may have the same `order`
- **Layer order sparsity**: recommend leaving >=5 gap between existing layers
- **Dependency cycle check**: no layer may `consume:` a downstream layer
- **Ranking signal conservation**: if a signal is removed, warn that all tasks using it may shift dramatically
- **Glob sanity check**: each `path_glob` must match at least one existing folder (warn if zero matches — possibly a typo)

### 5.5 Skill ergonomics

The skill must be **fast** for small changes (adding a single layer) and **thorough** for large changes (restructuring the priority order). It should:

- Default to Sonnet for declarative edits (adding a layer, a flag, a heuristic)
- Switch to Opus (via `claude-switch-opus`) when:
  - Changing `ranking_signals` order (high blast radius)
  - Removing a layer (may break classification)
  - Adding a cross-layer dependency heuristic that affects many tasks
- Always run `simulate.py` before committing

## Part 6: Open Questions, Risks, and Known Gaps

### 6.1 Open questions

1. **Flow scope key ambiguity.** A flow often serves multiple scenarios across multiple personas. The `scope_key: path_segment[1]` maps to the flow folder name, but scenario-to-flow coupling is many-to-many. For dependency proposals, should "scenario X updated" block "flow Y edit" if flow Y's `serves_scenarios` mentions X? The heuristic currently says no (same-scope-only), but a richer rule is possible.

2. **Test task timing.** TDD wants tests before impl; regression wants tests after. The current rule places `testing` at order 70 (after impl). This is correct for regression tests but wrong for TDD. Recommendation: split `testing` into two flags (`test_before_impl: true` and `test_after_impl: true`) or use task-level `after:` explicitly. Deferred until a concrete test task appears in the backlog to validate the choice.

3. **Scribble task integration.** The design introduces a `scribble_task: true` flag but there are zero instances today. If scribble work stays embedded in `code-complex` invocations, the flag may never be used. Should the layer be removed until the first standalone scribble task is actually created? Argument for keeping: the rule set is specification, it should be complete. Argument for removing: dead rules rot.

4. **Process task package inheritance.** Process tasks often lack `target_package` because they are cross-cutting. The current engine treats absent packages as "rank last within the package filter," which is the wrong heuristic for `writes_requirements` explores and some factory tasks. The new design handles `writes_requirements` via special_flag weight, but other factory tasks still fall to "rank last." Proposal: add a `factory_urgent: true` flag for critical factory work. Tracked as a follow-up.

5. **Cascade-aware ordering.** Tasks with `cascade_type: user_needs` have their own internal ordering (Pass 1 → 2 → 3 → 4). The ranker currently treats all passes equally. Should the ranker boost the pass that is currently active? Unclear — cascade tasks are rare; defer.

6. **Multi-project rule file.** Can one rule file serve multiple adjacent projects in a monorepo? The design assumes one rule file per project (`.claude/` in project root). Multi-project support is out of scope for v1.

### 6.2 Risks

| Risk | Likelihood | Severity | Mitigation |
|---|---|---|---|
| Rule file YAML corrupted by a manual edit | Medium | High | `validate_rules.py` CLI; engine falls back to defaults on parse error with visible warning |
| Layer ordering change silently shifts many tasks | Medium | High | `simulate.py` mandatory before writing rule file; update skill enforces it |
| Glob patterns don't match on Windows path separators | Low | Medium | Normalize paths in classifier (always use forward slashes) |
| Rule file drifts from script-hardcoded defaults | Medium | Low | Regression test: default-rules.yaml must produce byte-identical output to current `next_tasks.py` |
| New skill creates a task type but no one updates the rule file | High | Medium | `claude-create-skill` ends with an explicit question; `task-create` warns when a created task falls to `unclassified_layer_order` |
| Frontmatter field name drift (e.g. `writes_requirements` renamed) | Low | High | Schema version bump required for any frontmatter contract change; keep matching keys stable |
| Dependency proposals become noisy (false positives) | Medium | Low | Each proposal has a `reason:` field; user can see why and reject; proposals are suggestions not auto-applied |
| Engine falls back silently to defaults and nobody notices | Low | Medium | Warning goes to stderr; `--verbose` flag surfaces the source of loaded rules in CLI output |

### 6.3 What this design does NOT solve

- **LLM-level task understanding.** The engine still cannot reason about *what a task does*. "This explore actually doesn't produce anything new" remains a human judgment. The design reduces noise, not error.
- **Detection of implicit dependencies across projects or external systems.** Only within-project folder structure is analyzed.
- **Priority arbitrage between equally-ranked tasks.** When two tasks tie on every signal, their relative order depends on iteration order of the scan, which is filesystem-dependent. Not an issue in practice because urgency × impact breaks nearly all ties.
- **Backfilling `after:` on existing tasks.** A one-time reconciliation pass against existing tasks is a separate task, outside this design.

## Part 7: Portability Assessment

### 7.1 Requirements on a hosting project

A project that wants to use this engine must provide:

1. **Task frontmatter with at minimum**: `task_id`, `status`, `type`. Other fields (`target_package`, `parent_requirement`, `after`, `awaiting`) are optional but unlock more signals.
2. **Folder-based task organization**: each task in its own folder with a `goal.md` (or equivalent — configurable in a future rule-file extension).
3. **A `.claude/task_ordering_rules.yaml` file** describing the project's specific layers, paths, and flags. Without this file, the engine uses hardcoded defaults that describe THIS project — not useful for other projects.
4. **Python 3.9+** with `pyyaml` installed.

### 7.2 What is NOT assumed

- **Clean Architecture.** The engine does not assume Domain/Data/Presentation layers; those are project-specific and would be encoded in `layers:` only if relevant.
- **Flutter/Dart.** Language-agnostic. `testing` layer's `test/**` path is configurable.
- **The persona/scenario/flow user-needs hierarchy.** This is a convention of this project; a different project omits those layers from its rule file.
- **The `requirements_tasks/functional/non-functional/process/` taxonomy.** Purely project-specific paths.
- **A release cadence or package model.** The `current_package_scope` signal is optional; projects without packages skip it in `ranking_signals`.

### 7.3 Onboarding a new project

Steps for a new project to adopt the engine:

1. Copy `scripts/task_ordering/` (module + CLIs)
2. Copy `scripts/next_tasks.py` and `scripts/propose_after.py` (thin CLI wrappers)
3. Write `.claude/task_ordering_rules.yaml` from scratch OR start from the template shipped in `scripts/task_ordering/rules_template.yaml`
4. Run `python3 scripts/task_ordering/validate_rules.py` to check schema
5. Run `python3 scripts/next_tasks.py` and visually inspect the ranking; iterate on the rule file until ordering makes sense

**Effort estimate** for a new project to adopt: 2–4 hours, assuming the project already has task folders with YAML frontmatter.

### 7.4 What makes this design truly portable

The **engine is language-neutral in its rule schema** (it accepts any `layer name → path glob → frontmatter predicate` mapping) and **data-neutral in its ranking signals** (each signal is a named function; new signals can be added to the code and declared in the rule file).

The **rule file is the only project-specific artifact**. Two projects sharing the engine still maintain distinct rule files, each describing their conventions. The engine is the reusable part; the rule file is the configuration.

## Part 10: User Decisions and Design Amendments (2026-04-22)

This section records explicit decisions made during design review, with rationale, to inform future rule changes.

### 10.1 Ranking signal rationale — `current_package_scope` before `layer_order`

**Decision**: `current_package_scope` is intentionally placed before `layer_order` in the ranking tuple. This means current-release implementation tasks rank above upstream tasks (e.g. user flow writing) that have no package assignment.

**User rationale**: Writing user flows requires intensive manual user involvement — the AI cannot produce good flows without significant human feedback. Therefore, user flow tasks are always started deliberately by the user, not by the autorun. In contrast, implementation tasks can be executed fully autonomously by the AI. Prioritizing current-release impl tasks over unscheduled upstream tasks is therefore the correct behavior for autonomous operation.

**Implication for future changes**: Before moving `layer_order` above `current_package_scope`, revisit whether the upstream task type in question still requires heavy manual involvement. If the AI's ability to autonomously write user flows improves significantly, this trade-off may shift.

### 10.2 Reverse dependency detection — deferred (Option 3)

**Decision**: The `propose_after.py` heuristic will NOT retroactively update existing downstream tasks when a new upstream task is created.

**User rationale**: Try the simpler approach first. The `layer_order` ranking signal already ensures upstream tasks are prioritized correctly at ordering time, so missing `after:` entries on existing tasks are unlikely to cause incorrect behavior in practice. If this turns out to be insufficient (e.g. tasks are started that should have been blocked), a reverse-pass reconciliation tool can be added later.

**What this means**: `after:` fields are best-effort, not exhaustive. The engine must not assume `after: []` means "no dependencies" — it means "no explicitly declared dependencies."

### 10.3 Test task ordering — tests after implementation

**Decision**: The `testing` layer stays at order 70 (after `implementation` at 60). TDD ordering is not implemented.

**User rationale**: The user would ideally prefer TDD (tests written before implementation), but empirical experience shows the AI never successfully writes tests before implementation — even with explicit prompting. The hypothesis is that the AI requires an existing implementation to write meaningful tests. This may be revisited if AI capability improves. For now, tests run after implementation.

**Secondary note**: Explicit standalone test tasks (rare in this project) would theoretically benefit from running before implementation. However, given the AI's current limitations with TDD, this is also deferred. If a standalone test task is ever created with the intent of TDD, the user will set an explicit `after:` entry pointing to the impl task to reverse the default.

### 10.4 Scribble task flag — introduce now

**Decision**: Introduce `scribble_task: true` frontmatter flag in the initial rule file, even though no standalone scribble tasks exist yet.

**Rationale**: The rule set is a specification, not a reflection of current backlog state. Having the layer defined prevents misclassification if scribble tasks appear in the future.

### 10.5 `factory_urgent` flag — introduce now

**Decision**: Introduce `factory_urgent: true` as a new special flag in the initial rule file.

**Rationale**: Process/factory tasks often lack `target_package` (they are cross-cutting) and therefore fall to "rank last" under `current_package_scope`. Some factory tasks are genuinely urgent prerequisites for product work and should be elevated. The `writes_requirements` flag already handles the most critical case (requirement-writing explores), but other urgent factory work needs a signal too.

**Effect**: `factory_urgent: true` should receive a priority boost in `special_flags_weight`, less aggressive than `writes_requirements` (e.g. weight −1000 vs −10000). Exact weight to be determined during implementation (Task 1).

### 10.6 Cascade-aware ordering — deferred

**Decision**: No cascade-aware ordering signal for now. Defer.

**Background**: Tasks with `cascade_type: user_needs` have internal phases (Pass 1–4) managed via `cascade_log.md`. The question was whether the ranker should boost the currently active pass. This was deferred because cascade tasks are rare and the internal ordering is already managed within the task itself.

### 10.7 New project onboarding — init mode needed

**Gap identified**: The current design (Part 7.3) describes manual onboarding only (2–4 hours, write rule file from scratch or template). There is no mechanism to analyze an existing project and suggest a starting rule file.

**Proposed addition**: An init mode in `claude-modify-ordering-rules` (or a separate `claude-init-ordering-rules` skill) that:
1. Scans the existing folder structure and frontmatter fields
2. Proposes a starter layer taxonomy
3. Uses the opus-advisor agent (`claude-switch-opus`) for the inference step — no need to hardcode heuristics, the AI can reason about the project structure
4. Presents proposals to the user for review before writing the file

This is a follow-up item, not part of the initial 10-task implementation breakdown.

### 10.9 Cascade-in-flight boost — prevent layer drift

**Problem identified**: A cascade task that is partially complete (e.g. Pass 1 done, Pass 2 in progress) competes equally with new unrelated work in the ranker. If new higher-priority tasks appear, the cascade stalls mid-flight. Over time, multiple stalled cascades at different stages create layer drift: personas describe one version of the user, flows describe another, requirements yet another, and code a fourth.

**Decision**: Introduce a `cascade_active: true` frontmatter flag. When the cascade management skill advances a task from Pass 1 → Pass 2, it sets this flag. The flag is cleared when the cascade completes all passes.

**Effect in ranker**: `cascade_active: true` receives a `special_flags_weight` boost (proposed weight: −500). This places an active cascade above ordinary work but below `writes_requirements` tasks (−10000). Once started, a cascade is always completed before unrelated new work is prioritized above it.

**User rationale**: Incomplete cascades are invisible technical debt. A persona change that never propagates to requirements means the AI is implementing features for a persona that no longer matches the product vision. The `cascade_active` flag makes the in-flight state visible to the ranking engine so it can enforce completion.

**Implementation note**: The cascade management logic (the skill that advances passes) is responsible for setting and clearing this flag — the ranking engine only reads it.

### 10.8 Ranking signal rationale fields — required in rule file

**Gap identified**: The `ranking_signals` entries in the YAML rule file have `description:` fields but no `rationale:` fields. The `rationale:` and `rationale_source:` fields exist on layers and special_flags but were not applied consistently to ranking signals.

**Decision**: Add `rationale:` and `rationale_source:` fields to every `ranking_signals` entry in the initial rule file (Task 1). The `claude-modify-ordering-rules` skill must read and surface these rationale fields when proposing changes to signal ordering, so the user is reminded of the original reasoning before approving a shift.

**Example** (to be applied to all signals):
```yaml
- signal: current_package_scope
  description: "0 if task's target_package matches active package; 1 otherwise"
  rationale: >
    Placed before layer_order intentionally: current-release impl tasks are
    prioritized over upstream work (e.g. user flow writing) because upstream
    tasks require manual user involvement and are started deliberately, whereas
    impl tasks run autonomously. See §10.1 for full context.
  rationale_source: "user decision, 2026-04-22"
```
