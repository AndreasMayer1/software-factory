# Synthesis — TASK-PROC-045-08 (2026-05-28)

## TL;DR

REQ-PROC-045 was rewritten substantially (not just appended to) to (a) remove the carve-out exempting `process/` and `non-functional/` from epic-enforcement, (b) introduce a sanctioned-taxonomy mechanism with single-axis-per-level rule, (c) require anchor files on every grouping folder with declared inclusion criteria, anti-scope, and sub-axis, (d) commit each top-level category to one named axis (`functional/` = WHO–WHAT, `non-functional/` = system concern category, `process/` = artifact type), (e) define a deterministic placement algorithm and a governance gate for changing the taxonomy. Migration policy and grandfathering language was deleted from the requirement entirely — it lives in follow-up task files. The requirement now describes only the target state.

## Decision path

### Round 1 — Discovery: REQ-PROC-045 already exists with an explicit carve-out

The TASK-PROC-063-01 synthesis identified the carve-out at REQ-PROC-045 §3 line 136 as the blocker. This task's premise was to remove it.

### Round 2 — Anchor file rule for grouping folders

Initial proposal: allow "name-only" grouping folders (no anchor). User pushed back: name alone is insufficient — `workflows/` and `requirements_management/` are both individually plausible names that demonstrably let the same release-related requirement land in either. Conclusion: **every folder containing semantic sub-folders carries an anchor file (`README.md` for groupings, `requirements.md` for epics/atomic).**

### Round 3 — Discovery: overlap is structurally inevitable until the axis is constrained

User raised the deeper point: even with anchor files, two clusters along *different ontological axes* can legitimately both claim the same requirement. Cars-taxonomy analogy: color, brand, vehicle-type are all valid clusterings; using more than one at the same hierarchy level guarantees overlap. Conclusion: **single-axis-per-level is a hard rule; the set of available axes is enumerated and governed.**

### Round 4 — Top-level axis choice for `process/`

Considered four candidates (lifecycle phase / actor / failure mode / artifact type). Artifact type was the only axis where placement was unambiguous for most requirements and where the cross-cutting bucket stayed small and well-defined rather than a dumping ground. Conclusion: **artifact-type axis for `process/`.**

### Round 5 — The axis extends one level up: `process/AI_rules/` dissolves

User observed that the `AI_rules/` ↔ `documentation_rules/` ↔ `tooling_rules/` split at the `process/` level is itself fictitious — most rules apply equally to human and LLM authors. The artifact-type axis extends to `process/` itself, dissolving the AI/doc/tool top-level split. LLM-specific artifacts (skills, prompts, agent configs) become an artifact type in their own right (`skill_and_workflow_rules/`); the "for human vs. for LLM" facet becomes a YAML tag, not a folder level. Conclusion: **`process/` itself adopts the artifact-type axis.**

### Round 6 — Sub-axes are decided lazily, per folder

Each artifact folder declares its own sub-axis in its `README.md` when content forces the choice. REQ-PROC-045 names the meta-rule (single-axis per level, declared in anchor, governance gate for new axes) but does not pre-specify each artifact folder's sub-axis. Conclusion: **lazy sub-axis decisions, governed by the same mechanism.**

### Round 7 — Requirement content rules

User reminded that requirements describe only the target state — no log of old decisions, no migrations, no transient state. The §3 carve-out, "Known structural debt" paragraph, AC-09 grandfathering, and "Non-prefixed folders inside epics" grandfathering note were all transient state language and were deleted entirely. Migration policy (Strangler Fig + debt tracking) lives in follow-up task files, not in REQ-PROC-045. Conclusion: **delete transient state from requirement; create follow-up migration + enforcement tasks.**
