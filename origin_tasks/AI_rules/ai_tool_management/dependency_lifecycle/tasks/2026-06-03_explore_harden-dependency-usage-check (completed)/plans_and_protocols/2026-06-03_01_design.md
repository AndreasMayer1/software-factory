# Design synthesis — hardening the dependency-retirement usage-check

**Task**: TASK-PROC-061-18 · **Date**: 2026-06-03 · **Status**: captured design (pre-decision)
**Subject**: `scripts/release/check_dependency_usage.py` (REQ-PROC-061 AC-11)

This document captures the design produced in the 2026-06-03 conversation, with the
supporting evidence, so it survives context loss. Re-validate the probe data before
implementing — repo state may drift.

---

## 0. How the script works today

Scans `lib/ test/ integration_test/` for `import 'package:<name>/'`. Buckets each
pubspec dependency:
- `directly_imported` — ≥1 matching import
- `indirectly_required` — listed in the hardcoded `INDIRECT_REQUIREMENTS` dict (with a
  named consuming dependency)
- `no_evidence_of_use` — **removal candidate**

Reads **only** `pubspec.yaml` + those three dirs. Always exits 0 (except missing pubspec).
The monthly review writes a proposal to `automation/dependency_reviews/YYYY-MM/`; the
reusable decision task gates actual removal (developer: "approve removal or keep").

**Current removal-candidate output** (probe 2026-06-03):
```
rxdart, bloc_concurrency, local_notifier, mockito, google_fonts,
very_good_analysis, custom_lint, clean_architecture_kit, bloc_lint,
mutation_test, glados
```
This list mixes genuine dead weight with structural false positives, with no way to tell
them apart — that is the core problem.

## 1. Scanned-folders sufficiency (Dart)

**Finding**: For the current repo, the three dirs are sufficient — but by luck + the
allowlist, not by exhaustiveness.

Probe: the only Dart outside the three dirs that imports a pubspec dep is
`scripts/*.dart` importing `path` — already covered by `INDIRECT_REQUIREMENTS`. `test_driver/`
imports only the SDK `integration_test` package (excluded). `test_hive/` imports nothing
relevant. `packages/` (vendored forks) carry their own pubspecs.

**Latent gap**: `test_driver/` is a real Flutter source dir not scanned — today benign
(SDK-only import), but a future driver importing a real dep would false-flag it. Cheap
fix: add `"test_driver"` to `_SOURCE_DIRS`.

---

## 2. C++/native dependencies — the real blind spot

The script is 100% blind to native usage; it only reads Dart imports. Two cases:

- **Case A — native plugin WITH a Dart API** (majority: `camera`, `flutter_zxing` FFI,
  `wakelock_plus`, `window_manager`, `tray_manager`, `screen_capturer_qr`,
  `path_provider`): always imported, so caught incidentally. Harmless.
- **Case B — native effect, NO Dart import** (the true blind spot). Probe found two deps
  with 0 Dart imports:
  - `sqlite3_flutter_libs` — genuinely required (native SQLite for drift), saved **only**
    by `INDIRECT_REQUIREMENTS`.
  - `local_notifier` — **not** in the allowlist → currently emitted as a removal candidate.

**The circular-evidence trap**: `local_notifier` appears in
`generated_plugin_registrant.cc/.cmake` and `GeneratedPluginRegistrant.swift` — but
Flutter auto-generates those from *every* pubspec plugin, so registrant presence is
"declared", not "used". It cannot be used to rule out removal. (`local_notifier` needs
Dart calls to do anything and has none → it is very likely a genuine removal candidate.)

**Consequence**: correctness for native-only deps rests entirely on humans maintaining
`INDIRECT_REQUIREMENTS`, which currently covers only `sqlite3_flutter_libs` among natives.

## 3. The ten improvement items

### #1 — Config-referenced classification (highest impact; proven false positives)
A whole class of dev deps is used via `analysis_options.yaml`, never imported. Probe:
`very_good_analysis` (4 refs), `custom_lint` (3 refs), `clean_architecture_kit` (1 ref).
These are active analyzer/lint plugins — not removable — yet flagged every run.
**Fix**: scan `analysis_options.yaml` (`include:`, `plugins:`, custom_lint rules) →
classify matches as a new `config_referenced` bucket. Removes 3 perennial false positives.
(`bloc_lint` has 0 refs → may be genuinely dead; the new bucket would correctly reveal it.)

### #2 — Tiered output
Split the flat "REMOVAL CANDIDATE" list into `likely-dead` vs
`needs-manual-review (native/config)`. Stops true positives drowning in structural noise.

### #3 — Native-plugin awareness
Cross-reference `.flutter-plugins-dependencies` so native-declared packages are tagged
"native plugin — verify Dart call sites" (a hint to a human), not a bare removal candidate.
Declared ≠ used, so never auto-keep on this basis.

### #4 — Matcher gaps (latent; no live failures today)
The regex only matches `import 'package:…'`. Misses:
- `export 'package:…'` (barrel re-exports) — none in `lib/` today.
- Conditional/deferred imports `… if (dart.library.io) 'package:foo/…'` — package sits in
  the `if`-clause, missed. None today. Common for web/io splits.
Cheap to harden the regex now.

### #5 — Dependency-hygiene checks
- **Misplaced dependency**: a runtime `dependencies:` package imported only from `test/`
  should be a `dev_dependency`. The script counts test imports toward runtime deps, so it
  can't see this. Split import counts by source dir to enable the check.
- **Dead allowlist entries**: an `INDIRECT_REQUIREMENTS` key no longer in pubspec is
  silently ignored (allowlist rot). Warn on stale entries.
- **`dependency_overrides`** (vendored forks) are not classified/surfaced at all.

### #6 — Automation ergonomics
- `--fail-on-candidates` → non-zero exit so the monthly cron can gate/alert instead of
  scraping stdout (script currently always exits 0).
- Externalize `INDIRECT_REQUIREMENTS` to a YAML the monthly review owns, instead of
  editing the `.py`.

### #7 — Durable false-positive recovery registry (the missing piece)
See §4.

### #8 — Trial-removal recovery model (ADR)
See §5.

### #9 — Concrete `local_notifier` removal review
Live candidate: 0 Dart usage, native-declared, needs Dart calls it never receives. Decide
keep vs remove — a good first exercise of the trial-removal model.

### #10 — Document the native-dependency limitation
The allowlist is the actual safety mechanism for native-only deps; document the
maintenance rule in `doc/process/dependency_lifecycle.md`.

## 4. False-positive recovery — current state and the gap (#7)

**Destructive safety: exists.** Flagging is advisory only; the decision task gates actual
removal (developer chooses "approve removal or keep"). Nothing is auto-removed.

**Suppression ("stop flagging this"): effectively absent for the classes that occur.**
- The only suppression channel is `INDIRECT_REQUIREMENTS`, whose documented rule requires
  naming a consuming *dependency*. Config-referenced (`very_good_analysis`, `custom_lint`,
  `clean_architecture_kit`) and standalone-native (`local_notifier`) deps have no consuming
  dependency to name → they **cannot** be legitimately suppressed there.
- The "keep" decision is **not durable**: the decision task is reused/reset to `pending`
  each cycle; only the cycle month + proposal path are recorded. No keep/acknowledged
  ledger exists, and the script reads nothing but pubspec + source. Probe confirmed: no
  such file under `automation/dependency_reviews/`.

**Consequence**: the same false positives resurface every month and must be re-adjudicated
→ alert fatigue → risk of a rubber-stamp "approve" that removes a genuine false positive.

**Proposed recovery path — an acknowledged-keep registry.**
A data-owned file, e.g. `automation/dependency_reviews/kept.yaml`:
```yaml
- package: very_good_analysis
  class: config            # indirect | config | native | other
  reason: "analyzer ruleset referenced in analysis_options.yaml"
  acknowledged: 2026-06-03
```
The decision task **appends** to it when the developer says "keep" (no code edit). The
script **reads** it and routes those packages into an `acknowledged — kept` bucket so they
drop out of the active removal-candidate list. Gives every false-positive class a path,
makes the decision durable + auditable, and preserves the human gate for genuinely new
candidates.

## 5. Trial-removal recovery model (ADR draft) (#8)

**Idea (user)**: instead of the human searching the codebase to justify a "keep", treat
removal as a reversible experiment: baseline-green → remove dep → re-run oracle →
`git revert` if red.

**Sound, but with a trap.** Removal candidates are the *no-import* set by definition. For
them, removal produces no compile error, no build error, and usually no test failure —
because nothing references them. So a **green run is necessary-not-sufficient**; it's
weakest precisely for the population it targets. Strong signal only exists for invisible
couplings: native startup/registration side-effects, code-gen tools
(`build_runner`/`*_generator` — breaks `dart run build_runner build`, not `flutter test`),
runtime asset/DI wiring, and analyzer/lint plugins (removing them *silently weakens*
analysis — `flutter analyze` may still pass).

**Oracle by dependency class:**

| Class | Authoritative "safe to remove?" oracle | Trial-removal valid? |
|---|---|---|
| No-import pure-Dart runtime | full `flutter test` + integration/smoke | Yes, bounded by coverage |
| No-import **native** plugin | per-target-platform CI build + platform smoke | Only if every target platform has a green CI lane |
| Code-gen / build tool | `dart run build_runner build` succeeds + generated files unchanged | Special — run codegen, not tests |
| Analyzer / lint / config | static scan of `analysis_options.yaml` | **No — never trial-remove; tests blind** |

**CI coverage today** (`.github/workflows/`): `build_windows.yml` (windows-latest:
`flutter build windows --release` + an FFI test + `flutter test`) and an `ubuntu-latest`
lane (`flutter test` + `flutter build apk --release`). So: **Windows fully covered;
Android build-only (no device tests); Linux-desktop, macOS, iOS not covered.**

**Per-plugin target platforms** (`.flutter-plugins-dependencies`, probe):
```
flutter_zxing    android, ios, linux, macos, windows
local_notifier   linux, macos, windows
screen_capturer  windows
tray_manager     linux, macos, windows
wakelock_plus    android, ios, linux, macos, web, windows
window_manager   linux, macos, windows
```

**Proposed gating rule:**
> A trial-removal is **auto-confirmable only when every target platform listed in
> `.flutter-plugins-dependencies` for that package is covered by a green CI lane that
> builds + smoke-tests that platform.** Otherwise it is "unconfirmable on {…}" → route to
> the human gate / defer until that CI lane exists.

Today this means `window_manager`/`tray_manager`/`local_notifier` are confirmable on
Windows only (linux/macos blind) → **not** auto-confirmable; defer. The rule degrades
gracefully and self-activates when Apple/Linux lanes land.

**Elegant upside**: when a trial-removal goes red, the failure (compile error, Windows
link error, failing test name) **is the durable keep-justification** — it names the
consumer, exactly what `INDIRECT_REQUIREMENTS` demands and humans struggle to write. So a
failed experiment **auto-populates `kept.yaml`** (§4) with concrete evidence. The two
recovery paths compose.

**Mechanics**: do trial-removal on a throwaway branch/worktree (factory already uses
worktrees), push for CI, merge-or-discard; `git revert`/discard is clean only when
isolated — never on `develop`. Batch confirmable candidates to amortize CI; on red,
split/bisect (no-import deps are independent → batching is low-risk).

**Honest residual risk (must be stated in the ADR, not hidden)**: runtime Dart paths with
no coverage, and any platform with no CI lane (macOS/iOS today, Linux-desktop,
Android-device). Trial-removal cannot confirm those; they fall back to the human gate or a
documented residual-risk acceptance.
