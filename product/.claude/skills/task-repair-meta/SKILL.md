Audit and repair all dependency metadata and non-standard frontmatter in `requirements_tasks/`. Full content reading required for detail agents. Call rarely (once per ~50 new files).

---

## Phase 1: Refresh ID Registry

```bash
python scripts/artifacts/generate_id_registry.py --requirements
```

Read `requirements_tasks/_meta/id_registry.md` — all agents use this as their cross-reference index.

## Phase 2: Dynamic Grouping

Run:
```bash
find requirements_tasks -name "requirements.md" | sed 's|/[^/]*$||' | sort | uniq -c | sort -rn
```

Group directories so **no single detail agent handles more than 12 requirements.md files**. Combine small sibling directories into one agent, split large ones by subdirectory. Keep the groupings in context — you will use them to spawn Phase 4 agents.

---

## Phase 3: Dependency Oracle (1 sequential agent)

Spawn ONE agent before any parallel agents. Wait for it to finish.

**This agent:**
1. Globs ALL `requirements_tasks/**/requirements.md`.
2. For each file: reads **frontmatter + first 80 lines only** (not full content).
3. Extracts all REQ-* IDs mentioned as cross-references, preconditions, or dependencies.
4. Writes results to `requirements_tasks/_meta/dependency_map.md`:

```yaml
# Auto-generated by improve-requ-task-meta-info. Do not edit manually.
REQ-FUNC-005:
  inferred_after:
    - REQ-NFUNC-001  # uses Clean Architecture Patterns
  inferred_blocks:
    - REQ-FUNC-012   # mentioned as prerequisite in scope
```

Only include REQ-IDs where at least one dependency was found. Do not fabricate entries.

## Phase 4: Parallel Detail Agents (N agents)

Spawn N agents in parallel using the groupings from Phase 2. Each agent:

**Step 1 — Load inputs**
Read:
- `requirements_tasks/_meta/id_registry.md`
- `requirements_tasks/_meta/dependency_map.md`

**Step 2 — Find all files**
Glob `{assigned paths}/**/requirements.md` and `{assigned paths}/**/goal.md`.

**Step 3 — Read all files (full content)**
Read every file. Do not skip any, including completed/cancelled ones.

**Step 4 — Apply rules below using the Edit tool.**

---

### Rules for requirements.md

#### A. Non-standard frontmatter

A requirements.md is non-standard if it **lacks `id`** or has **no frontmatter block at all**.

1. Find `id` in id_registry.md by matching the folder name. If absent, derive from sibling requirements (next available number).
2. Infer all missing fields:
   - `stakeholder`: `functional/client` → `client`; `functional/therapist` → `therapist`; `non-functional` or `process` → `developer`; `functional/shared` → read content to determine.
   - `status`: content/tasks indicate completion → `implemented`, else `defined`.
   - `created`: today's date if absent.
   - `urgency` / `impact` / `effort`: infer from content scope, number of ACs, and strategic importance.
   - `after` / `blocks`: seed from dependency_map.md, verify against full content before adding.
   - `trackable_items`: see rule C.
3. Write complete standard frontmatter **before** existing content.

**Standard requirements.md frontmatter:**
```yaml
---
id: REQ-[CATEGORY]-[NUM]
urgency: [1-5]
urgency_reason: "[U-code]"
impact: [1-5]
impact_reason: "[I-code]"
status: defined|implemented|cancelled
effort: XS|S|M|L|XL|XXL  # XXL only for epic-level requirements
stakeholder: client|developer|therapist
created: YYYY-MM-DD
after: []
blocks: []
trackable_items:
  acceptance_criteria:
    - id: AC-01
      text: "..."
---
```

#### B. Dependency updates (apply to all requirements.md)

- Use dependency_map.md as starting point — verify each entry against full content before adding.
- Remove stale `after` entries (deprecated, nonexistent, or `implemented` IDs where the dependency no longer applies).
- Resolve text strings in `blocks` to proper REQ-* IDs via id_registry, or add `# TODO: resolve ID`.
- Preserve inline comments on existing entries.

```yaml
after:
  - REQ-FUNC-006  # Security layer must be defined first
  - REQ-NFUNC-001  # Architecture patterns required
```

#### C. trackable_items inference

Parse from content if `trackable_items` is missing or incomplete:

- **Functional / non-functional**: Find `## Acceptance Criteria` section. Extract each item (numbered or bulleted). Assign sequential IDs `AC-01`, `AC-02`, …
- **Process** (path contains `process/`): Extract all `## ` headings as sections with `SEC-01`, `SEC-02`, … format:
  ```yaml
  trackable_items:
    sections:
      - id: SEC-01
        name: "Overview"
        heading: "## Overview"
  ```
- If a `trackable_items` block already exists but is **incomplete**, append missing items only — do not overwrite existing IDs.

---

### Rules for goal.md (tasks)

**Mechanical:**
1. Do not modify `after` for `cancelled` tasks — leave as historical record.

**Semantic analysis:**
- `awaiting`: seed from dependency_map.md for the parent requirement. Verify against content. Remove entries where referenced requirement is now `implemented`. Accepted ID types: TASK-*, REQ-*, FLOW-*, or any project artifact ID.
- Add obviously missing cross-task dependencies.
- **Blocked status rule**: If `status: blocked`, verify that `awaiting` is non-empty OR `awaiting_note` is non-empty. If both are empty, flag as a repair issue and prompt user for the reason.

**Non-standard frontmatter** — missing `task_id`:
1. Determine `parent_requirement` from folder path via id_registry.md.
2. Check sibling goal.md files → assign next sequential task number.
3. Infer `type` from folder name (`explore_*` → `explore`, `impl_*` → `impl`).
4. Infer `status`: `(completed)` suffix in folder name → `completed`.
5. Write complete standard frontmatter **before** existing content.

**Standard task frontmatter:**
```yaml
---
task_id: TASK-[CATEGORY]-[PARENT_NUM]-[TASK_NUM]
type: explore|impl|analyze
parent_requirement: REQ-[CATEGORY]-[NUM]
urgency: [1-5]
urgency_reason: "[code like U4-DEP or U3-SPRINT]"
impact: [1-5]
impact_reason: "[code like I5-MVP or I4-DATA]"
status: pending|ready|in_progress|blocked|review|completed|cancelled
effort: XS|S|M|L|XL  # XXL is forbidden in tasks
created: YYYY-MM-DD
after: []
awaiting: []
awaiting_note: ""
covers:
  acceptance_criteria: []
  sections: []
scope_description: "[one sentence describing what this task accomplishes]"
---
```

Infer urgency/impact from parent requirement's values when not determinable from content.

## Phase 5: Cross-Category Reconciliation (1 sequential agent)

After all Phase 4 agents complete:

1. Glob ALL `requirements_tasks/**/requirements.md`.
2. Read frontmatter only from each.
3. Build map: `{REQ-ID: {after: [...], blocks: [...], file_path: "..."}}`
4. For every pair where `A.after` contains `B` but `B.blocks` does NOT contain `A`: edit B to add `A`.
5. Detect cycles — do NOT add an edge that creates a cycle; log the conflict instead.
6. Report all changes made and unresolved conflicts.

## Key Principles

- **Oracle reads partial content** (frontmatter + 80 lines) for efficiency; detail agents read full content.
- **dependency_map.md is a hint, not authority** — detail agents verify before applying each entry.
- **Append, don't reformat** — preserve inline comments and existing formatting.
- **Cross-references use REQ-* IDs only** — never folder paths or text strings.
- **Cycles are blockers** — never introduce circular dependencies; report and skip.
- **Completed/cancelled status is history** — update after only if clearly wrong.
